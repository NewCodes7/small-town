## 1. VU15 — 꺾임의 정체는 버퍼 풀 교체다

VU15에서 처리량이 14.33 → 10.19로 떨어지는데 **DB CPU는 오히려 78% → 84%로 올라간다.**
즉 DB가 더 열심히 일하면서 결과는 덜 나온다. 원인이 `blks/req`에 보인다:

| VU | RPS | blks/req | 요청당 MB |
|---|---|---|---|
| 5 | 12.85 | 14,107 | 110 |
| 10 | 14.33 | 13,531 | 106 |
| **15** | 10.19 | **19,915 (+47%)** | **156** |

> **⚠️ 이 장의 진단은 조건부다 (7장).** S에서 이미 재현되지 않았고(14,077로 평평), T에서는 요청당
> 블록 자체가 2,153으로 6.4배 낮아지며 꺾임이 사라졌다. 아래 "요청당 비용이 부하에 따라 커진다"는
> **당시 DB 조건(요청당 106 MB > shared_buffers 256 MB)에서만 성립**한다 — 요청당 16.5 MB가 되면
> 애초에 버퍼 풀을 쓸어내지 않으므로 증폭 자체가 일어나지 않는다.

**같은 쿼리인데 요청당 블록이 47% 늘었다.** 동시성이 오르면 각 요청의 워킹셋이 서로를 밀어내
같은 블록을 다시 읽는다 — 선행 문서 5.3의 "검색 한 번이 132MB를 256MB 버퍼 풀로 쓸어낸다"가
포화에서 실제로 증폭되는 모습이다. 요청당 비용이 부하에 따라 **커지는** 구조라
동시성을 올리는 것으로는 이 지점을 넘을 수 없다.

동시에 커넥션 압력도 붙는다 — 획득대기 0.050 → 0.117s, pending 6 → 16.

## 2. VU20 — 측정 불가 영역 (관측 스택 붕괴)

VU20 구간(11:29:35~11:32:35)에서 **DB·호스트 지표가 전부 비어 있다.** 수집 실패가 아니라
**앱 호스트의 관측 스택이 그 시각에 죽었기 때문**이다.

앱 호스트 메모리 타임라인 (2분 간격, 지표가 끊기는 지점이 사망 시각):

| 시각 | 레벨 | MemAvailable | swap-in |
|---|---|---|---|
| 11:18 | (시작 전) | 167MB | 189 pages/s |
| 11:20 | VU5 | 120MB | 978 |
| 11:22 | VU10 | 111MB | 2,541 |
| 11:24 | VU10 | **92MB** | 2,557 |
| 11:26 | VU15 | 124MB | 2,511 |
| 11:28 | VU15 | 172MB | 1,837 |
| 11:30 | VU20 | **(지표 끊김)** | 1,111 |

호스트 RAM 1,906MB에서 가용 92MB까지 내려갔고, VU20 진입과 함께
**Prometheus·Grafana·Loki·Tempo가 응답 불가**가 됐다. 부하 종료 후 20분이 지나도 회복되지 않아
(`/api/categories` 3~14초, Prometheus 000) **호스트 재부팅으로 복구**했다.
재부팅 후 Prometheus가 WAL을 재생하며 503을 거쳐 200으로 돌아왔고, **다행히 실행 데이터는 보존됐다** —
이 문서의 수치는 재부팅 이후 재수집한 것이다.

VU20의 5xx 48건은 정직한 풀 포화다:
`HikariPool-1 ... timed out after 3165ms (total=5, active=5, idle=0, waiting=16)` —
타임아웃이 설정값(3,000ms)대로 찍혔다. VU20은 요청당 커넥션 2개가 필요한 구조에서
동시 20 요청 = 수요 40 대 공급 5이므로 붕괴가 당연하다.

> **직전 실행(Q)의 8.4초 타임아웃과 다르다.** Q에서는 4.15초 GC 정지 때문에 스레드가 늦게 깨어나
> 3초 설정이 8.4초로 관측됐다(선행 문서 「다음」 항목). VU20에서는 설정값대로 3.1초라,
> 이 구간의 지배 요인은 GC가 아니라 **순수한 풀 초과 수요**다.

## 5. 앱 호스트 메모리 — 누가 차지했나

2장의 관측 스택 붕괴와 「다음」의 1순위를 정산하려고, 실행 시각의 Prometheus 데이터를 **사후 조회**해
앱 호스트 메모리를 분해했다(재부팅 전 데이터가 보존된 덕에 가능했다).
**결론: 1순위는 관측 스택이 아니라 백엔드 JVM의 커밋 힙이고, 2순위인 Prometheus는
k6 remote-write의 URL 카디널리티가 원인이다.**

### 5.1 총수요는 RAM의 1.6배였다

11:24 UTC(VU10 말~VU15 초, 압박 최대) 실측:

| 항목 | 값 |
|---|---|
| MemTotal | 1,906 MiB |
| AnonPages (프로세스 상주) | **1,474 MiB** |
| Swap used (2,048 중) | **1,530 MiB** |
| Cached / Slab / PageTables | 117 / 98 / 18 MiB |
| MemAvailable | 92 MiB |

**익명 메모리 총수요 = 1,474 + 1,530 ≈ 3,004 MiB = RAM의 1.6배.** 페이지캐시는 117MB까지
쪼그라들어 있었다 — 1장의 DB 쪽 `blks/req` 증가와는 **별개의 축**으로, 앱 호스트에는 캐시가
남아 있지 않았다.

### 5.2 1순위 — 백엔드 JVM: used가 아니라 **committed가 비용이다** (used 수치는 5.9에서 정정)

「다음」에 적었던 "힙 276MB/1,024MB로 여유가 있다"는 **used 기준의 오독**이다.
호스트가 물리 메모리 비용을 치르는 건 committed다. 11:24 실측:

| 영역 | committed | used |
|---|---|---|
| G1 Old Gen | 841 MiB | 258 MiB |
| G1 Eden | 81 MiB | 63 MiB |
| G1 Survivor | 16 MiB | 15 MiB |
| **heap 합** | **984 MiB** | 337 MiB |
| Metaspace | 158 MiB | 155 MiB |
| CodeHeap + Compressed Class | 87 MiB | 68 MiB |
| **nonheap 합** | **244 MiB** | 206 MiB |
| direct buffer | 27 MiB | — |

- JVM 커밋 총합 ≈ **1,255 MiB**, 스레드 스택·GC·JIT 네이티브까지 더하면 **약 1.3 GB = 호스트 RAM의 68%**
- `-Xms512m -Xmx1024m`(`Dockerfile:16`)에서 G1이 부하 중 상한까지 확장했고, 확장분은 쓰지 않아도
  즉시 반납되지 않아 그대로 스왑 대상이 된다
- 대조군: **같은 blue의 idle 커밋 힙은 542 MiB**(08-18 측정). 부하 때만 +440MB가 붙는 구조다

> **⚠️ 2026-08-19 정정 — 위 `used 337 MiB`는 11:24 한 시점 샘플이다.** R 구간(11:18~11:34)을
> `max_over_time`으로 다시 뜨면 **힙 used 피크는 601 MiB**이고, S 구간은 **652 MiB**다.
> 다만 그 대부분은 Eden 쓰레기라 GC로 압축되는 몫이고, 실제 요구량인 live set(Old Gen)은
> **R 341 / S 295 MiB**다. 5.6 조치 2의 근거를 이 값으로 교체했다 — 5.9 참고.

### 5.3 2순위 — Prometheus: k6가 검색 키워드를 라벨에 실어 보냈다

11:24 기준 **활성 시계열 158,716개**의 출처:

| 출처 | 시계열 수 |
|---|---|
| job 라벨 없음 = **k6 remote-write** | **151,911 (96%)** |
| postgres_exporter | 3,324 |
| backend | 2,470 |
| node-exporter ×2 (앱·DB) | 1,011 |

원인은 k6 태그다. 실제 시계열 라벨을 뽑으면 `name`/`url`이 **쿼리스트링까지 포함한 전체 URL**이다:

```
name = "https://newcodes.net/api/search/articles/loadtest?keyword=opentelemetry%20코루틴&page=1&size=10"
url  = (같은 값)
```

시나리오가 `tags: { endpoint: 'search', level }`만 주고 `name`을 덮어쓰지 않으며
(`scenarios/ramp-limit-finder.js:97`), `systemTags`로 `url`을 끄지도 않아 k6 기본값이 그대로 라벨이 된다.
키워드가 요청마다 다르니 **키워드 수 = 카디널리티**가 된다:

- `k6_http_req_duration_p95` 한 메트릭에 **3,452 시계열** (= 유니크 URL 수)
- k6 메트릭 이름 **56개** (`K6_PROMETHEUS_RW_TREND_STATS`의 통계 6종 × trend 8종 + 카운터/게이지)
- → **실행 1회당 15만~19만 시계열**. 게다가 `testid`가 매번 달라 실행끼리 절대 합쳐지지 않는다
- 최근 1시간(Q 10:38 + R 11:18) 창으로 세면 그 한 메트릭만 **11,755 시계열** →
  head 전체로는 **약 65만 시계열** 규모다 (stale 시계열도 2시간 블록이 잘릴 때까지 head에 남는다)

Prometheus 2.37의 head 시계열당 통상 3~4 KiB로 잡으면 **head+WAL만 대략 1~2 GB**다.
VU20에서 관측 스택이 통째로 죽고 재부팅 후 Prometheus가 큰 WAL을 재생하며 503을 거친 것과 맞는다.
같은 시각 **백엔드는 설정값대로 3.1초 Hikari 타임아웃을 정직하게 냈다**(2장) — 먼저 무너진 쪽은
백엔드가 아니라 Prometheus다.

누적 증거도 있다. 익명 총수요(anon + swap used)는 10:00 2,262 MiB → 11:20 2,525 MiB로 **+263 MiB**
늘었는데, 이 구간의 배포(green→blue 교체, 10:32)로 설명되는 몫은 +120 MiB뿐이다. 나머지는 Q 실행이
남긴 시계열이 head에 계속 머문 몫으로 본다.

### 5.5 이 분해의 한계와 확정 방법

**앱 호스트에는 cAdvisor도 process-exporter도 없어 컨테이너별 RSS가 Prometheus에 남지 않는다.**
위 표에서 JVM과 exporter만 실측이고, Prometheus·Tempo·Loki·Grafana는 추정이다. 확정하려면
운영 셸에서 아래를 남겨야 한다:

```bash
# 현재 상태(idle 기준선)
docker stats --no-stream --format "table {{.Name}}\t{{.MemUsage}}\t{{.MemPerc}}"
smem -k -s swap -r | head -20        # 스왑까지 포함한 프로세스별 점유 (apt install smem)

while true; do docker stats --no-stream --format '{{.Name}} {{.MemUsage}}' \
  | sed "s/^/$(date -u +%H:%M:%S) /" >> /tmp/memstat.log; sleep 10; done &
```

### 5.8 Tempo 억제 (2026-08-18) — 544 MiB의 정체는 "필요량"이 아니라 GC 목표였다

5.7에서 Tempo가 실측 2위(544 MiB, 피크 RSS 625)로 드러났지만 **왜** 그만큼 쓰는지는 몰랐다.
`prometheus.yml`에 Tempo job이 없어 내부 지표가 남지 않았기 때문이다. Grafana 데이터소스 프록시로
`:3200/metrics`와 `/debug/pprof/heap`, `/status/config`를 직접 떠서 분해했다.

#### 실측 — 정상 상태 live heap은 85 MB뿐이다

| 지표 | 값 |
|---|---|
| `HeapAlloc` (GC 직후 live) | **85 MB** |
| `HeapInuse` / `HeapSys` | 95 MB / 818 MB |
| `HeapReleased` | 579 MB (이미 OS에 반납) |
| `NextGC` (다음 GC 목표) | 164 MB … **직전 관측 시점엔 738 MB** |
| `MaxRSS` (기동 후 피크) | **625 MiB** |
| `GCCPUFraction` | **0.0006 (0.06%)** |
| `go_goroutines` | 1,011 |
| 인제스터 live traces | **4개 / 6 KB** |
| 블록 수 / 누적 flush | 170 / 45개 (54 MB → 평균 **1.2 MB/블록**) |
| 22시간 누적 수신 | 326,755 spans / 257 MB |

**즉 Tempo는 544 MiB가 필요한 게 아니다.** 상주분의 대부분은 순간 버스트가 남긴 자국이다.

#### 원인 1 — GOGC=100 기본값이 버스트 기준으로 힙 목표를 2배로 잡는다

Go GC는 `GOMEMLIMIT`이 없으면 힙 목표를 **직전 live의 2배**로 잡는다. 블록 완성 중 live가 잠깐
370 MB까지 뛰면 목표가 738 MB가 되고, 그 사이 OS에서 받아온 페이지가 RSS로 눌러앉는다.
**GC CPU는 0.06%밖에 안 쓰고 있었다** — 메모리를 CPU로 바꿔 쓸 여유가 3자릿수 배로 남아 있었다.

#### 원인 2 — 힙 프로파일이 지목한 곳은 인제스터의 블록 완성 경로다

`inuse_space` 1위(41.4 MiB)와 `alloc_space` 1위(1,749 MiB)가 같은 스택이다:

```
parquet-go.newRowGroupRows ← FileRowGroup.Rows ← vparquet4.(*rowIterator).Next
  ← vparquet4.CreateBlock ← tempodb.CompleteBlockWithBackend ← ingester.(*instance).CompleteBlock
```

WAL 블록을 읽어 완성 블록으로 다시 쓰는 경로다. 뒤이어 `vparquet4.newRowPool`(1,007+288 MiB),
`BufferedWriter.Write`(494), `ZstdCodec.Encode`(321)까지 전부 같은 flush/compaction 축이다.
쿼리는 무관하다 — 기동 후 검색이 **6건**뿐이었다.

#### 원인 3 — 기본값이 이 호스트 규모와 3~100배 어긋나 있다 (`/status/config` 실측)

| 키 | 기본값 | 이 호스트의 현실 |
|---|---|---|
| `block.parquet_row_group_size_bytes` | **100 MB** | 실제 블록 평균 **1.2 MB** — 100배 과대 |
| `pool.max_workers` / `queue_depth` | **400 / 20,000** | 2 vCPU. goroutine 1,011개의 출처 |
| `search.read_buffer_count` × `size` | 32 × 1 MiB = **32 MiB/리더** | `max_workers`와 곱해진다 |
| `query_frontend.search.concurrent_jobs` | **1,000** | 블록당 잡 1개 → 170 블록 동시 조회 |
| `ingester.concurrent_flushes` | 4 | 완성 1건이 수십 MB |
| `global.max_bytes_per_trace` | 5 MB | 트레이스 1건이 힙을 밀 수 있다 |

> **부수 발견 — 아직 안 터진 폭탄이 하나 있다.** `pool.max_workers`(400) × `read_buffer_count`(32 MiB)는
> 상한이 없다. Grafana Explore에서 7일 범위 TraceQL 검색을 한 번 돌리면 이론상 수 GB를 잡는다.
> 지금까지 안 터진 건 검색이 6건뿐이었기 때문이다. RAM 1,906 MiB 호스트에서 이건 우연에 기댄 상태였다.

「다음」에 적어둔 건 `TRACING_SAMPLING=0.1`이었지만, 측정해 보니 **그건 틀린 레버다.**

- 22시간 요청 19,412건 중 부하테스트가 **7,775건(40%)**, 평시 트래픽은 11,637건 = **약 0.15 RPS**다
- 전역으로 0.1을 걸면 평시 트레이스가 **7분에 1건** 수준으로 떨어져 운영 관측성이 사실상 사라진다.
  정작 줄여야 할 버스트는 부하테스트 쪽인데 그건 10%만 줄어든다

백엔드는 커스텀 `Sampler` 빈이 없어 Boot 기본값 **`ParentBased(TraceIdRatioBased(1.0))`**를 쓴다.
따라서 **sampled 플래그가 0인 W3C `traceparent`가 들어오면 그 요청은 span을 하나도 만들지 않는다.**
`lib/config.js`의 `bypassHeaders()`(전 시나리오가 공유, `rate-limit-check.js`만 의도적으로 미사용)에
이 헤더를 붙였다. `LT_TRACE_RATIO`(기본 **0.02**)만큼은 헤더를 안 붙여 정상 트레이스로 남긴다 —
**워터폴 진단은 살리고 양은 1/50로 줄인다.** 운영 샘플링(1.0)은 손대지 않는다.

- `sampled=1`인 traceparent를 보내지 않는 이유: 존재하지 않는 부모를 가리켜 루트가 끊긴 트레이스가 된다
- 부작용: 억제된 요청도 MDC의 traceId는 남으므로 **Loki 로그의 traceId를 클릭하면 트레이스가 없다.**
  부하테스트 로그에 한정된다
- ⚠️ 이 변경은 `lib/`에 있어 **ECR 이미지 재빌드가 필요하다** (5.7의 조치 1과 달리 실행 레이어가 아니다).
  「다음」의 이미지 재빌드 항목과 함께 나가야 한다

### 5.9 커밋 힙의 진짜 비용은 장부가 아니라 GC 정지다 (2026-08-19)

5.7 표의 「GC 최대 정지 4.15s → 2.52s」는 지금까지 원인 없이 떠 있던 한 줄이었다. 실측해 보니
**이 정지는 GC가 일을 많이 해서가 아니라, 스왑아웃된 힙 페이지를 STW 구간 안에서 폴트인하느라
생긴 것**이다. 조치 2(`-Xmx`)의 명분이 여기서 바뀐다 — 메모리 절감이 아니라 **지연 제거**다.

#### 메커니즘 — GC는 LRU에게 최악의 접근 패턴이다

1. `-Xmx1024m`이라 부하 중 G1이 **912 MiB까지 커밋**한다. 실제 live set은 **300 MiB 남짓**이라
   나머지 600 MiB는 커밋됐지만 한동안 아무도 안 만지는 페이지다.
2. 커널의 축출 기준은 "최근에 안 만진 익명 페이지" — 위 600 MiB가 정확히 그 대상이다.
   RAM 1,906에 관측 스택이 동거하니 실제로 스왑으로 나간다.
3. **그런데 그 페이지를 주기적으로 훑는 유일한 작업이 GC다.** Young GC조차 Eden/Survivor 스캔에
   더해 remembered set·card table을 따라 Old Gen 영역을 건드린다. 커널이 "차갑다"고 판단해
   내보낸 페이지를 GC가 정확히 되불러온다.
4. 폴트인은 디스크 랜덤 4KB 읽기이고, 이게 **STW 구간 안에서** 벌어진다. GC 스레드가 디스크를
   기다리는 동안 애플리케이션 스레드는 전부 정지다.

#### 실측 — 일감은 오히려 줄었는데 시간은 100배다 (S 실행, 08-18)

같은 실행 안의 같은 종류 GC(`G1 Young Generation` / `G1 Evacuation Pause`)다:

| 시각 (UTC) | GC 횟수/분 | 평균 정지 | 최대 정지 | swap-in (pages/s) |
|---|---|---|---|---|
| 07:50 (유휴) | — | — | **0.013s** | **1.7** |
| 07:58 | 9.3 | 0.030s | 0.228s | 428 |
| 08:00 | 6.7 | 0.023s | 0.052s | 60 |
| 08:02 | 9.3 | 0.029s | 0.137s | 368 |
| **08:03** | 9.3 | **0.589s** | **2.519s** | 205 |
| 08:04 | **4.0** | 0.015s | — | **958** |
| 08:05 | **1.3** | 0.233s | 1.398s | **1,136** |

- **정상 young GC는 23~56ms다** — 부하 내내 그렇다. 그런데 하나가 **2,519ms로 같은 실행 평균의 45~110배**다.
- **일감이 늘어서가 아니다.** young 대피 비용은 살아남은 객체 양에 비례하는데, 2.5초짜리가 터진
  08:03 시점 **Eden은 17 MiB**였다. 일감은 오히려 적다.
- **GC 횟수가 오히려 줄어든다**(9.3 → 4 → 1.3회/분). GC가 빨라진 게 아니라 JVM이 디스크를
  기다리느라 갇혀 있었다는 뜻이다.
- 유휴(07:50)와의 대조가 결정적이다 — 같은 힙·같은 콜렉터·같은 코드인데 **13ms vs 2,519ms(190배)**,
  달라진 변수는 swap-in **1.7 → 1,136 pages/s** 하나뿐이다.

#### 이것이 5xx로 이어지는 경로

2장 각주가 관측만 하고 원인을 연결하지 않았던 부분이다:

```
커밋 힙 912 (live 300) → 차가운 600 MiB 스왑아웃 → GC가 STW 안에서 폴트인
  → 4.15s 정지 (R) → 요청 스레드가 Hikari 커넥션을 쥔 채 정지
  → 대기 요청의 타임아웃 시계는 계속 흐름 → 3초 설정이 8.4초로 관측 → 5xx
```

문서는 이걸 "Q의 8.4초는 GC 탓, VU20의 3.1초는 순수 풀 초과"로 **분류만** 했다. 그 GC의 정체가
스왑이고 스왑의 정체가 커밋 힙이면, **`-Xmx` 한 줄이 그 8.4초의 뿌리**다.

#### 조치 2의 근거·기대효과 재작성

| 항목 | 종전 (5.6) | 교체 |
|---|---|---|
| 근거 | "used 최대 337MB라 여유 있다" | **live set 300~341 MiB** (used 피크 601/652는 대부분 Eden 쓰레기라 GC로 압축된다) |
| 여유 | 충분 | **1.5배로 빠듯** (G1 통상 권장 2배) |
| 기대효과 | 메모리 ~440 MiB 절감 | 스왑 가능한 차가운 힙 **400 MiB 소멸 → GC 폴트인 대상 자체가 없어짐**. 메모리 절감은 부산물 |
| 대가 | 없음 | young GC 횟수 증가(분당 7~9회 → 그 이상). 정상 1회가 30ms이고 CPU는 남으므로 2,519ms 하나와 바꾸면 압도적으로 남는다 |

**유휴 절감은 0이라는 점도 분명히 해둔다.** `-Xms512m`이라 현재 유휴 커밋이 이미 **525 MiB**다
(08-19 실측, used 250). Xmx만 512로 내리면 힙이 512에 고정되어 유휴 footprint는 그대로고,
절감은 **부하 중 912 → 512**에서만 생긴다. 유휴 상태에서도 스왑 사용 **880~990 MiB** /
MemAvailable **120~380 MiB**인 이 호스트의 만성 압박은 이 조치로 안 없어진다(5.8·6장과 같은 결론).

#### ⚠️ 방향이 뒤집힐 수 있는 조건 — 순서가 중요하다

스왑 압력이 그대로인 채 힙만 줄이면 **GC 횟수가 늘어 폴트인 기회도 같이 는다.** "힙이 작아
페이지가 따뜻하게 유지되는" 효과가 이기느냐 "횟수가 늘어" 지느냐는 호스트 여유에 달렸다.
→ **Tempo 억제가 실제로 먹은 것을 확인한 뒤** Xmx를 건드린다. 순서를 뒤집으면 개선이 아니라
악화일 수 있고, 무엇보다 어느 쪽이었는지 구분이 안 된다.

#### 시행 방법 — 이미지 재빌드가 필요 없다

`Dockerfile:19`가 shell form(`java $JAVA_OPTS -jar app.jar`)이라 compose `environment`의
`JAVA_OPTS`가 `Dockerfile:16`의 ENV를 덮는다. `DB_POOL_SIZE`/`DB_MAX_PARALLEL_WORKERS`와
**똑같은 실험 패턴**으로 넣고 재기동만 하면 A/B가 된다 (재빌드·이미지 푸시 없음).

```yaml
# docker-compose.yml, backend blue/green 공통 env
- JAVA_OPTS=${JAVA_OPTS:--Xms512m -Xmx1024m -XX:+UseG1GC -XX:MaxGCPauseMillis=200}
```

- 유휴 footprint까지 노리면 **`-Xms`도 같이 내려야 한다**(`-Xms256m -Xmx512m`). Xms를 512에 둔 채
  Xmx만 내리면 고정 힙이 되어 반납 여지가 사라진다
- 상한을 안 내리는 대안: `-XX:MaxHeapFreeRatio=30 -XX:MinHeapFreeRatio=10 -XX:G1PeriodicGCInterval=60000`으로
  **반납을 빠르게** 하고 1024는 안전판으로 남긴다. live 341에 512는 1.5배라 빠듯하므로 실패
  모드(풀 GC 폭주)는 이쪽이 더 안전하다
- 어느 쪽이든 tempo가 받은 `mem_limit`(5.6 조치 3)을 backend에도 붙여야 실패 시 호스트 전체
  스래싱 대신 컨테이너 하나로 국한된다

#### 검증 쿼리

CONTAINER   NAME    CPU %    MEM USAGE / LIMIT     MEM %    PIDS
cbb2d43...  tempo   0.28%    65.43MiB / 400MiB     16.36%   23

`docker ps` 기준 **가동 21시간**이다(08-18 배포분). 조기 측정이 아니라 **정상 상태 값**으로 읽어도 되고,

#### 조치 j 실패 — 원인은 **bind mount inode**이고, nginx 함정과 같은 것이다

증상이 모순처럼 보였다:

```
06:23:51  Prometheus "Completed loading of configuration file"   ← SIGHUP 리로드 성공
호스트 ~/small-town/prometheus.yml 에 job_name: 'tempo' 존재    ← 파일도 정상
06:30     up{job="tempo"} 여전히 없음                             ← 그런데 타깃이 없다
```

**실측으로 확정했다** — 컨테이너가 보는 파일과 호스트 파일이 다른 파일이다:

```bash
$ grep -c tempo ~/small-town/prometheus.yml                         # 호스트
3
$ docker exec prometheus grep -c tempo /etc/prometheus/prometheus.yml   # 컨테이너
0
```

**Prometheus가 읽은 파일이 그 파일이 아니다.** `docker-compose.yml:154`는 `./prometheus.yml`을
**단일 파일 bind mount**하는데, 파일 마운트는 경로가 아니라 **inode를 묶는다.** `git pull`은 제자리
수정이 아니라 임시 파일 + rename이라 **inode가 교체된다** → 컨테이너는 계속 옛 inode를 본다.
SIGHUP은 그 **옛 내용을 성공적으로 다시 읽었다.** `docker ps` 기준 prometheus는 **2주 전 생성**이고
마지막 기동이 43시간 전(08-17 호스트 재부팅)이라, 그 사이 모든 `git pull`이 마운트에서 떨어져 나갔다.

**CLAUDE.md에 이미 적혀 있는 nginx 함정과 정확히 같은 메커니즘이다** —
*"Nginx 설정 변경 시 `sed -i` 금지 (inode 교체 → `docker restart newcodes-nginx` 필요)"*.
그게 nginx 전용 주의사항이 아니라 **bind mount된 모든 설정 파일의 문제**였다.

이 설명은 **왜 tempo만 반영됐는지도 설명한다** — tempo는 compose 정의(`GOMEMLIMIT`/`mem_limit`)가
바뀌어 **컨테이너가 재생성**되면서 마운트가 새 inode로 다시 걸렸고, prometheus는 compose 정의가
안 바뀌어 재생성 대상이 아니었다. 조치 a·b가 c~i를 데리고 들어온 셈이다.

```bash
docker restart prometheus     # 마운트를 현재 inode로 다시 건다. SIGHUP으로는 영원히 안 된다
```

> **리로드 vs 재기동 판정법**: 설정 *내용*만 바뀌었고 파일을 **제자리 수정**했다면 SIGHUP으로 충분하다.
> `git pull`·`sed -i`·에디터 저장처럼 **파일이 교체(rename)됐다면 재기동**이어야 한다.
> 판별이 애매하면 위처럼 **호스트와 컨테이너에서 같은 grep을 돌려 대조**하는 게 가장 빠르다 —
> 리로드 로그의 "성공"은 이 실패를 못 잡는다.

#### 배포 파이프라인의 진짜 문제

`deploy.sh`가 하는 일은 백엔드 blue/green 교체(`docker compose up -d newcodes-backend-blue`)와
nginx 재기동뿐이고 `prometheus`/`tempo`는 대상이 아니다(grafana만 별도 경로에서 `up -d`).
5.8에 적어둔 **"`./deploy.sh deploy` 후 확인"이라는 지침 자체가 틀렸다.**

여기에 inode 문제가 겹치면 실패 모드가 **조용하다**:
compose 정의가 바뀐 서비스는 재생성되며 설정이 따라 들어가고, 정의가 안 바뀐 서비스는
파일만 갈아입은 채 **옛 설정으로 계속 돈다 — 로그에는 "리로드 성공"이 찍힌다.**
관측 스택 변경 절차를 `deploy.sh`에 넣든 별도로 문서화하든 정해두지 않으면 이 조합이 반복된다.

### 7.2 Tempo — 조건부 통과. **측정 창을 잘못 잡아 처음엔 과대평가했다**

부하 창(06:45~06:56)만 보고 "피크 88.7 MiB, 목표 크게 통과"로 적었다가, 사후에 5시간
`max_over_time`으로 다시 뜨면서 **틀렸다는 것을 발견했다.** Tempo의 비용은 부하 중이 아니라
**부하가 끝난 뒤 다음 블록 완성 시점에 나타난다.**

#### 실측 — 30분 주기 스파이크, 피크 385.5 MiB

`max_over_time(process_resident_memory_bytes{job="tempo"}[5m])` (08-19, 5분 해상도):

| 시각 (UTC) | RSS |
|---|---|
| 06:45~06:56 (**부하 구간**) | 84~104 MiB |
| **07:05** | **385.5 MiB** ← 부하 직후 첫 블록 완성 |
| 07:35 / 08:05 / 08:35 | 254.8 / 260.5 / 209.8 |
| 09:05 / 09:35 / 10:05 | 208.3 / 248.7 / 242.7 |
| 10:35 / 11:05 | 261.9 / **297.5** |
| 그 외 상시 | 64~97 MiB |

**정확히 :05와 :35, 30분 주기다.** 원인은 `/status/config`에 있다 —
**`ingester.max_block_duration: 30m0s`**. 30분마다 블록을 끊어 완성하고, 그 경로가 5.8의 pprof가
지목한 `CompleteBlock → vparquet4 → parquet-go.newRowGroupRows`다. 5.8은
`complete_block_timeout`을 15m→5m으로 줄였지만 **`max_block_duration` 30m은 손대지 않았다** —
버스트의 *크기*를 정하는 건 이쪽이다.

#### 판정 정정

| 지표 | 5.8 목표 | 처음 보고 | **실제** | 판정 |
|---|---|---|---|---|
| RSS 피크 | < 300 MiB | ~~88.7~~ | **385.5 MiB** | ❌ **초과** |
| `GOMEMLIMIT` 300 | 소프트 상한 | — | 385 > 300 | ⚠️ 버스트 시 넘긴다(소프트라 정상 동작이지만 억제력이 없다) |
| `mem_limit` 400m | 하드 상한 | 여유 | **385.5 / 400 = 96.4%** | 🔴 **OOM-kill까지 3.6%** |
| GC STW 비중 | < 5% | 0.0096% | 0.0096% | ✅ (CPU 여유는 여전히 크다) |

**개선 폭도 다시 써야 한다.** 5.7의 544 MiB는 S 부하 중 `docker stats` 값이고, 여기 385.5는
T 부하 직후 피크다 — 비교 가능한 쌍으로 보면 **544 → 385 (−29%)**이지 −84%가 아니다.
상시 구간이 64~97 MiB로 낮아진 것은 사실이지만, **호스트를 위협하는 건 상시가 아니라 피크다.**

#### 남은 레버

1. **`ingester.max_block_duration` 30m → 10m** — 블록이 3분의 1이면 완성 버스트도 그만큼 작아진다.
   스파이크 자체를 줄이는 유일한 직접 레버다
2. `GOMEMLIMIT` 300 → 200은 **취소하지 않는다.** 7.2 초판에서 "next_gc 53 MiB라 실익 없음"으로
   적었으나 그건 상시 구간만 본 것이다. 버스트 때 넘기고 있으므로 낮추면 완성 중 GC를 더 돌려
   RSS를 누른다 — GC CPU가 0.0096%뿐이라 대가를 치를 여유가 있다
3. 조치 k(`traceparent` 억제)가 ECR 이미지에 들어가면 **부하테스트발 스팬이 1/50로 줄어**
   07:05 같은 부하 직후 피크가 사라진다. 다만 평시 :05/:35 스파이크(200~260)는 남는다
4. `mem_limit` 400m 유지 여부 — 지금은 96.4%까지 찼다. 1~3을 하기 전에 올리면 호스트 스래싱으로
   되돌아가므로, **레버를 먼저 당기고 그래도 부족하면 올린다**

> **방법론 교훈: 배치성 소비자는 부하 창 안에서 측정하면 안 된다.** Tempo·Loki·컴팩션처럼
> 주기적으로 몰아 처리하는 컴포넌트는 **부하 종료 후 최소 한 주기**를 포함해 측정해야 한다.
> 앞으로 사다리 수집 창은 부하 종료 +40분까지 잡는다.

### 7.3 앱 호스트 — 개선됐지만 스왑은 그대로다

| | R 피크 | S 피크 | **T 피크** |
|---|---|---|---|
| MemAvailable 최저 | 92 MiB | 164 MiB | **275 MiB** |
| swap used | 1,530 MiB | — | **1,041 MiB** |
| swap-in | 2,500 pages/s | 1,136 | **1,199** |
| **GC 최대 정지** | **4.15s** | **2.52s** | **0.93s** |
| 커밋 힙 최대 | 984 MiB | 840 | **815** |

- **GC 최대 정지 4.15 → 0.93초.** 5.9의 인과(커밋 힙 → 스왑 → STW 폴트인)와 방향이 일치한다
- **그러나 swap-in 피크는 1,199 pages/s로 S와 사실상 같다.** 스왑 압박 자체는 안 없어졌고,
  커밋 힙도 815 MiB까지 확장했다 — **5.9의 `-Xmx` 조치는 여전히 유효하며, 이 실행이 그 대조군이다**
- 총수요는 RAM 1,906을 여전히 넘는다(5.8·6장 결론 유지)

### 7.4 유효성 검증과 원인 추적 — 설정값은 기각, 세그먼트 누적이 새 가설

**캐시 오염은 없다.** 레벨당 완료가 4,154건으로 2-term 키워드 풀(2,525개)을 1.6배 넘겨 3장이
경고한 소진 구간에 들어갔으므로 판별법을 돌렸다:

| 레벨 | 완료 2xx | Loki `총:` (코어 실행) | 비율 |
|---|---|---|---|
| 5 | 4,154 | 4,014 | 0.97 |
| 10 | 4,426 | 4,175 | 0.94 |
| 15 | 4,310 | 4,073 | 0.95 |

코어가 매 요청 실제로 돌았다. 캐시 히트가 지배했다면 `총:`이 2,525 근처로 떨어졌어야 한다.
**5~6%의 부족분은 창 경계와 소수의 캐시 히트로 설명되는 수준이고, 6.4배 개선의 설명이 될 수 없다.**

**원인은 특정하지 못했다.** 배제된 것부터:

- ❌ **코드 변경** — 백엔드 마지막 커밋이 `838ae893`(08-17 10:25)로 R·S와 동일 빌드
- ❌ **캐시 오염** — 위 표
- ❌ **DB 호스트 캐시 온도** — 페이지캐시 24시간 평평(550~580 MiB)
- ❌ **앱 호스트 메모리** — 논리 읽기는 앱 속도와 무관

**원인은 BM25 mutable 세그먼트로 좁혀졌다.** `DB_MAX_PARALLEL_WORKERS` 가설은 **기각**됐다 —
`application-prod.properties:38`이 이를 connection-init-sql
(`SET max_parallel_workers_per_gather=${DB_MAX_PARALLEL_WORKERS:0}`)로 적용하는데 compose 기본값이
0이고, deploy 워크플로는 수동 `workflow_dispatch` 입력이 있을 때만 덮는다. 무엇보다
[`2026-08-08-search-checkout-workers-2x2-cachemiss.md`](2026-08-08-search-checkout-workers-2x2-cachemiss.md)에서
**08-08에 이미 0으로 확정**됐다 — R·S 때도 0이었다.

`paradedb.index_info` 실측(08-19)과 `docs/operations/BM25_MUTABLE_SEGMENT_RUNBOOK.md`(08-15)의
전후 기록을 대조하면 인덱스가 **런북의 "튜닝 후" 형태로 바뀌어 있다**:

| | 런북 기준선 (08-15) | 런북 목표 상태 | **현재 실측 (08-19)** |
|---|---|---|---|
| mutable 세그먼트 | **645 docs** | 비움 | **2 docs** |
| 큰 immutable | 14,940 (13 MB) + 1,000×3 | `Segment Count: 4` | **4,565 / 4,585 / 4,870 / 4,565** (각 ~4 MB) |
| BM25 쿼리 `Buffers` | **shared hit=933** | **shared hit=185** | (미측정) |

런북의 조치는 **`ALTER SYSTEM SET paradedb.global_mutable_segment_rows = 50; SELECT pg_reload_conf();`** —
**재배포도 재시작도 필요 없는 런타임 변경**이라 우리 배포 이력에 흔적이 안 남는다. 이것이
R·S(13,500 blks/req)와 T(2,120)를 가르는 유일한 후보다.

**GUC 실측 (08-19).**

```
name                                  | setting | source             | sourcefile                | line
paradedb.global_mutable_segment_rows  | 1       | configuration file | postgresql.auto.conf      | 3
```

```
$ docker exec postgres ls -l /var/lib/postgresql/data/postgresql.auto.conf
-rw------- 1 postgres postgres 176 Aug 15 13:47 ...

$ docker exec postgres cat /var/lib/postgresql/data/postgresql.auto.conf
paradedb.global_mutable_segment_rows  = '1'
paradedb.global_mutuable_segment_rows = '50'      ← 오타 이름. placeholder라 무효
```

#### ⚠️ 정정 — "설정 변경이 원인"은 **기각**이다

이 문서의 앞선 판(08-19 오전)은 `global_mutable_segment_rows = 1`을 R·S와 T를 가른 변수로
**확정이라고 적었다. 틀렸다.** `postgresql.auto.conf`의 mtime이 **08-15 13:47**로
**R(08-17)·S(08-18)보다 앞선다.** 즉 R·S도 이미 `= 1` 상태에서 돌았고, 그런데도
13,500 blks/req를 냈다. **설정값 자체는 차이를 만들지 않았다.**

> 이 오판은 "현재 상태가 런북의 목표 형태와 같다"에서 "그러니 최근에 적용됐다"로 건너뛴 것이다.
> **상태를 보고 변경 시각을 추론하면 안 된다** — 시각은 시각으로 확인해야 한다(그래서 mtime을 떴고,
> 그 결과가 가설을 뒤집었다).

또 하나: 오타 이름(`mutuable`)에도 `ALTER SYSTEM`이 실행된 흔적이 파일에 남아 있다. Postgres는
확장 네임스페이스의 미정의 이름을 **placeholder로 받아 저장까지 한다** — `SHOW`로 조회하면 50이
나오지만 아무 일도 하지 않는다(`pg_settings` 18행에 없다). 세 번째 철자(`mutual`)는
`unrecognized configuration parameter` 에러다 — **placeholder는 한 번이라도 SET된 이름에만 생긴다.**
**GUC 적용 판정은 `SHOW`가 아니라 `pg_settings`의 `source`/`sourcefile`로 해야 한다.**

#### 새 가설 — 값이 아니라 **세그먼트 누적/병합 주기**다

`= 1`은 행마다 세그먼트를 끊으므로 **세그먼트가 계속 늘어난다.** 그리고
`paradedb.global_enable_background_merging = on`(기본값)이 이를 주기적으로 병합한다.
즉 이 설정 하에서 세그먼트 수는 **톱니처럼 오르내린다.**

| 시점 | 세그먼트 상태 | blks/req |
|---|---|---|
| 08-15 13:47 | `= 1` 적용. 런북 §0 기준선은 mutable 645 + 큰 것 14,940 + 1,000×3 | — |
| R (08-17) / S (08-18) | **기록 없음** — 매일 크롤링이 쌓여 tiny 세그먼트가 다수였을 것으로 추정 | **13,531 / 13,601** |
| T (08-19) | **23개** (큰 것 4×~4,600 + tiny 19). 균등한 4개는 **백그라운드 병합의 결과** | **2,120** |

큰 세그먼트가 `14,940 + 1,000×3` → `4,565 / 4,585 / 4,870 / 4,565`로 **균등하게 재편된 것**이
병합이 실제로 돌았다는 증거다. R·S 시점에 tiny 세그먼트가 다수 쌓여 있었다면 스캔이 그만큼
비쌌고, 병합 후인 T에서 싸진 것이 된다.

**이 가설은 확인도 반증도 되지 않았다** — R·S 시점의 `index_info` 기록이 없기 때문이다.
그리고 **가설이 맞다면 성능은 앞으로도 톱니처럼 오르내린다** — T의 24.6 RPS는 "병합 직후"의
값이고, tiny 세그먼트가 다시 쌓이면 내려간다. 런북 자신의 「다음」이
*"세그먼트 수 모니터링 상시화 — 수십 개로 늘면 `mutable_segment_rows`를 올릴 것"*이라고
적어둔 것이 정확히 이 위험이다.

> **⚠️ 2026-08-19 추가 — 비용 모델을 정정한다.** `docs/operations/BM25_MUTABLE_SEGMENT_RUNBOOK.md`의
> 프로덕션 실측(08-15)에 따르면 지배 변수는 세그먼트 **개수**가 아니라 **mutable 세그먼트의 행 수**다.
> mutable 세그먼트는 term dictionary가 없어 **매 쿼리마다 전 문서를 선형 스캔**한다 —
> immutable 17,940 docs가 1.5ms인데 mutable 645 docs가 **148.2ms**(문서당 2,900배)로,
> 전체 3.5% 문서가 쿼리 시간의 99%를 먹는다. 런북은 이 주기적 재발을 **톱니파**로 명명했다.
>
> 이 모델이면 R·S → T·U도 설명된다: `global_mutable_segment_rows = 1`에서 대량 rebuild
> (`ArticleTermService:399`)가 지나가면 **행마다 세그먼트가 생겨 수천 개**가 되고(런북이 정확히
> 이 위험을 경고했다), 이후 백그라운드 병합이 **균등한 4개로 재편**한다 — 08-19에 관측한
> `4,565 / 4,585 / 4,870 / 4,565`가 그 모양이다. **여전히 확정은 아니다**(그 시점 기록 부재).

**닫는 방법**: `paradedb.index_info`를 **주기적으로 기록**하고 사다리 실행과 겹쳐 본다.
세그먼트 수와 blks/req가 함께 움직이면 확정된다. 단발 실행으로는 영원히 못 가른다.
→ **2026-08-19 구현됨** — `Bm25SegmentMetricsScheduler`(5분 간격)가 게이지를 올리고
`collect-results.py`가 레벨별 `segs`/`mut` 열로 찍는다. 배포 후부터 시계열이 쌓인다.

### A. `ALTER SYSTEM` 적용 시각 (7.4의 마지막 고리)

DB 호스트(운영 Postgres 서버)에서. **postgres가 컨테이너로 돌아 호스트 경로엔 파일이 없다** —
`ls -l $PGDATA/...`는 실패한다. 컨테이너 안에서 봐야 한다.

```bash
docker ps --filter name=postgres --format '{{.Names}}'
docker exec postgres ls -l /var/lib/postgresql/data/postgresql.auto.conf
docker exec postgres cat /var/lib/postgresql/data/postgresql.auto.conf
```

**✅ 실행됨 (08-19). 결과: `Aug 15 13:47` — S·T 사이가 아니라 R보다도 앞선다.**
따라서 설정값 가설은 **기각**됐고 7.4를 새 가설(세그먼트 누적/병합)로 다시 썼다.
파일에는 오타 이름(`global_mutuable_segment_rows = '50'`) 줄도 함께 남아 있었다 — placeholder라 무효다.

### B. 컨테이너별 피크 RSS (5.4 장부 확정 / 5.5가 요청한 계측)

앱 호스트. 런 T 구간은 **06:44:45~06:55:00 UTC**이고,
`/tmp/memstat.log`는 `HH:MM:SS <name> <used> / <limit>` 형식이라 첫 필드 문자열 비교로 자른다.

```bash
# 컨테이너별 피크 (MiB 정규화)
awk '$1>="06:44:00" && $1<="06:56:00" {
       v=$3; u=v; gsub(/[0-9.]/,"",u); gsub(/[^0-9.]/,"",v); v+=0;
       if(u=="GiB")v*=1024; else if(u=="KiB")v/=1024;
       if(v>m[$2])m[$2]=v
     } END{ for(c in m) printf "%-28s %8.1f MiB\n", c, m[c] }' /tmp/memstat.log | sort -k2 -nr

# 전체 합계의 피크 시각
awk '$1>="06:44:00" && $1<="06:56:00" {
       v=$3; u=v; gsub(/[0-9.]/,"",u); gsub(/[^0-9.]/,"",v); v+=0;
       if(u=="GiB")v*=1024; else if(u=="KiB")v/=1024; s[$1]+=v
     } END{ for(t in s) if(s[t]>mx){mx=s[t]; at=t}; printf "피크 합계 %.1f MiB @ %s\n", mx, at }' /tmp/memstat.log
```

이걸로 5.4의 추정 칸이 **부하 중 실측**으로 바뀐다 (5.7의 `docker stats`는 S 실행 1회 스냅샷이었다).

> **⚠️ 08-19 시도 결과: 매칭 0건.** 로그 마지막 줄이 `08:06:43`인데 그 줄의 limit 칸이 `1.861GiB`
> (= 호스트 RAM, 즉 `mem_limit` 없음)라 **08-18 기록**이다 — tempo가 `mem_limit: 400m`을 받은 건
> 08-18 09:30이다. 즉 **루프가 런 T 때 돌고 있지 않았다.** 재시도 전에 살아 있는지부터 확인할 것:
>
> ```bash
> pgrep -af "docker stats" ; ls -l /tmp/memstat.log
> awk '{print $1}' /tmp/memstat.log | sort -u | sed -n '1p;$p'   # 로그가 덮는 시각 범위
> ```
>
> **또한 이 측정은 부하 창만으로는 부족하다** — 7.2에서 드러났듯 Tempo 피크는 부하 종료 후
> 다음 블록 완성(최대 30분 뒤)에 온다. 루프를 **부하 종료 +40분까지** 돌릴 것.

수집이 끝나면 로그 루프를 정리한다:

```bash
pkill -f "docker stats"
```
