## 1. VU15 — 꺾임의 정체는 버퍼 풀 교체다

VU15에서 처리량이 14.33 → 10.19로 떨어지는데 **DB CPU는 오히려 78% → 84%로 올라간다.**
즉 DB가 더 열심히 일하면서 결과는 덜 나온다. 원인이 `blks/req`에 보인다:

| VU | RPS | blks/req | 요청당 MB |
|---|---|---|---|
| 5 | 12.85 | 14,107 | 110 |
| 10 | 14.33 | 13,531 | 106 |
| **15** | 10.19 | **19,915 (+47%)** | **156** |

**같은 쿼리인데 요청당 블록이 47% 늘었다.** 동시성이 오르면 각 요청의 워킹셋이 서로를 밀어내
같은 블록을 다시 읽는다 — 선행 문서 5.3의 "검색 한 번이 132MB를 256MB 버퍼 풀로 쓸어낸다"가
포화에서 실제로 증폭되는 모습이다. 요청당 비용이 부하에 따라 **커지는** 구조라
동시성을 올리는 것으로는 이 지점을 넘을 수 없다.

동시에 커넥션 압력도 붙는다 — 획득대기 0.050 → 0.117s, pending 6 → 16.

## 2. VU20 — 측정 불가 영역 (관측 스택 붕괴)

VU20 구간(11:29:35~11:32:35)에서 **DB·호스트 지표가 전부 비어 있다.** 수집 실패가 아니라
**앱 호스트의 관측 스택이 그 시각에 죽었기 때문**이다.

앱 호스트 메모리 타임라인 (2분 간격, 지표가 끊기는 지점이 사망 시각):

| 시각 | 레벨 | MemAvailable | swap-in |
|---|---|---|---|
| 11:18 | (시작 전) | 167MB | 189 pages/s |
| 11:20 | VU5 | 120MB | 978 |
| 11:22 | VU10 | 111MB | 2,541 |
| 11:24 | VU10 | **92MB** | 2,557 |
| 11:26 | VU15 | 124MB | 2,511 |
| 11:28 | VU15 | 172MB | 1,837 |
| 11:30 | VU20 | **(지표 끊김)** | 1,111 |

호스트 RAM 1,906MB에서 가용 92MB까지 내려갔고, VU20 진입과 함께
**Prometheus·Grafana·Loki·Tempo가 응답 불가**가 됐다. 부하 종료 후 20분이 지나도 회복되지 않아
(`/api/categories` 3~14초, Prometheus 000) **호스트 재부팅으로 복구**했다.
재부팅 후 Prometheus가 WAL을 재생하며 503을 거쳐 200으로 돌아왔고, **다행히 실행 데이터는 보존됐다** —
이 문서의 수치는 재부팅 이후 재수집한 것이다.

VU20의 5xx 48건은 정직한 풀 포화다:
`HikariPool-1 ... timed out after 3165ms (total=5, active=5, idle=0, waiting=16)` —
타임아웃이 설정값(3,000ms)대로 찍혔다. VU20은 요청당 커넥션 2개가 필요한 구조에서
동시 20 요청 = 수요 40 대 공급 5이므로 붕괴가 당연하다.

> **직전 실행(Q)의 8.4초 타임아웃과 다르다.** Q에서는 4.15초 GC 정지 때문에 스레드가 늦게 깨어나
> 3초 설정이 8.4초로 관측됐다(선행 문서 「다음」 항목). VU20에서는 설정값대로 3.1초라,
> 이 구간의 지배 요인은 GC가 아니라 **순수한 풀 초과 수요**다.

## 5. 앱 호스트 메모리 — 누가 차지했나

2장의 관측 스택 붕괴와 「다음」의 1순위를 정산하려고, 실행 시각의 Prometheus 데이터를 **사후 조회**해
앱 호스트 메모리를 분해했다(재부팅 전 데이터가 보존된 덕에 가능했다).
**결론: 1순위는 관측 스택이 아니라 백엔드 JVM의 커밋 힙이고, 2순위인 Prometheus는
k6 remote-write의 URL 카디널리티가 원인이다.**

### 5.1 총수요는 RAM의 1.6배였다

11:24 UTC(VU10 말~VU15 초, 압박 최대) 실측:

| 항목 | 값 |
|---|---|
| MemTotal | 1,906 MiB |
| AnonPages (프로세스 상주) | **1,474 MiB** |
| Swap used (2,048 중) | **1,530 MiB** |
| Cached / Slab / PageTables | 117 / 98 / 18 MiB |
| MemAvailable | 92 MiB |

**익명 메모리 총수요 = 1,474 + 1,530 ≈ 3,004 MiB = RAM의 1.6배.** 페이지캐시는 117MB까지
쪼그라들어 있었다 — 1장의 DB 쪽 `blks/req` 증가와는 **별개의 축**으로, 앱 호스트에는 캐시가
남아 있지 않았다.

### 5.2 1순위 — 백엔드 JVM: used 337MB가 아니라 **committed 984MB**

「다음」에 적었던 "힙 276MB/1,024MB로 여유가 있다"는 **used 기준의 오독**이다.
호스트가 물리 메모리 비용을 치르는 건 committed다. 11:24 실측:

| 영역 | committed | used |
|---|---|---|
| G1 Old Gen | 841 MiB | 258 MiB |
| G1 Eden | 81 MiB | 63 MiB |
| G1 Survivor | 16 MiB | 15 MiB |
| **heap 합** | **984 MiB** | 337 MiB |
| Metaspace | 158 MiB | 155 MiB |
| CodeHeap + Compressed Class | 87 MiB | 68 MiB |
| **nonheap 합** | **244 MiB** | 206 MiB |
| direct buffer | 27 MiB | — |

- JVM 커밋 총합 ≈ **1,255 MiB**, 스레드 스택·GC·JIT 네이티브까지 더하면 **약 1.3 GB = 호스트 RAM의 68%**
- `-Xms512m -Xmx1024m`(`Dockerfile:16`)에서 G1이 부하 중 상한까지 확장했고, 확장분은 쓰지 않아도
  즉시 반납되지 않아 그대로 스왑 대상이 된다
- 대조군: **같은 blue의 idle 커밋 힙은 542 MiB**(08-18 측정). 부하 때만 +440MB가 붙는 구조다

### 5.3 2순위 — Prometheus: k6가 검색 키워드를 라벨에 실어 보냈다

11:24 기준 **활성 시계열 158,716개**의 출처:

| 출처 | 시계열 수 |
|---|---|
| job 라벨 없음 = **k6 remote-write** | **151,911 (96%)** |
| postgres_exporter | 3,324 |
| backend | 2,470 |
| node-exporter ×2 (앱·DB) | 1,011 |

원인은 k6 태그다. 실제 시계열 라벨을 뽑으면 `name`/`url`이 **쿼리스트링까지 포함한 전체 URL**이다:

```
name = "https://newcodes.net/api/search/articles/loadtest?keyword=opentelemetry%20코루틴&page=1&size=10"
url  = (같은 값)
```

시나리오가 `tags: { endpoint: 'search', level }`만 주고 `name`을 덮어쓰지 않으며
(`scenarios/ramp-limit-finder.js:97`), `systemTags`로 `url`을 끄지도 않아 k6 기본값이 그대로 라벨이 된다.
키워드가 요청마다 다르니 **키워드 수 = 카디널리티**가 된다:

- `k6_http_req_duration_p95` 한 메트릭에 **3,452 시계열** (= 유니크 URL 수)
- k6 메트릭 이름 **56개** (`K6_PROMETHEUS_RW_TREND_STATS`의 통계 6종 × trend 8종 + 카운터/게이지)
- → **실행 1회당 15만~19만 시계열**. 게다가 `testid`가 매번 달라 실행끼리 절대 합쳐지지 않는다
- 최근 1시간(Q 10:38 + R 11:18) 창으로 세면 그 한 메트릭만 **11,755 시계열** →
  head 전체로는 **약 65만 시계열** 규모다 (stale 시계열도 2시간 블록이 잘릴 때까지 head에 남는다)

Prometheus 2.37의 head 시계열당 통상 3~4 KiB로 잡으면 **head+WAL만 대략 1~2 GB**다.
VU20에서 관측 스택이 통째로 죽고 재부팅 후 Prometheus가 큰 WAL을 재생하며 503을 거친 것과 맞는다.
같은 시각 **백엔드는 설정값대로 3.1초 Hikari 타임아웃을 정직하게 냈다**(2장) — 먼저 무너진 쪽은
백엔드가 아니라 Prometheus다.

누적 증거도 있다. 익명 총수요(anon + swap used)는 10:00 2,262 MiB → 11:20 2,525 MiB로 **+263 MiB**
늘었는데, 이 구간의 배포(green→blue 교체, 10:32)로 설명되는 몫은 +120 MiB뿐이다. 나머지는 Q 실행이
남긴 시계열이 head에 계속 머문 몫으로 본다.

### 5.4 메모리 장부 (11:24)

| 프로세스 | MiB | 근거 |
|---|---|---|
| **backend-blue JVM** | **~1,300** | **실측** (committed heap+nonheap+direct) |
| **Prometheus** | ~700–1,200 | **추정** — 시계열 수는 실측, 바이트/시계열은 통상값 |
| Tempo + Loki + promtail + Grafana | ~300–450 | 추정. `management.tracing.sampling.probability=1.0`이라 전 요청이 트레이싱된다 |
| nginx, exporter 3종, dockerd, 그 외 | ~150–200 | exporter RSS만 실측 (각 12~15 MB) |
| **합** | **~2.4–3.1 GB** | 실측 총수요 3.0 GB와 정합 |

### 5.5 이 분해의 한계와 확정 방법

**앱 호스트에는 cAdvisor도 process-exporter도 없어 컨테이너별 RSS가 Prometheus에 남지 않는다.**
위 표에서 JVM과 exporter만 실측이고, Prometheus·Tempo·Loki·Grafana는 추정이다. 확정하려면
운영 셸에서 아래를 남겨야 한다:

```bash
# 현재 상태(idle 기준선)
docker stats --no-stream --format "table {{.Name}}\t{{.MemUsage}}\t{{.MemPerc}}"
smem -k -s swap -r | head -20        # 스왑까지 포함한 프로세스별 점유 (apt install smem)

# 다음 사다리 실행 때 같이 띄워둘 것 — 추정 칸이 실측으로 바뀐다
while true; do docker stats --no-stream --format '{{.Name}} {{.MemUsage}}' \
  | sed "s/^/$(date -u +%H:%M:%S) /" >> /tmp/memstat.log; sleep 10; done &
```

### 5.6 조치와 예상 절감

절감 추정의 전제: Prometheus 몫을 총수요에서 역산하면
`3,004 − JVM 1,300 − (Tempo·Loki·Grafana·nginx·시스템 450~650) ≈ **1,050~1,250 MiB**`이고,
이를 head 시계열 35만~65만으로 나누면 **시계열당 2~3 KiB** — Prometheus 2.x의 통상값과 맞는다.
아래 절감액은 이 역산에 기댄 추정이며, 5.5의 `docker stats` 측정으로 확정해야 한다.

| # | 조치 | 예상 절감 | 방법론 영향 |
|---|---|---|---|
| **1** | k6 `name`/`url` 라벨 제거 (`--system-tags`) | **700~1,100 MiB** (실행당 시계열 19만 → 500 미만, **−99.7%**) | ⚠️ p50/p95 산출식 교체 필요 (아래) |
| **1′** | `K6_PROMETHEUS_RW_TREND_STATS`를 `p(50),p(95),p(99)`로 축소 | ~350~500 MiB (메트릭 이름 56 → 32, −43%) | **없음** — `avg/min/max`는 소비자가 없다. `p(99)`는 대시보드 패널이 쓰므로 남긴다 |
| 2 | `-Xmx1024m` → `512m` | ~440 MiB (부하 중 커밋 힙 984 → ~540) | 없음. used 최대 337MB라 여유 있다 |
| 3 | 컨테이너 `mem_limit` 부여 | (절감 아님) 호스트 전체 스래싱 대신 컨테이너 1개 OOM-kill로 국한하는 안전장치 | 없음 |
| 4 | `TRACING_SAMPLING=1.0 → 0.1` | ~~수십~150 MiB~~ → **5.7 실측 결과 Tempo가 544 MiB로 2위. 우선순위 2위로 상향** | 트레이스 표본 1/10 |

**1번만 반영했을 때**: 총수요 3,004 → **약 1,950~2,300 MiB**(RAM 1,906 대비 1.6배 → **1.0~1.2배**).
스왑 사용은 1,530MB → 200~400MB, swap-in은 2,500 pages/s → 수백 대로 떨어져
**관측 스택이 VU20을 넘길 가능성이 생긴다.** 다만 여유는 여전히 없다 —
**1번 + 2번을 같이 해야 총수요가 1,500~1,900 MiB로 RAM 안에 들어온다.**

**절감되지 않는 것**: 14.3 RPS 천장은 DB 제약이라 그대로다(1·4장). VU20의 5xx 48건도
수요 40 대 공급 5의 풀 문제라 그대로다. ingest 표본율도 원래 낮다(14 RPS × 56 메트릭 ≈ 800 samples/s) —
**이 조치의 절감은 CPU가 아니라 head 메모리와 인덱스다.** 부수 효과로 WAL이 작아져
재부팅 후 replay 시간(2장의 503 구간)도 함께 줄어든다.

> **⚠️ 1번의 숨은 의존성.** `collect-results.py:87`의 p50/p95는 **URL별 시계열을 요청 1건으로 간주해
> `quantile()`로 재구성**한다(코드 주석에 명시). `name`/`url`을 없애면 레벨당 시계열이 소수로 붕괴해
> 이 식이 무의미해진다 — 에러 없이 p50과 p95가 같은 값이 나오는, 가장 위험한 형태로 틀린다.
> **→ 2026-08-18 해결됨. 산출식 교체와 실측 캘리브레이션은 5.7 참고.**

### 5.8 Tempo 억제 (2026-08-18) — 544 MiB의 정체는 "필요량"이 아니라 GC 목표였다

5.7에서 Tempo가 실측 2위(544 MiB, 피크 RSS 625)로 드러났지만 **왜** 그만큼 쓰는지는 몰랐다.
`prometheus.yml`에 Tempo job이 없어 내부 지표가 남지 않았기 때문이다. Grafana 데이터소스 프록시로
`:3200/metrics`와 `/debug/pprof/heap`, `/status/config`를 직접 떠서 분해했다.

#### 실측 — 정상 상태 live heap은 85 MB뿐이다

| 지표 | 값 |
|---|---|
| `HeapAlloc` (GC 직후 live) | **85 MB** |
| `HeapInuse` / `HeapSys` | 95 MB / 818 MB |
| `HeapReleased` | 579 MB (이미 OS에 반납) |
| `NextGC` (다음 GC 목표) | 164 MB … **직전 관측 시점엔 738 MB** |
| `MaxRSS` (기동 후 피크) | **625 MiB** |
| `GCCPUFraction` | **0.0006 (0.06%)** |
| `go_goroutines` | 1,011 |
| 인제스터 live traces | **4개 / 6 KB** |
| 블록 수 / 누적 flush | 170 / 45개 (54 MB → 평균 **1.2 MB/블록**) |
| 22시간 누적 수신 | 326,755 spans / 257 MB |

**즉 Tempo는 544 MiB가 필요한 게 아니다.** 상주분의 대부분은 순간 버스트가 남긴 자국이다.

#### 원인 1 — GOGC=100 기본값이 버스트 기준으로 힙 목표를 2배로 잡는다

Go GC는 `GOMEMLIMIT`이 없으면 힙 목표를 **직전 live의 2배**로 잡는다. 블록 완성 중 live가 잠깐
370 MB까지 뛰면 목표가 738 MB가 되고, 그 사이 OS에서 받아온 페이지가 RSS로 눌러앉는다.
**GC CPU는 0.06%밖에 안 쓰고 있었다** — 메모리를 CPU로 바꿔 쓸 여유가 3자릿수 배로 남아 있었다.

#### 원인 2 — 힙 프로파일이 지목한 곳은 인제스터의 블록 완성 경로다

`inuse_space` 1위(41.4 MiB)와 `alloc_space` 1위(1,749 MiB)가 같은 스택이다:

```
parquet-go.newRowGroupRows ← FileRowGroup.Rows ← vparquet4.(*rowIterator).Next
  ← vparquet4.CreateBlock ← tempodb.CompleteBlockWithBackend ← ingester.(*instance).CompleteBlock
```

WAL 블록을 읽어 완성 블록으로 다시 쓰는 경로다. 뒤이어 `vparquet4.newRowPool`(1,007+288 MiB),
`BufferedWriter.Write`(494), `ZstdCodec.Encode`(321)까지 전부 같은 flush/compaction 축이다.
쿼리는 무관하다 — 기동 후 검색이 **6건**뿐이었다.

#### 원인 3 — 기본값이 이 호스트 규모와 3~100배 어긋나 있다 (`/status/config` 실측)

| 키 | 기본값 | 이 호스트의 현실 |
|---|---|---|
| `block.parquet_row_group_size_bytes` | **100 MB** | 실제 블록 평균 **1.2 MB** — 100배 과대 |
| `pool.max_workers` / `queue_depth` | **400 / 20,000** | 2 vCPU. goroutine 1,011개의 출처 |
| `search.read_buffer_count` × `size` | 32 × 1 MiB = **32 MiB/리더** | `max_workers`와 곱해진다 |
| `query_frontend.search.concurrent_jobs` | **1,000** | 블록당 잡 1개 → 170 블록 동시 조회 |
| `ingester.concurrent_flushes` | 4 | 완성 1건이 수십 MB |
| `global.max_bytes_per_trace` | 5 MB | 트레이스 1건이 힙을 밀 수 있다 |

> **부수 발견 — 아직 안 터진 폭탄이 하나 있다.** `pool.max_workers`(400) × `read_buffer_count`(32 MiB)는
> 상한이 없다. Grafana Explore에서 7일 범위 TraceQL 검색을 한 번 돌리면 이론상 수 GB를 잡는다.
> 지금까지 안 터진 건 검색이 6건뿐이었기 때문이다. RAM 1,906 MiB 호스트에서 이건 우연에 기댄 상태였다.

#### 조치 k — `TRACING_SAMPLING=0.1` 대신 유입 지점에서 끈다

「다음」에 적어둔 건 `TRACING_SAMPLING=0.1`이었지만, 측정해 보니 **그건 틀린 레버다.**

- 전역으로 0.1을 걸면 평시 트레이스가 **7분에 1건** 수준으로 떨어져 운영 관측성이 사실상 사라진다.

- 부작용: 억제된 요청도 MDC의 traceId는 남으므로 **Loki 로그의 traceId를 클릭하면 트레이스가 없다.**
  부하테스트 로그에 한정된다
- ⚠️ 이 변경은 `lib/`에 있어 **ECR 이미지 재빌드가 필요하다** (5.7의 조치 1과 달리 실행 레이어가 아니다).

**약 2,200 MiB**가 된다 — RAM 1,906은 여전히 넘으므로 **이 둘로도 스왑은 안 없어진다**.

**아직 검증 안 됨** — 배포(`./deploy.sh deploy`) 후 j의 스크레이프로 확인할 것:

```promql
rate(go_gc_duration_seconds_count{job="tempo"}[5m]) # GC 빈도 상승 폭 (CPU 대가)
```

`GOMEMLIMIT`이 너무 빡빡하면 Go는 OOM 대신 **GC를 계속 돌리며 CPU를 최대 50%까지 태운다**.
`GCCPUFraction`이 5%를 넘으면 상한을 400MiB로 완화할 것. 2 vCPU라 이건 실제 위험이다.

## 6. 한계

- **VU20 구간의 원인 분해가 불가능하다** — 그 시각 DB/호스트 지표가 없다. 풀 포화는 앱 로그로
  확인했지만, 호스트 메모리가 얼마나 기여했는지는 측정되지 않았다.
- R은 1회 실행이다. 다만 정점 값은 Q와 교차 확인됐다.
- 실행 전부터 스왑 압박(SwapFree 445MB)이 있었으므로 **VU5의 12.85 RPS는 Q의 VU5(10.92)와
  직접 비교하기 어렵다.** 레벨 순서도 다르다(첫 레벨 vs 세 번째 레벨).
- **5.4의 컨테이너별 배분은 추정이었고 5.7에서 `docker stats` 실측으로 갈아엎였다** — Prometheus는
  2배 이상 과대추정(700~1,200 → 73 MiB), 그 차액의 실체는 Tempo(544 MiB)였다.
- **5.8의 Tempo 조치는 아직 배포되지 않았다** — 설정 파일만 반영됐고 `process_resident_memory_bytes`
  실측 검증이 남아 있다. 예상 효과 300 MiB는 계산값이다.
- **조치를 다 해도 총수요는 RAM을 넘는다** (5.8 추정 ~2,200 MiB vs RAM 1,906). 관측 스택을 앱 호스트에
  동거시키는 구조 자체가 남은 문제다.
