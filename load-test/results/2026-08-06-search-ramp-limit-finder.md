## 결론

- **10~50 VUs 구간은 SLA 안전** — level_50까지도 5xx가 0.17%(28건)에 불과하고 p95도 임계치의 92% 수준.
- **처리량은 level_20(~96.5 req/s)에서 사실상 정점을 찍고 level_50에서는 오히려 소폭 하락(~92.0 req/s)** — 동시성을 20→50으로 올려도 처리량이 늘지 않고 지연시간만 증가(p95 444ms→997ms, p50 187ms→647ms)하는 전형적인 큐잉 포화 초입 패턴.
- **100 VUs에서 완전 붕괴** — p95 7.42s(임계치 대비 683%), p50 6.36s, 에러율 31.6%(926/2,930건 5xx). 처리량도 오히려 ~16.3 req/s로 급락(부하를 더 걸었는데 처리량이 떨어짐 — 전형적 congestion collapse). README의 가설(HikariCP pool(5) 포화 → 커넥션 대기 최대 3s → `statement_timeout` 5s → 5xx)과 정합적인 패턴.
- **SLA 기준 RPS는 약 90~97 req/s** (level_10~50 관측 처리량 범위, 정점은 level_20의 ~96.5 req/s). **한계선은 50~100 VUs 사이**에 있다 — level_50은 아직 SLA 안이지만 여유가 크지 않고(p95 92%), level_100은 완전 붕괴이므로 정확한 breakpoint를 좁히려면 60/70/80 VUs 구간 후속 테스트가 필요(미실행, RAG 선례와 동일한 한계).
- Loki 기반 BM25/Vector/Rerank(NSF) 단계별 소요시간 breakdown은 이번 실행에서 `/admin/monitor/` 프록시 타임아웃으로 조회하지 못함 — 후속 분석 시 재시도 필요(원인 진단을 위해서는 유용하지만 본 RPS 판정 자체에는 영향 없음).

### 2위 — (수정: 후속 조사 결과 별도 병목이 아니라 1위의 착시로 확인됨) ~~BM25/Vector 쿼리 자체의 실행시간 급증~~ → 정체는 "BM25:/Vector: 로그 타이머 안에 커넥션 대기시간이 포함되는 구조"

최초 결론(BM25/Vector 자체가 느려진다)은 **후속 검증(재현 실험 + 소스코드 확인)으로 반증됨**. 아래는 검증 과정과 정정된 결론.

#### 검증 1 — 재현 실험(`scenarios/pool-vu-check.js`, VUS=5 고정, 5분 sustained, testid `20260806-114632`)

풀 크기(5)와 정확히 같은 동시성으로 돌리면 이론상 풀 경합이 없어야 한다 — 이 상태에서도 BM25/Vector가 여전히 느리면 진짜 DB 실행 병목, 평소 수준으로 돌아오면 1위의 착시였다는 뜻.

| | VUS=5 (풀 경합 거의 없음) | level_10 (10 VUs) | level_100 (100 VUs) |
|---|---|---|---|
| `hikaricp_connections_pending` | **0~4** | 8~16 | 최대 167 |
| 앱 로그 "총"(BM25+Vector+Rerank) 평균 (n=29/25/13 표본) | **~1.9s** | ~2.68s | ~5.0s |
| 완료 요청 | 24,283건 | 14,426건 | 2,930건 |
| 에러 | **0건(0%)** | 0건 | 926건(31.6%) |

풀 경합이 없는 VU=5에서도 "총"이 평균 1.9초로 결코 빠르지 않지만(→ 별도의 baseline 비용, 아래 검증 2 참고), **pending이 0→8~16→167로 늘어나는 것과 정확히 같은 방향·비율로 "총"도 늘어난다** — 즉 부하가 늘수록 나빠지는 부분은 온전히 풀 대기시간과 상관관계를 보인다.

#### 검증 2 — 소스코드 확인 (`ArticleSearchService.computeHybridCore`, `SearchQueryEmbeddingService.getEmbeddingWithCacheInfo`)

- **`BM25: Xms` 타이머는 `TransactionTemplate.executeWithoutResult(...)` 호출 *전*부터 시작한다** — 즉 트랜잭션 시작(=HikariCP 커넥션 획득)이 타이머 안에 포함됨. BM25 자체는 async 아님, 호출 스레드에서 동기 실행.
- **`Vector: Yms` 타이머도 마찬가지** — `CompletableFuture.supplyAsync(..., searchExecutor)`의 람다 내부에서 타이머가 시작되고, 이 안에서 `SearchQueryEmbeddingService`(자체 트랜잭션/커넥션)와 `chunkRepository`의 2단계 벡터 쿼리(또 별도 트랜잭션/커넥션)를 순차 호출 — 둘 다 커넥션 획득 대기가 타이머에 포함됨.
- **`searchExecutor`는 병목이 아님** — `Executors.newVirtualThreadPerTaskExecutor()`(JDK 26 가상스레드, 무제한). 코드 주석에 이미 "실질 동시성 상한은 HikariCP 커넥션 풀에서 결정됨"이라고 명시돼 있음(`SearchExecutorConfig.java`) — 개발 시점에 이미 알려진 설계 의도.
- **가장 심각한 발견 — 임베딩 캐시 미스 시 외부 API 호출 동안 커넥션을 붙잡음**: `SearchQueryEmbeddingService.getEmbeddingWithCacheInfo`가 메서드 레벨 `@Transactional`인데, 캐시 미스 시 이 트랜잭션 *안에서* `embeddingApiService.generateEmbedding(...)`(Clova로 동기 blocking HTTP 호출, 타임아웃 오버라이드 없음)를 호출한다. 즉 **5개뿐인 커넥션 중 하나가 DB 작업과 무관한 외부 API 왕복 시간 동안 통째로 묶인다.**
- 요청 하나가 순차적으로 **최대 5~6개의 개별 커넥션**을 체크아웃한다(BM25 readOnlyTx, 임베딩 서비스 tx, 벡터 2단계 쿼리 tx, cross-scoring Phase B, Phase C, 최종 유효성 검사) — 동시성 카운트보다 실질 풀 압박이 훨씬 큼을 의미.
- HikariCP 설정 확인(`application-prod.properties`): `maximum-pool-size=5`, `minimum-idle=5`, **`connection-timeout=3000`**(로그의 "timed out after 3000ms"와 정확히 일치), `statement_timeout=5000`(connection-init-sql).

#### 정정된 결론

2위는 별개의 "DB 쿼리 자체가 느려지는" 병목이 아니라, **1위(HikariCP 풀 고갈)가 요청 하나당 최대 5~6번의 개별 커넥션 체크아웃 구조 + 로그 타이머가 커넥션 대기시간을 포함하는 구조 때문에 증폭되어 관측된 것**이다. 특히 임베딩 캐시 미스 시 외부 API 호출 동안 커넥션을 붙잡는 패턴은 3위(캐시 미스)와 1위를 직접 연결하는 가장 뾰족한 회귀 지점 — **롱테일 쿼리의 캐시 미스가 실제로는 "풀 고갈 증폭기" 역할**을 한다.

### 핵심 관찰

- **level_100에서 압도적 개선**: 3분 동안 완료된 요청이 2,930건 → 15,154건(5.2배)으로 늘었고, 5xx는 926건(31.6%) → 271건(1.8%)으로 급감. `HikariPool-1` 자체는 여전히 5개뿐이라 100 VUs를 감당하기엔 부족하지만(`hikaricp_connections_pending`이 오히려 143~194로 수정 전 최대 167과 비슷하거나 더 높음), **처리량이 5배 늘었다는 건 Little's Law 관점에서 커넥션 하나가 회전하는 속도(=대기 하나당 평균 대기시간)가 훨씬 빨라졌다는 뜻** — 이전엔 커넥션이 Clova 호출 동안 인질로 잡혀 회전율 자체가 낮았고, 지금은 각 체크아웃이 실제 DB 작업 시간만큼만 짧게 유지되다 반납된다.
- **앱 로그로 직접 확인**: 수정 후 level_100 샘플에서 `BM25: 277~2694ms`(대부분 1초 미만, 수정 전 1000~5000ms대에서 개선)로 확인됨. 다만 `Vector` 단계는 여전히 느림(2~5초대) — 특히 `embedding: hit(1437~2967ms)` 처럼 캐시 "히트"인데도 조회 자체가 1~3초 걸리는 사례가 다수 관측됨. **이건 예상된 잔여 병목**: 이번 수정은 "커넥션을 오래 붙잡는 안티패턴"만 제거했을 뿐, 풀 크기(5) 자체를 늘린 게 아니라서 100 VUs는 여전히 풀 대비 20배 과다 동시성 — 다만 각 체크아웃이 짧아져 전체 회전율이 좋아진 것.
- **level_100 안에서 시간이 지날수록 p95/p50이 스스로 하락**(p95 6.03s→3.25s, p50 5.35s→1.93s, 3분 구간 내) — 수정 전엔 레벨 내내 평평하게 고정(7.42s대)돼 있던 것과 대조적. 시스템이 부하에 적응/안정화되는 신호로 해석됨(수정 전엔 계속 악화되기만 했다면, 수정 후엔 초반 버스트 이후 회복).
- **level_50 이하는 이미 안전 구간이라 개선 폭이 상대적으로 작거나 노이즈에 가림** — 다만 level_50에서도 처리량 +42%·에러 0건 달성은 유의미. level_10/20의 미세한 "악화"처럼 보이는 수치는 §참고 항목에서 밝힌 `avg by (level)` 집계 방식의 노이즈로 판단(안전 구간에서 방향성 결론은 무의미).

### 결론

**수정은 명확히 효과가 있었다.** 특히 시스템이 완전히 붕괴하던 구간(level_100)에서 처리량 5.2배, 에러율 94% 감소라는 큰 개선을 실측으로 확인했다. 다만 **HikariCP 풀 크기(5)라는 근본 제약 자체는 그대로**라 100 VUs 수준의 극단적 동시성에서는 여전히 상당한 지연(p95 3~6초대)과 잔여 에러(1.8%)가 남아있다 — 이번 수정으로 "붕괴"는 막았지만 "완전한 SLA 준수"까지는 못 갔다. 풀 크기 자체를 늘리는 것(비용/DB 스펙과 트레이드오프)이 다음 후속 과제로 남는다.

## 10/15 회귀 원인 정밀 분석 — 2026-08-07 후속 조사

`pool=8`이 여전히 커넥션 풀 자체에 병목이 있다는 건 실제 트레이스(Tempo)로 확정했다(아래 "pool=8 잔여 병목 — 분산 트레이싱 증거" 참고). 그와 별개로 **왜 10/15는 8보다 더 나빠지는가**를 Postgres 내부 모니터링 지표까지 동원해 파고든 결과.

### pool=8 잔여 병목 — 분산 트레이싱(Tempo) 증거

이미 배포돼 있던 Tempo(`docker-compose.yml`, OpenTelemetry JDBC 계측)로 pool=8의 6,377ms짜리 실제 요청 트레이스를 span 단위로 열어봤다:

| 구간 | 소요 |
|---|---|
| 요청 시작 ~ 첫 SQL span 시작 | **6,307ms — SQL span 전무** |
| `SELECT article+corporation join` | 3.6ms |
| `SELECT like_log` | 21ms |
| `SELECT category` ×4 | 각 10~16ms |
| **실제 DB 쿼리 합계** | **~68ms (전체의 1.1%)** |

전체 6.38초 중 6.3초(98.9%)가 SQL span이 하나도 안 찍히는 구간이었다. 이 구간은 하이브리드 검색 코어(BM25+Vector)가 도는 구간인데, `io.opentelemetry.jdbc` 계측은 `Statement.execute()`만 span으로 잡고 `DataSource.getConnection()`(HikariCP 체크아웃 대기)은 계측 범위 밖이다. 같은 시간대 에러 로그(`SQLTransientConnectionException ... waiting=169~190`)와 `hikaricp_connections_pending`(138~190 지속)까지 겹쳐 보면, **이 "빈 구간"이 곧 커넥션 대기 그 자체**임이 확정된다. pool=8에서도 100 VUs 앞에서는 여전히 풀이 병목이라는 뜻 — "다음 병목"은 아직 관측된 바 없다.

### 10/15가 8보다 더 나빠지는 이유 — 원인은 DB CPU 포화(코어별로 봐야 보임)

최초 확인(양쪽 코어 평균 + `rate(...[1m])` 스무딩)에서는 "CPU가 노이즈만 있고 안 뚜렷하다"고 판단했으나, **이는 잘못된 결론**이었다. 코어별·`rate(...[30s])`로 재확인:

| | pool=8 | pool=10 (level_50 붕괴 구간) | pool=15 (53초 정체 구간) |
|---|---|---|---|
| DB CPU(코어별) | 간헐적 스파이크(96~99%)만, 짧게 | 55~96% 사이를 계속 오르내림 — 지속적으로 높음 | **두 코어 모두 98~99%가 75초 이상 지속** |

pool=15의 정체 구간(1786100385~1786100445 UTC epoch, level_50 요청이 안 빠지고 쌓이던 구간)에 정확히 두 코어 다 98~99%로 고정돼 있었다 — 요청이 쌓였다가 한꺼번에 터지는 패턴과 시간이 정확히 일치한다.

**배제한 원인들**(전부 지표로 직접 확인):
- **락 경합**: `pg_locks_count`(postgres_exporter 기본 수집 지표, 이번에 처음 조회) — `accessexclusivelock`/`exclusivelock`/`sharerowexclusivelock`/`shareupdateexclusivelock` 전부 문제 구간 내내 0. `pg_stat_activity`의 `wait_event_type=Lock`도 전혀 안 잡힘 → **테이블/로우 락 경합 아님, 확정**.
- **디스크 I/O**: `node_disk_io_time` 사용률 15~21%, 버퍼캐시 히트율 99%+(`pg_stat_database_blks_hit/read`) → 디스크 병목 아님.
- **CPU steal(하이퍼바이저 스로틀링)**: `rate(node_cpu_seconds_total{mode="steal"}[30s])`가 문제 구간 내내 0.06~0.07% 수준(사실상 0) → burstable 인스턴스 CPU 크레딧 소진 같은 가상화 레벨 문제 아님.

### 앱(Spring/JVM) 쪽 기여 — 부차적이지만 실재함

DB뿐 아니라 앱이 병목일 가능성도 확인. 앱이 도는 호스트도 **DB와 마찬가지로 vCPU 2개**(`system_cpu_count=2`, Micrometer)였다.

- `process_cpu_usage`(Micrometer): 문제 구간 내내 0~80%를 오르내림 — DB 코어처럼 98~99%로 깔끔하게 고정되진 않지만 상당히 높은 구간이 잦음.
- **`jvm_gc_pause_seconds`**: 평시 30초당 0.01~0.15초였다가, 위기 구간(level_100 진입 시점) 진입과 함께 **30초당 0.44~0.62초로 10~20배 급증**(그래도 절대 비중은 wall time의 ~2% 수준 — 그 자체로 초 단위 지연을 설명하진 못함). 타이밍이 `SQLTransientConnectionException` 폭증 시점과 거의 일치 — 예외(+스택트레이스) 생성이 GC에 부담을 주는 전형적 패턴으로 보임.
- `jvm_threads_live_threads`: 40~42로 완전히 안정 — `SearchExecutorConfig`가 가상 스레드(`Executors.newVirtualThreadPerTaskExecutor()`) 기반이라 스레드 폭증은 없음(설계 의도대로 동작 확인).

즉 **앱 CPU/GC 압박은 독립적인 원인이라기보다 DB 쪽 문제가 만든 예외 폭풍의 부산물**에 가깝고, 다만 그 자체로 상황을 살짝 더 악화시키는 되먹임 요소로 작용한다.

### 인과관계 정리

```
DB 2vCPU + BM25(ParadeDB/tantivy)·pgvector는 쿼리당 CPU 비용이 상당함
        ↓
동시 커넥션이 8→10→15로 늘수록, 진짜 동시에 CPU를 요구하는 백엔드 수도 늘어남
        ↓
2코어가 감당 못 하는 지점부터 커넥션 하나당 실제 쿼리 실행시간 자체가 늘어남
        ↓
HikariCP가 그 늘어난 실행시간만큼 커넥션을 더 오래 붙잡음 → 대기열이 더 빨리 참
        ↓
SQLTransientConnectionException 대량 발생 → 앱 JVM GC 압박 증가(부차적 악화)
        ↓
정체(요청이 큐에 쌓임) → DB가 순간적으로 여유 생기면 쌓인 요청이 한꺼번에 폭주 처리
```

**10/15 회귀의 근본 원인은 "DB 2코어가 감당하는 동시 CPU 작업량을 넘어서면서 커넥션 회전율 자체가 느려지고, 그게 다시 대기열을 눈덩이처럼 불리는 되먹임 구조"다.** 락도 디스크도 하이퍼바이저 스로틀링도 아니고, 순수하게 CPU 코어 수 대비 과도한 동시 쿼리 실행 요구가 원인 — HikariCP 사이징 공식(`cores×2+spindle`)이 경고하는 정확히 그 현상이 실측으로 재확인됐다.

### 해석 — 대부분 구간에서 큰 승리, 극단 구간(level_100)은 오히려 악화

**level 10/20/50(10~50 VUs, 오늘 확립한 "SLA 기준 RPS" 90~97 req/s 범위와 실질적으로 겹치는 구간)에서는 pool=5(안전 기본값)로도 이전 pool=8(그동안의 최적치)을 전 지표에서 능가**했다 — p95 최대 36% 개선, 처리량 최대 19% 향상. 즉 풀 크기를 굳이 늘리지 않고도 오늘 두 코드 변경만으로 이전 최적 구성보다 나은 결과를 얻었다.

**반면 level_100(100 VUs, 풀 대비 20배 과다 동시성 — 이미 모든 구성에서 파탄이었던 극단 구간)은 오히려 처리량이 84.2/118.0 → 42.9 req/s로 절반 가까이 떨어지고 에러율도 소폭 상승**했다. 같은 시간대 에러 로그를 보면:

```
SQLTransientConnectionException: HikariPool-1 - Connection is not available,
request timed out after 11404ms (total=5, active=5, idle=0, waiting=38)
```

`connectionTimeout=3000`인데 실제로는 11초 넘게 걸린 뒤에야 타임아웃 예외가 던져짐 — 설정값을 크게 초과. 이는 이 레벨에서 **앱 JVM 자체도 극심한 부하 상태**(이전 섹션에서 확인한 GC 압박·process_cpu_usage 상승과 일치)라 HikariCP의 타임아웃 감시 스레드조차 제때 못 도는 정황으로 보인다.

**유력한 메커니즘**: Phase B+C 병합은 요청당 체크아웃 *횟수*는 줄이지만, 그 대신 하나의 체크아웃이 더 오래(cross-scoring+NSF+유효성검사를 전부) 커넥션을 붙잡는다. 풀이 여유 있는 상황(10~50 VUs)에서는 순수하게 이득이지만, **20배 과다 동시성(level_100)처럼 이미 파탄난 상황에서는 "커넥션 하나를 더 오래 붙잡는" 것이 다른 대기자들 입장에서 순번이 더 늦게 도는 결과**로 이어져(공정성 저하), 이미 나쁜 상황을 더 나쁘게 만들 수 있다. `max_parallel_workers_per_gather=0`도 개별 쿼리가 여분 코어의 도움을 못 받게 되므로, 극단적으로 붐빌 때는 쿼리 하나하나가 조금 더 오래 걸려 같은 방향으로 작용했을 수 있다.

### 결론

- **오늘 두 변경은 실질적인 트래픽 범위(10~50 VUs, SLA 기준 RPS 구간)에서 명확한 순승** — 풀 크기를 8로 올리지 않고도 그 이상의 성능을 pool=5(안전값)로 달성.
- **level_100 같은 이미 파탄난 극단 과부하 구간은 오히려 소폭 악화** — 다만 이 구간은 개선 전에도 모든 구성에서 이미 SLA를 크게 위반하던 "완전 장애" 영역이라(p95 2~6초대), 실사용 트래픽에서 의미 있는 구간이라기보다는 이론적 한계 테스트에 가깝다. 그럼에도 "왜 나빠졌는지"는 위에서 설명한 커넥션 점유시간-공정성 트레이드오프로 잠정 설명되며, 정말 우려된다면 후속 조사(동시성 60~80 구간 세분화, 또는 Phase B/C를 다시 분리하되 대신 다른 방식으로 체크아웃을 줄이는 방법 모색) 가치 있음.
- **풀 크기(`DB_POOL_SIZE`)는 여전히 5(안전 기본값) 유지 권장** — 오늘 변경만으로 이미 이전 pool=8 수준을 넘어섰으므로, 풀을 더 키울 필요성 자체가 줄었다.

### 해석 — 두 변경의 효과가 구간마다 정반대로 지배적이다

**level_100(20배 과다 동시성)에서는 merge가 지배적 원인이다.** A(구코드, workers=2)=84.2 req/s와 C(신코드, workers=2)=37.0 req/s를 비교하면 — `workers`값은 둘 다 2로 동일하고 코드(merge 여부)만 다르다 — **merge 하나만으로 RPS가 84.2→37.0으로 절반 이하 폭락**한다. 반면 B(신코드, workers=0)=42.9 req/s와 C(신코드, workers=2)=37.0 req/s를 비교하면 — merge는 둘 다 적용된 채 workers만 다르다 — workers=0→2 전환의 순수 효과는 42.9→37.0으로 상대적으로 작다(약 14% 추가 악화). 즉 **level_100 악화의 주 원인은 Phase B/C 트랜잭션 병합이고, `max_parallel_workers_per_gather=0`은 오히려 그 피해를 살짝 완화하는 방향으로 작용했다** — 앞 섹션에서 세운 "체크아웃 점유시간-공정성 트레이드오프" 가설과 정합적이다(커넥션을 더 오래 쥐는 merge가 20배 과다 동시성에서는 대기자 공정성을 해치고, 반대로 workers=0은 쿼리 자체를 가볍게 만들어 그 피해를 부분적으로 상쇄).

**level_10/20(저~중 동시성)에서는 반대로 `max_parallel_workers_per_gather=2` 자체가 지배적 원인이다.** C(신코드, workers=2)는 level_10에서 52.7 req/s·p95 0.48~0.93s로, **merge가 적용돼 있음에도 불구하고 B(신코드, workers=0)의 96.3 req/s·245ms는 물론, merge조차 없던 A(구코드, workers=2)의 68.6 req/s·379ms보다도 나쁘다.** level_20은 더 뚜렷해서 C가 24.6 req/s로 세 구성 중 가장 낮고(A 81.2, B 120.0 대비), p95도 0.5~1.3s로 A(~600ms)보다 나쁘다. 즉 **10~50 VUs 구간에서 관찰됐던 "pool=5로도 이전 pool=8을 능가"하는 큰 승리는 사실상 거의 전부 `max_parallel_workers_per_gather=0` 덕분**이며, merge 자체는 이 구간에서 뚜렷한 추가 이득을 주지 못한다(오히려 workers=2와 결합하면 손해). `docs/operations/DB_LOAD_REDUCTION.md`에서 실측한 "BM25 쿼리 1건 = leader+worker 2개 = 프로세스 3개"가 2vCPU DB 호스트에서는 **동시 접속 10~20건 수준에서 이미 코어 수를 넘는 프로세스 경합을 유발**한다는 뜻으로, 병렬 워커 비활성화가 왜 이렇게 큰 효과를 냈는지에 대한 정합적인 설명이 된다.

**level_50만 예외적으로 C(124.2 req/s)가 A(131.1 req/s)와 비슷하고 B(158.7 req/s)보다는 낮다** — merge+workers=2가 A 수준을 회복한 유일한 구간. 다만 level_20(24.6 req/s)이 level_10(52.7 req/s)보다도 낮게 나온 것과 함께 보면 이 구간 데이터는 단조롭지 않은 잡음이 섞여 있다(§참고). 단발성 실행(재시도 없이 1회)이라 개별 레벨 수치의 노이즈에 과도한 의미를 부여하지 않는 것이 안전하다 — 다만 level_100의 A vs C, B vs C 비교(84.2 vs 37.0 vs 42.9)처럼 격차가 크고 방향이 뚜렷한 결과는 노이즈로 설명하기 어렵다.

### 결론

- **level_100 회귀의 주 원인은 Phase B/C 트랜잭션 병합**이다 (workers 고정 비교에서 84.2→37.0 req/s 폭락, workers만 바꾼 비교에서는 42.9→37.0으로 상대적으로 작은 변화). `max_parallel_workers_per_gather=0`은 죄가 없고, 오히려 그 구간에서도 소폭 완화 효과가 있었다.
- **level_10~50 구간의 큰 승리는 거의 전부 `max_parallel_workers_per_gather=0` 덕분**이다 (merge만 있고 workers=2로 되돌리면 이 구간 이득이 대부분 사라지거나 역전된다). 이 값은 **되돌릴 이유가 없다** — 정상 트래픽 범위(10~50 VUs)에서 순수 이득, 극단 구간(level_100)에서도 손해가 아니라 오히려 소폭 이득.
- **Phase B/C 병합은 재고할 가치가 있다** — 정상 트래픽 범위(10~50 VUs)에서 뚜렷한 추가 이득이 확인되지 않았고(그 구간의 이득은 workers=0의 몫), 극단 과부하(level_100) 악화의 주범으로 지목됐다. 다만 level_100 자체가 모든 구성에서 이미 SLA를 683%~ 초과하는 "완전 장애" 영역이라는 점(§결론), 그리고 merge가 요청당 DB 커넥션 체크아웃을 실제로 줄인다는 점(연결 수 절약이라는 별개 목표엔 여전히 유효)은 남아 있다 — **당장 되돌리기보다는, 다음 셋 중 하나를 후속 과제로 검토**: (1) merge를 유지하되 level_100 같은 극단 과부하에서만 완화되는 다른 장치(예: 커넥션 획득 큐에 fairness 보장, 혹은 timeout을 짧게 잡아 실패를 빠르게 반환) 모색, (2) merge를 되돌려 원래 3-트랜잭션 구조로 복귀(체크아웃 수는 늘지만 개별 점유시간은 짧아짐), (3) 애초에 level_100(20배 과다 동시성)이 실사용 트래픽 범위 밖이므로 현행 유지하고 우선순위를 낮춤.
- **운영 설정 변경 없음** — 이번 실험은 `DB_MAX_PARALLEL_WORKERS`를 임시로 2로 올렸다가 실험 종료 후 즉시 0(최적값)으로 원복했다. 현재 운영값은 앞 섹션과 동일(`DB_POOL_SIZE` 미지정=5, `DB_MAX_PARALLEL_WORKERS` 미지정=0).

### 참고

- level_20의 낮은 처리량(24.6 req/s, level_10보다도 낮음)은 단조롭지 않은 패턴이라 단일 실행의 잡음일 가능성을 배제할 수 없다 — 다만 방향성(workers=2가 workers=0보다 나쁨)은 level_10과 일치한다.
- p95/p50가 근접한 값으로 나오는 구간(예: level_10 plateau 483ms)은 `avg by (level)` 집계 특유의 근사(§결론 기존 캐치업)에 더해, 이번엔 요청 수 자체가 적어(레벨당 최대 2만여 건, 쿼리별로 쪼개면 표본이 더 작음) 분포 추정이 거칠어진 영향도 있을 수 있다.
- level_10 구간 말미에 `level="10"` 태그로 12~22초짜리 이상치가 기록됐다(실제 시각으로는 level_100 구간과 겹침) — level_10 스케줄이 끝난 뒤에도 요청 하나가 응답을 못 받고 오래 걸리다 뒤늦게 완료되며 시작 시점의 태그(level=10)를 달고 집계된 것으로 추정된다. workers=2 구성에서 저동시성 구간에도 극단 tail-latency가 발생할 수 있다는 정황이며, 원인 규명은 후속 과제로 남긴다.

### 해석 — 앞 절의 "workers=0 단독 효과" 결론을 정정한다

앞 절(3점 비교, A/B/C만 있던 시점)에서는 "**level 10~50의 승리는 거의 전부 `max_parallel_workers_per_gather=0` 덕분**"이라고 결론 냈다. 이제 네 번째 점(D)이 채워지면서 이 결론은 **틀렸다는 게 드러났다** — D(구코드에 workers=0만 적용)는 세 레벨 모두에서 A(구코드+workers=2)보다 오히려 **더 나쁘다**(68.6→45.3, 81.2→16.5, 131.1→84.9). 즉 workers=0을 "단독으로" 적용하면 이득이 아니라 손해다.

행/열 각각의 "단독 효과"(다른 변인을 고정하고 하나만 바꿨을 때)를 레벨별로 계산하면:

| level | merge 단독 효과(workers=2 고정, A→C) | merge 단독 효과(workers=0 고정, D→B) | workers=0 단독 효과(구코드 고정, A→D) | workers=0 단독 효과(신코드 고정, C→B) |
|---|---|---|---|---|
| 10 | −15.9 | **+51.0** | −23.3 | **+43.6** |
| 20 | −56.6 | **+103.5** | −64.7 | **+95.4** |
| 50 | −6.9 | **+73.9** | −46.3 | **+34.5** |

**두 변경 모두 "단독으로는" 중간~저동시성 구간에서 오히려 해롭거나 미미하고, 반드시 "둘 다 함께" 적용해야만 큰 이득이 난다** — 전형적인 양의 상호작용(시너지) 패턴이다. 특히 level_20은 극명해서, merge만 하거나 workers=0만 해도 baseline(A=81.2)보다 나쁜 16.5~24.6까지 떨어지는데 **둘을 합치면 오히려 120.0으로 baseline의 1.5배**가 된다.

**메커니즘 가설**: merge는 요청당 커넥션 *체크아웃 횟수*를 줄이고, workers=0은 쿼리 1건당 *DB CPU 비용*을 줄인다. 이 둘은 서로 다른 자원(커넥션 풀 vs DB CPU)에 대한 압박을 각각 줄이는데, **한쪽만 줄이면 병목이 다른 쪽으로 옮겨갈 뿐 전체 처리량은 개선되지 않는다** — 오히려 한쪽 자원이 싸지면 그만큼 다른 쪽 자원에 대한 유효 요청률이 늘어나 그쪽 병목이 더 심해질 수 있다(예: workers=0으로 쿼리가 가벼워지면 초당 더 많은 쿼리가 커넥션 풀 앞에 도달해 구코드의 체크아웃 3회 구조를 더 강하게 압박). 두 자원 모두를 동시에 풀어야 실제로 병목이 해소된다.

#### 메커니즘 상세 — 커넥션 풀 총 점유량 = (체크아웃 횟수) × (한 번 머무는 시간)

이 프레임으로 두 변인이 왜 "따로는 손해, 같이는 이득"인지 설명할 수 있다.

**① `max_parallel_workers_per_gather=2`가 왜 커넥션을 더 오래 붙잡게 만드는가.** DB 호스트는 vCPU가 2개뿐인데, `docs/operations/DB_LOAD_REDUCTION.md`의 `EXPLAIN ANALYZE` 실측으로 BM25 쿼리 1건이 leader+worker 2개 = **프로세스 3개**를 띄운다는 게 확인돼 있다. 쿼리가 단독으로 돈다면 2코어가 일을 나눠 처리하니 workers=2가 오히려 빠르다. 하지만 **동시에 N건의 쿼리가 몰리면 필요한 프로세스 수는 3×N인데 코어는 2개뿐**이라, OS가 프로세스들을 쪼개 번갈아 돌려야 하고(컨텍스트 스위칭) 프로세스 하나당 실제로 받는 CPU 시간 조각이 줄어든다 — 그 결과 쿼리 하나가 실제로 끝나는 wall-clock 시간이 늘어난다. 커넥션은 그 쿼리가 끝날 때까지 붙잡혀 있는 것이므로, 쿼리 실행 시간이 늘어나면 커넥션 점유 시간도 그대로 늘어난다. workers=0이면 쿼리 1건당 프로세스가 1개만 필요해 동시 N건이 몰려도 오버서브스크립션이 workers=2의 3분의 1 수준이라 경합이 훨씬 덜하다.

**② 신코드(merge)+workers=2(C)가 왜 구코드+workers=2(A)보다도 더 나빠지는가.** merge는 체크아웃 *횟수*만 줄일 뿐, 각 단계(옛 Phase B: cross-scoring 보충, 옛 Phase C: 유효성 검사)가 걸리는 *시간* 자체는 줄이지 않는다 — Phase B의 보충 쿼리도 BM25/Vector 쿼리라 workers=2의 코어 경합을 그대로 받는다. 문제는 merge가 이 늘어진 B+C 구간을 **끊김 없이 이어서 한 커넥션에 계속 물려 놓는다는 것**이다. merge 이전에는 Phase B가 끝나고 커넥션을 반납하는 짧은 틈에 다른 대기 요청이 그 자리를 채갈 기회가 있었는데, merge로 그 틈이 사라진다. workers=2 때문에 B/C 각 구간이 이미 늘어져 있는 상태에서 그 둘을 안 끊고 이어 붙이면, 한 요청이 커넥션 하나를 훨씬 더 긴 시간 동안 독점하게 되고 그만큼 뒤에서 기다리는 다른 요청들의 대기 시간이 늘어난다 — merge의 이득(체크아웃 오버헤드 감소)은 원래 크지 않은데, merge의 손해(연속 점유로 인한 공정성 저하)는 workers=2가 개별 구간을 늘려놓은 만큼 증폭된다. 반대로 workers=0이면 B/C 각 구간이 원래 짧아 "이어붙여서 독점하는" 손해가 미미한 반면 체크아웃 횟수를 줄이는 이득은 상대적으로 두드러진다 — 그래서 merge는 workers=0과 짝지을 때만 순이익이 나고, workers=2와 짝지으면 baseline(A)보다도 나빠진다.

**level_100(20배 과다 동시성)은 이 패턴에서 벗어난다** — A(84.2)가 네 구성 중 가장 좋고, 나머지 셋(B 42.9, C 37.0, D 45.8)은 서로 비슷하게 나쁘다. merge 단독(A→C: −47.2)과 workers=0 단독(A→D: −38.4) 모두 큰 폭으로 해로운데, 그렇다고 병합해서(B) 더 나빠지지도 않는다(오히려 D보다 근소 우위). 이는 level_100이 "정상적인 처리량 개선/악화"가 아니라 **이미 완전히 붕괴한 상태에서 어느 쪽으로 건드려도 비슷하게 나쁜, 포화 구간(ceiling effect)**이라는 뜻으로 해석된다 — 이 구간에서는 개별 변인의 순효과보다 "이미 20배 과다 동시성"이라는 사실 자체가 지배적이다.

### 결론 (최종 — 앞 절의 잠정 결론을 대체)

- **level 10~50(정상~준정상 트래픽 범위)의 큰 개선은 merge와 `max_parallel_workers_per_gather=0`의 시너지 조합에서만 나온다.** 둘 중 하나만 적용하면 오히려 원래 baseline(A)보다 나빠질 수 있다 — 특히 workers=0만 단독 적용하는 것은 명확히 손해(level 10/20/50 전부 A보다 나쁨). **두 변경을 항상 함께 유지해야 한다** — 실제로 현재 운영 상태(병합 코드 + `DB_MAX_PARALLEL_WORKERS` 미지정=0)가 정확히 이 조합이므로 추가 조치는 불필요하다.
- **level_100은 어느 조합도 뚜렷한 승자가 없는 포화 구간**이다. A가 그나마 낫지만(84.2), 이는 이미 모든 구성이 SLA를 크게 위반하는 완전 장애 영역(§결론)이라 실사용 의미는 제한적이다. 앞 절에서 "merge가 level_100 악화의 주범"이라고 단정했던 것은 3점만으로 낸 성급한 결론이었다 — 실제로는 merge와 workers=0 둘 다 이 구간에서 독립적으로 해롭고, 어느 한쪽을 되돌린다고 A 수준을 회복하지는 못한다(D=45.8도 여전히 A=84.2에 크게 못 미침).
- **구코드+workers=0(D) 구성의 level_10 수치가 두 차례 실행에서 45.3 vs 96.2로 크게 벌어진 점**은 이 조합(체크아웃 3회 구조가 workers=0으로 쿼리 비용까지 싸진 상태)이 풀(5) 포화 임계점에 가깝게 붙어 있어, 작은 우연(캐시 상태, 이전 요청 잔여 부하 등)에도 결과가 크게 흔들리는 **본질적으로 불안정한 영역**임을 시사한다 — merge가 이 불안정성 자체를 줄여준다는 정황이기도 하다(B/C의 반복 측정들은 D보다 훨씬 일관적이었다).
- **운영 설정 변경 없음** — 두 차례 실험 모두 종료 직후 병합 버전(B와 동일 구성)으로 즉시 복원·재배포했다.
