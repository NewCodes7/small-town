## 원인 규명 — 퍼널은 DB 일을 줄였다. 그런데 커넥션을 더 오래 잡는다

### 1. DB는 일을 덜 했다 (퍼널 설계대로)

level_5 종료 시점 DB CPU 모드 분해:

| | total | user | **iowait** | system |
|---|---|---|---|---|
| W1 | 1.749 | 1.402 | **0.276** | 0.064 |
| W2 | 1.743 | 1.402 | **0.263** | 0.069 |
| **Z** | **1.619** | 1.443 | **0.129** | 0.042 |

**iowait이 정확히 절반으로 줄었다.** PGSS 문서가 예측한 그대로다 — cross-scoring의 TOAST
간접 참조(블록 접근의 64%, `toast_blks_read` 500만 = 물리 I/O)가 binary Stage 1로 우회됐다.
총 DB CPU도 −7.4%. **퍼널 자체는 의도한 대로 작동한다.**

### 2. 그런데 커넥션 점유 시간이 늘었다 — 이게 처리량을 결정했다

| level_5 | W1 | W2 | **Z** |
|---|---|---|---|
| 커넥션 점유(usage) | 0.458s | 0.419s | **0.567s (+29%)** |
| 획득 대기(acquire) | 0.345s | 0.303s | 0.382s (+18%) |
| 체크아웃/s | 10.93 | 10.97 | **8.39 (−23%)** |
| `pending` 최대 | 5 | 5 | **7** |
| 체크아웃/요청 | 4.08 | 3.97 | 4.15 (불변) |

**요청당 체크아웃 수는 그대로인데 한 번 잡는 시간이 29% 늘었다.**
풀이 5개뿐이므로 처리량 = 5 ÷ 점유시간에 직결된다 → 대기열이 자라고(`pending` 5→7),
3초 커넥션 타임아웃에 걸리는 요청이 3%→9.3%로 늘고, p95가 2배가 됐다.

### 3. 왜 자원을 덜 쓰는데 더 오래 잡나

퍼널 쿼리의 `stage1 AS MATERIALIZED`가 **배리어**다. Stage 1이 후보 100개 아티클의 전 청크
(~840개)를 훑어 집계·정렬·LIMIT 20을 **완전히 끝낸 뒤에야** Stage 2가 시작한다.
옛 단일 쿼리는 하나의 스캔으로 흘려보냈다. **총 작업량은 줄었지만 직렬 구간이 생겨
벽시계 시간이 늘었다** — 자원 예산이 아니라 커넥션 점유 시간이 이 시스템의 제약이다.

> PGSS 문서의 기대치(예산 33% → 8~9%, RPS 2.94 → 3.9)는 **DB CPU 예산**을 최적화 대상으로
> 삼았다. 실제 제약은 **점유시간 × 풀 크기(5)**였고, 두 지표가 이번에 반대로 움직였다.

| 2 | 유의어 N+1 | ⚠️ 체크아웃/요청이 4.08 → 4.15로 **불변**. 이 시나리오에선 효과 관측 안 됨 |
| 3 | Stage 1 후보 재활용 | ✅ **커버리지 0/100 = 기여 0**. mock 무상관 예측이 실측으로 확인됨 |
| 4 | `= ANY` + 로깅 | ⚠️ **부하테스트 구성에선 배제 맞음(아래).** 단 일반 트래픽에선 미판정 — SQL 텍스트를 고정시켜 generic plan 고착을 앞당기는 부수효과가 있다 (`QUERY_PARAM_REPARSE.md` 6장) |
| 5·6 | cross-scoring 퍼널 | ✅ **쿼리 단위로는 3.8배 개선(91.2 → 24.0ms) — 2026-08-12 실측으로 정정.** 처리량 −28%의 원인은 이 쿼리가 아니다 |

### #4가 원인이 아닌 이유 — 부하테스트 없이 코드로 갈린다

`VectorSearchService.computeSimilarityForSearchCrossScoring`은 첫 줄에서 분기한다:

```java
if (!crossScoringTwoStage) {
    return computeSimilarityForArticlesWithEmbedding(queryEmbedding, articleIds, threshold);
}
```

`0346ede`가 `= ANY`로 바꾼 건 **`computeSimilarityForArticleIds`(레거시 단일 쿼리)** 인데,
퍼널이 켜져 있으면 그 메서드는 **아예 호출되지 않는다.** 따라서 Z 구성에서 `= ANY` 변경은
핫패스에 없고, 점유시간 증가의 원인이 될 수 없다.

→ **퍼널 off 실행의 목적이 "#4 vs #5·6 분리"에서 "#1·#2·#3이 순중립인지 확인"으로 바뀐다.**
퍼널 off가 before 기준선(2.72 RPS)으로 복귀하면 나머지 3개는 순중립이고,
복귀하지 않으면 거기에도 회귀가 있다는 뜻이다.

그런데 **최적화 대상을 잘못 골랐다.** 이 시스템의 제약은 DB CPU 예산이 아니라
**커넥션 점유시간 × 풀 크기(5)** 였고, 두 지표가 반대로 움직였다.

### 선택지 평가

| 안 | 평가 |
|---|---|
| **`query_vec AS MATERIALIZED` (2026-08-12 적용 완료)** | **새 1순위.** 커넥션 점유시간을 우회하지 않고 직접 줄인다. cross-scoring 레거시 **91.2 → 5.3ms**, 퍼널 **24.0 → 3.6ms**. 본검색은 generic 미전환이라 중립. 결과 동등성 검증 완료라 **랭킹 리스크 0** |
| **`DB_POOL_SIZE` 상향 + 재측정** | ~~1순위~~ → 2순위. 제약을 직접 겨냥한다. 2026-08-07 실험이 풀 5 초과를 기각한 근거는 "DB CPU 포화"였는데, **퍼널이 그 전제를 바꿨다** — 지금 DB CPU는 2코어 중 1.19~1.62(60~81%)로 여유가 생겼다. `.env` 한 줄 |
| `stage2-limit` 하향 (20→10) | 3순위. 위 1순위를 적용하면 Stage 2가 이미 싸져 회수 여지가 줄고, 랭킹 리스크는 그대로 남는다 |
| `stage1 AS MATERIALIZED` 제거 | **효과 없다** — 단 이유가 다르다. ~~배리어가 설계에 내재해서~~가 아니라 **애초에 배리어가 문제가 아니었기 때문이다**(위 정정 참고). 옛 단일 쿼리도 동일하게 블로킹이다 |
| 퍼널 롤백 | **철회.** 퍼널은 쿼리 단위로 3.8배 빠르고 iowait 65% 절감도 실재한다. 롤백하면 두 이득을 다 버린다 |

### 왜 퍼널 off를 실행하지 못했나

이 실험은 운영 서버 `.env` 수정 + `./deploy.sh deploy`가 필요한데 devcontainer에서는
운영 서버에 접근할 수 없다(SSH 키 없음). 저장소의 `docker-compose.yml` 기본값
(`SEARCH_HYBRID_CROSS_SCORING_TWO_STAGE:-true`)을 뒤집어 push하면 같은 효과를 낼 수 있지만,
그건 **커밋된 운영 기본값을 바꾸는 것**이라 서버 측 `.env` 토글과 blast radius가 다르다 —
무인 상태에서 임의로 치환하지 않았다.

실행 방법은 `2026-08-12-PROD-COMMANDS.md` 부록에 있다. 한 줄 추가 후 재배포하면 된다.
