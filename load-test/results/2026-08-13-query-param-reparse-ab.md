### 계측 방법

- k6 지표는 Prometheus remote-write, 서버측은 Loki `[검색]` 로그와 `pg_stat_database` / node_exporter.

- 이번에 추가한 계측 2개:
  - `dbact/req` = `rate(pg_stat_database_active_time_seconds_total)` × 180 ÷ 완료건수

## 헤드라인

**요청당 비용은 전 레벨에서 내려갔다. 포화 레벨의 처리량 천장은 올라가지 않았다.**

`QUERY_PARAM_REPARSE.md`의 기계적 예측 두 가지가 **정확히** 맞았다:

1. **본검색(`findArticlesByTwoStageSearch`)은 중립** — generic plan 미전환이라 원래 영향이 없다.
2. **cross-scoring 구간만 싸진다** — 별도 로깅되는 모든 구간이 중립인데 총합만 줄었다.

반면 처리량은 level_5에서 개선되지 않았다. 선행 문서가 지목한 제약
(**커넥션 점유시간 × 풀 크기(5)**)이 그대로 남아 있다는 뜻이다.

## 2. 어느 구간이 줄었나 — 로그 구간별 분해 (중앙값, ms)

`[검색]` 로그는 BM25 / Vector(임베딩·query) / Rerank를 따로 찍는다. **셋 다 중립인데 총합만 줄었다.**

| 구간 | L1 before | L1 after | L2 before | L2 after |
|---|---|---|---|---|
| BM25 | 157 | 160 | 202 | 201 |
| Vector 합계 | 274 | 284 | 289 | 290 |
| ├ embedding (mock) | 145 | 145 | 145 | 145 |
| └ query (2단계 본검색) | 116 | 120 | — | — |
| **총** | **535.5** | **482** | **629** | **551** |
| **잔차** = 총 − max(BM25, Vector) | **261.5** | **198** | **340** | **261** |
| | | **−63.5 (−24%)** | | **−79 (−23%)** |

BM25와 Vector는 `CompletableFuture`로 병렬 실행되므로 총합에서 둘 중 큰 쪽을 뺀 **잔차**가
직렬 후속 구간(cross-scoring 보충 + 유효성 검증 + NSF)이다. 변경된 SQL은 이 구간에만 있고,
잔차가 두 레벨에서 일관되게 **−23~24%** 빠졌다.

> **잔차 계산의 한계**: 두 future가 정확히 동시에 시작하지 않으므로 `max()`는 근사다.
> 절대값이 아니라 before/after 차이의 방향·크기 근거로만 쓴다. 정밀한 항목별 귀속은
> cross-scoring 구간에 별도 타이머를 넣어야 가능하다(미적용).

**격리 SQL 예측치와의 대조**: 커밋은 퍼널 쿼리 24.0 → 3.6ms(**−20.4ms**)를 예측했다.
관측된 잔차 감소는 −63.5 / −79ms로 **예측보다 크다.** 잔차에는 변경되지 않은 쿼리도
섞여 있으므로 이 초과분을 전부 커밋에 귀속시킬 수는 없지만, 방향과 최소 규모는 확인됐다.

## 3. 처리량 — 과도구간을 걷어내야 보인다

### 3.1 겉보기 수치와 그 함정

level_5 전체 180초 기준 RPS를 늘어놓으면 after가 나빠 보인다:

| 구성 | 코드 | RPS (180s 전체) | degraded |
|---|---|---|---|
| W1 / W2 | `5cb2266` | 2.68 / 2.76 | ~14 / ~15 |
| Z / Z' | `2d66ea2` | 2.02 / 1.91 | 31 / — |
| **Z3** | `2d66ea2` | **2.06** | **30 (8.1%)** |
| **M** | `fe087b6` | **1.86** | **56 (16.8%)** |
| **M'** | `fe087b6` | **2.18** | **33 (8.4%)** |

**M' 실행으로 degraded 배증은 노이즈로 확정됐다** — 같은 코드로 33건(8.4%)이 나와
Z3(30건) · Z(31건) 수준으로 복귀했다. M의 56건이 이상치였다.

### 3.2 그런데 "노이즈"의 정체는 무작위가 아니었다 — level 전환 과도구간이다

degraded를 30초 버킷 시계열로 펼치면 **다섯 실행 전부 level_5 시작 직후에 버스트가 있다.**

| 실행 | level_5 시작부터 30초 버킷 | 총 degraded |
|---|---|---|
| Z (before) | **22** → 3 → 3 → 8 | 31 |
| Z3 (before) | **25** → 4 → 3 | 30 |
| M' (after) | 8 → 5 → **14** → 5 → 5 | 33 |
| **M (이상치)** | **15 → 27 → 10** (90초 지속) | 56 |

degraded의 70~90%가 **레벨 시작 30~90초 안에** 발생한다. 실행 간 차이는
"버스트가 30초 만에 가라앉느냐, 90초를 끄느냐"뿐이다. M은 후자였다.

### 3.3 왜 전환 시점에 무너지는가 — 요청당 커넥션 2개 × 풀 5

`ArticleSearchService.searchHybridCore`는 **요청 하나가 커넥션 2개를 동시에 잡는다**:

- Vector 검색을 `searchExecutor`(가상 스레드, 무제한)로 `supplyAsync` 제출 → 커넥션 1개
- 곧바로 호출 스레드에서 BM25를 `readOnlyTx`로 실행 → 커넥션 1개

`SearchExecutorConfig` 주석대로 **"실질 동시성 상한은 HikariCP 커넥션 풀에서 결정"** 되는데,
그 풀이 5다. 즉 **풀 5는 동시 요청 2.5개분**이다. VU가 2 → 5로 계단식으로 뛰면 5개 요청이
동시에 도착해 BM25 커넥션 5개를 다 잡고, Vector 브랜치들이 전부 굶어 3초 만에 타임아웃한다.

로그의 `(0개)`가 **항상 Vector 쪽에서만** 찍히는 것도 이 구조로 설명된다 — Vector 브랜치는
`catch (Exception e) { log.warn("Vector 검색 실패 (스킵)") }`로 예외를 삼키고 빈 결과를 반환하지만,
BM25 브랜치는 트랜잭션이라 실패하면 전파된다. **Vector가 편애당해 굶는 게 아니라, Vector 실패만
조용히 200으로 나가는 것이다.**

측정치가 구조와 맞는다: 요청당 체크아웃 **4.2회**, `active max` 항상 **5**(포화), `pending max` 8~15.

### 3.4 과도구간을 빼면 결론이 뒤집힌다

level_5의 **앞 60초를 버리고 뒤 120초만** 재면:

| 구성 | 전체 180s | 과도 60s | **정상 120s** | **정상 RPS** |
|---|---|---|---|---|
| Z (before) | 368 | 120 | 247 | 2.06 |
| Z' (before) | 341 | 101 | 242 | 2.02 |
| Z3 (before) | 371 | 108 | 262 | **2.19** |
| **M** (after) | 333 | 71 | 258 | **2.15** |
| **M'** (after) | 403 | 110 | 290 | **2.42** |

- before 3회: 2.02 / 2.06 / 2.19 (평균 **2.09**)
- after 2회: 2.15 / 2.42 (평균 **2.29**) → **+9.4%**

**M의 겉보기 −10% 회귀는 전부 과도구간이었다.** 정상상태만 보면 M(2.15)도 before 3회 중
2회보다 높다. 저부하 level 1·2에서 관측된 +5~9%와 방향·크기가 일치한다.

### 3.5 판정 프로토콜의 결함 (이번에 발견)

선행 문서는 level_5를 "가장 재현성 높은 판정 레벨"로 확정했는데, **그 3분 창에 전환 과도구간이
통째로 들어가 있었다.** 과도구간은 degraded의 70~90%를 만들고 RPS를 최대 ±10% 흔든다.

→ **앞으로 level별 판정은 앞 60초를 버린 정상상태 120초로 한다.**
   `ramp-limit-finder`의 레벨 간 드레인(30초)은 과도구간을 흡수하기에 부족하다.

| 주장 | 판정 |

| 지연 감소 | ✅ **확인.** 서버측 p50 세 레벨 모두 −10~21%, 2회 재현 |

**결론: 커밋은 의도한 대로 작동했고, 처리량까지 개선했다.**
요청당 DB CPU −13.7%, 서버측 지연 −10~21%, 정상상태 처리량 +9.4%.
메커니즘도 예측대로 확인됐다(본검색 중립, cross-scoring 구간만 감소, 블록 불변).

다만 **풀 5가 여전히 천장이다.** 요청당 커넥션 2개를 동시에 쓰는 구조라 풀 5는 동시 요청
2.5개분이고, 버스트가 오면 Vector 브랜치가 무더기로 3초 타임아웃한다.
DB CPU는 2코어 중 1.36~1.60(68~80%)까지 내려왔으니 풀을 늘릴 여유는 이전보다 커졌다.
