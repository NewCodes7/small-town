## 헤드라인

**요청당 비용은 전 레벨에서 내려갔다. 포화 레벨의 처리량 천장은 올라가지 않았다.**

`QUERY_PARAM_REPARSE.md`의 기계적 예측 두 가지가 **정확히** 맞았다:

(**커넥션 점유시간 × 풀 크기(5)**)이 그대로 남아 있다는 뜻이다.

## 2. 어느 구간이 줄었나 — 로그 구간별 분해 (중앙값, ms)

`[검색]` 로그는 BM25 / Vector(임베딩·query) / Rerank를 따로 찍는다. **셋 다 중립인데 총합만 줄었다.**

| 구간 | L1 before | L1 after | L2 before | L2 after |
|---|---|---|---|---|
| BM25 | 157 | 160 | 202 | 201 |
| Vector 합계 | 274 | 284 | 289 | 290 |
| ├ embedding (mock) | 145 | 145 | 145 | 145 |
| └ query (2단계 본검색) | 116 | 120 | — | — |
| **총** | **535.5** | **482** | **629** | **551** |
| **잔차** = 총 − max(BM25, Vector) | **261.5** | **198** | **340** | **261** |
| | | **−63.5 (−24%)** | | **−79 (−23%)** |

BM25와 Vector는 `CompletableFuture`로 병렬 실행되므로 총합에서 둘 중 큰 쪽을 뺀 **잔차**가
직렬 후속 구간(cross-scoring 보충 + 유효성 검증 + NSF)이다. 변경된 SQL은 이 구간에만 있고,
잔차가 두 레벨에서 일관되게 **−23~24%** 빠졌다.

> **잔차 계산의 한계**: 두 future가 정확히 동시에 시작하지 않으므로 `max()`는 근사다.
> 절대값이 아니라 before/after 차이의 방향·크기 근거로만 쓴다. 정밀한 항목별 귀속은
> cross-scoring 구간에 별도 타이머를 넣어야 가능하다(미적용).

**격리 SQL 예측치와의 대조**: 커밋은 퍼널 쿼리 24.0 → 3.6ms(**−20.4ms**)를 예측했다.
관측된 잔차 감소는 −63.5 / −79ms로 **예측보다 크다.** 잔차에는 변경되지 않은 쿼리도
섞여 있으므로 이 초과분을 전부 커밋에 귀속시킬 수는 없지만, 방향과 최소 규모는 확인됐다.

### level_5에서 중앙값은 내려갔는데 처리량도 내려간 이유

**closed model이라 `RPS = VU수 ÷ 평균응답시간`이고, 처리량을 정하는 건 중앙값이 아니라 평균이다.**

- before: 5 ÷ 2.434s = 2.05 (실측 2.06)
- after : 5 ÷ 2.720s = 1.84 (실측 1.86)

산수가 정확히 맞는다. 그리고 평균을 밀어올린 건 **p90이 2,784 → 5,566ms로 정확히 2배**가 된
꼬리다. 분포가 두 덩어리로 갈렸다 — **대부분은 빨라졌고, 일부는 3초 커넥션 타임아웃 벽에 몰렸다.**

degraded를 제외하고 실제로 벡터 단계까지 수행한 요청만 서버측 로그로 보면 개선이 더 뚜렷하다:

| level_5, degraded 제외 | before | after | 변화 |
|---|---|---|---|
| 서버측 `총:` 중앙값 | 1,649ms | **1,340ms** | **−18.7%** |
| 서버측 `총:` 평균 | 1,667ms | 1,604ms | −3.7% |
| degraded 비율 | 30/371 (8.1%) | 56/334 (**16.8%**) | 배증 |

**정상 처리된 요청은 18.7% 빨라졌다.** 처리량이 떨어진 건 순전히 degraded가 2배로 늘어
평균을 끌어올렸기 때문이다.

### degraded 배증의 원인은 미규명

커넥션 획득 대기가 0.432 → 0.523s(+21%)로 늘어 3초 벽에 몰린 요청이 늘었다.
**DB가 빨라졌는데 커넥션 획득이 더 오래 걸리는 이유는 이번 데이터로 설명되지 않는다.**
가능성 두 가지가 남아 있고 1회 실행으로는 못 가른다:

1. **노이즈** — degraded 비율은 실행마다 크게 흔들린다 (W1 14 · W2 15 · Z 31 · Z3 30 · M 56).
2. **실재하는 회귀** — 이 경우 원인 규명이 필요하다.

→ M 구성 1회 반복이면 갈린다. 반대로 **level 1·2는 두 실행 모두 degraded 0건**이라
그 구간의 −5%/−9% 개선은 이 불확실성과 무관하게 신뢰할 수 있다.

## 4. 판정

| 주장 | 판정 |
|---|---|
| 본검색은 중립 (generic 미전환) | ✅ **확인.** query 116 → 120ms |
| cross-scoring 구간만 싸진다 | ✅ **확인.** 별도 로깅 구간 전부 중립인데 잔차만 −23~24% |
| 재파싱은 블록을 안 건드린다 | ✅ **확인.** blks/req +3.3%(불변)인데 DB CPU −22% |
| 요청당 DB 비용 감소 | ✅ **확인.** core-s/req −13.7%, DB active/req −8.9%, 전 레벨 일관 |
| 지연 감소 | ✅ **확인.** 서버측 p50 −10~17%, 전 레벨 일관 |
| 랭킹 리스크 0 | — 이번 테스트 범위 밖 (mock 벡터라 원리적으로 측정 불가, 기존 부채) |
| **처리량 천장 상승** | ❌ **미확인.** level_5 1.86 vs before 밴드 1.91~2.06 |

**결론**: 커밋은 **의도한 일을 했다** — 요청당 DB CPU와 지연을 실제로 줄였고, 메커니즘까지
예측대로 확인됐다. 저부하(level 1·2)에서는 처리량도 +6~9% 올랐다.
그러나 **포화 지점의 처리량 제약을 푸는 변경은 아니었다.** 선행 문서의 진단
(제약은 DB CPU 예산이 아니라 커넥션 점유시간 × 풀 크기 5)이 이번 실측으로 재확인됐다.
DB CPU를 22% 더 비워줬지만 그 여유가 처리량으로 환전되지 않았다.

→ **다음 레버는 `DB_POOL_SIZE` 상향이다.** 선행 문서가 2순위로 내려둔 항목인데,
이번 결과가 1순위로 되돌린다. 근거가 더 강해졌다: DB CPU는 이제 2코어 중 1.36(68%)까지
내려왔고 iowait은 0.106으로 거의 없다. 풀을 늘릴 여유가 이전보다 커졌다.
