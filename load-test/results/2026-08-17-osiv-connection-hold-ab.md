|---|---|---|---|

## 1. 예측 대조 — 8개 항목 전부 적중

선행 문서가 세운 판정 기준(계획 단계에서 미리 못 박은 값)과 실측:

| 예측 | 실측 | |
|---|---|---|
| 요청당 체크아웃 2.93 → **5~6회 증가** | **5.9회** (VU2) | ✅ |
| 요청당 점유 430ms → **200ms 부근**(SQL 193ms) | **195ms** (VU2) | ✅ |
| 쿼리중 비율 40% → **80% 이상** | **82%** (VU2) | ✅ |
| VU2 RPS **거의 불변**(지연 바운드) | 5.72 → **5.75** | ✅ |
| VU5 Hikari 활성 커넥션 평균 4.58/5 → **크게 하락** | **3.25/5** | ✅ |
| VU5 획득대기 0.19~0.23s → **0에 근접** | **0.0008s** | ✅ |
| VU5 `search_query_embedding` 조회 120ms → **한 자릿수 ms** | **2ms** | ✅ |
| VU5 RPS → **VU2를 넘어섬** | 11.35 ≫ 5.75 | ✅ |

체크아웃 수가 **늘고** 점유가 **주는** 것이 가설의 서명이었고, 그대로 나왔다.
체크아웃 3회 → 6회는 "요청 스레드 트랜잭션 4개가 커넥션 1개를 공유하던 것"이
"각자 잡고 각자 반납하는 것"으로 바뀐 결과다.

## 2. 요청당 커넥션 회계 — 유휴 점유가 사라졌다

| 실행 | VU | 체크아웃/req | 점유/req | DB 실행/req | **쿼리중 비율** |
|---|---|---|---|---|---|
| N (before) | 1 | 3.05회 | 446ms | 168ms | 38% |
| N (before) | 2 | 2.93회 | 430ms | 172ms | 40% |
| N (before) | 5 | 3.14회 | 858ms | 192ms | 22% |
| N' (before) | 5 | 3.17회 | 1,016ms | 184ms | 18% |
| **P (after)** | 1 | 6.08회 | **201ms** | 153ms | **76%** |
| **P (after)** | 2 | 5.90회 | **195ms** | 160ms | **82%** |
| **P (after)** | 5 | 5.72회 | **269ms** | 188ms | **70%** |
| **P (after)** | 10 | 5.21회 | 516ms | 201ms | 39% |

점유/req가 **430 → 195ms**로 떨어져 Tempo 트레이스의 SQL 스팬 합계(193ms)에 거의 붙었다.
남은 차이는 커넥션 획득·반납 오버헤드 수준이고, **"일도 안 하면서 잡고 있던 시간"은 소멸했다.**

이것이 `ArticleSearchService`의 Phase A/B 트랜잭션 분리(`ad64c7a`)가 **처음으로 실제 효과를
내기 시작한 지점**이다. 그 커밋의 목적은 `vectorFuture.get()` 대기 290ms 동안 커넥션을 놓는
것이었는데, OSIV가 EntityManager를 요청 내내 열어두는 바람에 지금까지 무력화돼 있었다.

## 3. 병목 재판정 — 다시 DB CPU로 돌아왔다

| 실행 / VU | RPS | DB CPU | usr+sys | DB 실행중 세션 | 획득대기 | pending |
|---|---|---|---|---|---|---|
| N' VU1 | 2.62 | 23% | 9% | 0.44 | 0.000s | 0 |
| N' VU2 (정점) | 5.57 | 48% | 18% | 0.98 | 0.000s | 0 |
| N' VU5 | 5.14 | 45% | 18% | 0.93 | **0.233s** | 7 |
| N' VU10 | 2.34 | 10% | 5% | 0.20 | 2.061s | 16 |
| P VU1 | 2.76 | 22% | 9% | 0.43 | 0.000s | 0 |
| P VU2 | 5.62 | 46% | 18% | 0.92 | 0.000s | 0 |
| **P VU5 (정점)** | **11.02** | **70%** | **43%** | **2.13** | **0.001s** | 4 |
| P VU10 | 8.27 | 45% | 32% | 1.81 | 0.106s | 19 |

- **정점이 VU2 → VU5로 이동했고 값은 2배가 됐다.** 그 지점에서 획득대기는 0.001s로 사실상 없다.
- **DB 실행중 세션이 0.93 → 2.13으로 늘었다** — 풀이 막고 있던 병렬성이 실제로 DB에 전달됐다.
  같은 풀 5, 같은 쿼리인데 DB를 2배로 먹이고 있다.
- DB CPU가 45% → **70%**로 올라왔다. 이제 천장을 정하는 건 다시 **DB 2코어**다.
- VU10에서는 여전히 꺾이지만(11.35 → 8.81) 붕괴 폭이 훨씬 얕다(이전엔 5.57 → 2.63).
  VU10의 5xx 8건은 전부 풀 타임아웃이며, 로그를 보면 `active=4, idle=1, waiting=16` —
  **커넥션이 너무 빨리 반납돼 대기열이 길어도 풀이 꽉 차 있지도 않은** 상태다.

## 4. 판정

| 주장 | 판정 |
|---|---|
| OSIV가 트랜잭션 사이에 커넥션을 잡는다 | ✅ **로컬 프로브로 확정.** 대기 구간 활성 커넥션 = OSIV 적용 1 / 해제 0 |
| 유휴 점유 제거로 풀 실효 용량 2배 이상 | ✅ **확인.** 점유/req 430 → 195ms, 쿼리중 비율 40% → 82% |
| 포화 레벨 처리량 개선 | ✅ **확인.** level_5 5.30 → 11.35 (**+114%**), 정상상태 5.98 → 10.72 |
| DB 일의 양은 불변 | ✅ **확인.** blks/req 17.4k → 16.9k |
| VU2(지연 바운드)는 불변 | ✅ **확인.** 5.72 → 5.75 |
| 지연로딩 회귀 없음 | ✅ **확인.** 853개 테스트 통과, 부하테스트 20분간 `LazyInitializationException` 0건 |
| 병목이 풀에서 DB CPU로 이동 | ✅ **확인.** 정점에서 획득대기 0.001s / DB CPU 70% |

**결론: 커넥션 풀(5)은 원래 병목이 아니었다. 풀을 유휴로 채우던 OSIV가 병목이었다.**
`DB_POOL_SIZE`를 올리지 않고, 쿼리 하나 바꾸지 않고, 포화 처리량을 2배로 만들었다.

### 한계

- **1회 실행이다.** before는 2회(N/N', ±11%)라 밴드가 있지만 after는 1회다. 다만 +114%는
  그 밴드의 10배를 넘고, 8개 예측 지표가 모두 방향·크기까지 맞았다.
- `steady-state-rps.py`는 `increase()` 기반이라 호출마다 ±5% 흔들린다(같은 N/N'가
  6.59/5.26 ↔ 6.53/5.43). 위 표는 3개 실행을 한 번의 호출로 뽑은 값이다.
- **랭킹 정확도는 이번에도 범위 밖**(mock 벡터, 기존 부채).
- OSIV 해제 범위를 `/api/**`로 좁혔으므로 **Thymeleaf 경로의 유휴 점유는 그대로 남아 있다.**
  실사용자 페이지 트래픽이 커지면 같은 문제가 그쪽에서 재현될 수 있다.
