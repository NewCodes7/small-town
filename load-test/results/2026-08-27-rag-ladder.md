# RAG 채팅 용량 측정 — 2026-08-26~27

> 검색 ramp에서 얻은 방법론 교훈을 RAG에 이식하고, RAG의 현재 처리량과 무릎을 다시 잰다.
> 직전 RAG 측정은 `2026-08-05-rag-ramp-limit-finder.md` **단 1회**이고, 그 뒤 RAG가 공유하는
> retrieval 코드에 성능 커밋이 20건 넘게 들어가 코드 기준으로 이미 낡았다.

## 0. 시작 전에 고친 것 — RAG 부하테스트는 벡터 팔 없이 돌고 있었다

검색이 사다리 5회를 무효로 만든 것과 **같은 종류의 결함**이 RAG 경로에 그대로 남아 있었다
(`2026-08-17-search-ladder-5-10-15-20.md` 9장).

- mock Clova(`ClovaHandler`)는 SHA-256 시드 기반 **의사난수 단위벡터**를 반환한다 →
  실제 문서 임베딩과의 코사인 유사도가 N(0, 1/√1024) ≈ ±0.03에 몰린다
- `RagChatLoadTestController`는 운영 임계값 `THRESHOLD = 0.6`을 그대로 넘기고,
  `searchForRag`는 검색 경로와 달리 `vectorThresholdFor(useMockEmbedding)`를 **거치지 않았다**
- 결과: 벡터 팔이 **항상 0건** → NSF 병합이 BM25 단독으로 축퇴 → top-5가 전부 BM25에서 나옴

곁가지로, 임계값만 0.0으로 풀면 이번엔 벡터가 매번 `DEFAULT_MAX_RESULTS(100)`를 채워
cross-scoring 대상이 운영 대비 부푼다 — 검색이 커밋 `08afcc8b`로 이미 겪은 문제라
**임계값과 결과 수 상한(30)을 짝으로** 고쳤다. cross-scoring 보충도 같은 기준으로 정렬했다.

수정 커밋: `f4c2ea8d`. 실사용자 경로는 무변경(`useMockEmbedding=false` → 0.6/100 유지)이며
회귀 가드 테스트로 고정했다.

### 0.1 `[RAG검색]` 로그 신설 — 검색 9.7 교훈 2항의 빈칸

9.7 교훈 2항은 "단계별 로그를 먼저 봤어야 했다 — `(0개)`와 `embedding: miss(0ms)`는 처음부터
로그에 찍혀 있었다"였다. 확인해 보니 **RAG 경로엔 그 줄이 아예 없었다.** 검색은 로그가 있는데
안 본 것이고 RAG는 볼 것 자체가 없었다 — 즉 "벡터가 돌았는가"가 관측 불가능했다.

`getTopArticleIdsForRag`에 요약 로그를 신설하고, `searchForRag`가 임베딩·쿼리 계측을
`0, 0, false, 0`으로 버리던 것도 실제 값으로 채웠다(안 그러면 로그의 그 칸이 항상 0이라 무용지물).
프리픽스는 `[RAG검색]`으로 둬 Grafana의 `[검색]` Loki 파서와 섞이지 않게 했다.

## 1. 측정 방법 — 검색과 무엇을 다르게 했나

| 검색에서 배운 것 | RAG에 어떻게 적용했나 |
|---|---|
| 캐시 히트 경로만 때리면 코어가 0.5%만 돈다 | nonce가 RAG의 4개 앱 캐시를 전부 미스로 만드는 것을 코드로 확인. **단 BM25 팔은 예외** — 아래 1.2 |
| 5xx 0이어도 벡터가 꺼져 있을 수 있다 | 임계값 결함 수정 + `[RAG검색]` 로그로 실행마다 확인 |
| `run-task.sh`는 mock을 안 띄운다 | 전부 `run-prod-test.sh`로 실행 |
| 레벨 전환 과도구간을 버려야 한다(검색 60초) | RAG는 iteration이 21.4초라 **앞 120초** 제외 |
| 사다리는 병목이 바뀔 때마다 재조정 대상 | 2026-08-05의 5/10/20/40 폐기, 런 1 실측으로 재산정 (2.3) |
| 세그먼트와 짝짓지 않은 용량값은 재현 안 된다 | 모든 레벨에 `segs`/`mut` 병기 |
| 19시간 전 baseline은 like-for-like가 아니다 | SLA 분모를 같은 창의 레벨에서 잡음 (3장) |

### 1.1 RAG의 "RPS"는 검색의 RPS와 성격이 다르다

mock 기본값에서 요청 1건의 시간 구성:

| 구간 | 값 | 서버가 일하나 |
|---|---|---|
| 전처리 Converse | 2,075ms (median) | 대기만 (가상 스레드 파킹) |
| retrieval (임베딩 + BM25 + 벡터 + cross-scoring) | 300~560ms | **예** — DB 커넥션 2회 체크아웃 |
| TTFT | 1,650ms (median) | 대기만 |
| 토큰 스트리밍 410청크 × 51ms | ≈ 20,900ms | 릴레이 CPU만 |
| **합계** | **≈ 21.4s (실측)** | |

즉 **완료 RPS ≈ VU / 21.4**로, 상한을 정하는 것은 서버 용량이 아니라 **mock의 토큰 페이싱 상수**다.
그래서 이 문서는 두 축을 나눠 보고한다 — 운용 용량(mock 기본값)과 서버 코어 한계(유휴 제거).

### 1.2 알려진 한계 — BM25 팔은 캐시 미스가 아니다

mock의 `BedrockHandlers.stripNonce()`가 전처리 결과의 `keywords`에서 nonce를 벗기므로,
BM25 쿼리는 `rag-questions.json`의 **30개 질문만 반복**한다. 벡터 팔은 `vectorQuery`에 nonce가
남아 매번 고유하다. 즉 PG 플랜·버퍼가 BM25 쪽에서는 뜨거운 상태로 도는 것이며,
절대 처리량을 인용할 때 붙여야 하는 단서다. (실사용자도 질문을 반복하므로 비현실적이진 않다.)

추가 단서: `MOCK_EMBED_MEDIAN_MS=150`은 **미보정 상수**다(README가 명시한 기존 부채).
전처리·TTFT 기본값도 2026-08-01 요청 12건 표본이라 신뢰구간이 넓다. 이번엔 재보정하지 않았다 —
2026-08-05 런과 같은 조건을 유지해 비교 가능성을 남기려는 선택이다.

### 2.3 이 baseline이 사다리를 다시 잡게 했다

런 1의 자원 단가로 외삽하면:

- 요청당 DB CPU **0.444 core-s** → 2 vCPU 포화 예상 **4.5 RPS**
- 요청당 app CPU 비율 0.196 → 100% 포화 예상 5.1 RPS
- iteration 21.4s 기준 4.5 RPS ≈ **VU 96**

계획했던 사다리 10/20/35/55는 상단이 DB 57%에 그쳐 무릎을 못 담는다. 다만 이 외삽은

프록시"를 같은 이유로 기각했다). 동시성이 오르면 요청당 비용은 보통 올라가고,
RAG의 `blks/req`는 이미 검색 하이브리드의 2배다. 그래서 상단을 96이 아니라 **70**으로 잡았다.

### 3.3 병목은 DB도 앱도 mock도 아니다 — Bedrock 클라이언트 커넥션 풀이다

VU70에서 터진 84건의 에러 메시지:

```
Bedrock 호출 실패 - modelId=mock.anthropic.claude-sonnet-4-5:
Unable to execute HTTP request: Acquire operation took longer than the configured
maximum time. This indicates that a request cannot get a connection from the pool
within the specified maximum time. This can be due to high request rate.
```

`BedrockClientFactory.async()`는 `NettyNioAsyncHttpClient`에 **`maxConcurrency`를 설정하지 않는다.**
AWS SDK v2 기본값(`SdkHttpConfigurationOption`, v2.33.5):

```java
private static final int DEFAULT_MAX_CONNECTIONS = 50;
private static final Duration DEFAULT_CONNECTION_ACQUIRE_TIMEOUT = Duration.ofSeconds(10);
```

**숫자가 전부 이 하나로 설명된다:**

| 관측 | 풀 상한 50 가설 |
|---|---|
| VU45 에러 0, ft p95 평평 | 동시 스트림 45 < 50 → 대기 자체가 없다 |
| VU70 ft p95 7,176 → 15,284 (**+8,108ms**) | 20건이 커넥션 대기 → 획득 타임아웃 10,000ms 안쪽 |
| VU70 에러율 **9.5%** | 10초를 넘겨 획득에 실패한 비율 |
| VU70 RPS가 선형의 77% | 상한 50 기준 이론 최대 = 50/21.4 = **2.34 RPS**, 실측 2.53(과도구간 포함) |
| 청크 간격 51.1ms (설정 51.0) | 커넥션을 잡은 뒤로는 스트리밍이 정상 — **mock은 포화가 아니다** |
| ttfb p95는 3,984 → 4,256 (+7%뿐) | 전처리(sync 클라이언트)는 멀쩡하다 — async 풀만의 문제 |

**다른 자원은 전부 한가하다.** VU70에서 DB CPU 31%, app CPU 0.188, DB iowait 0.233.
검색이 DB CPU 94%라는 하드웨어 한계에 닿았던 것과 대조적으로, RAG는 **설정한 적 없는 SDK 기본값**에
그 한참 앞에서 막힌다.

> ⚠️ **운영 경로에 그대로 적용되는가 — 조건부 예.** 부하테스트는 mock(JDK HttpServer)이 h2를
> 지원하지 않아 `Protocol.HTTP1_1`로 강제한 경로에서 쟀다. 운영은 h2다. 다만 `MAX_CONNECTIONS`
> 기본값 50은 두 경로가 공유하며, h2에서는 "동시 스트림 수" 상한으로 해석된다 — **천장 숫자는
> 같고 포화 시 거동만 다를 수 있다.** h2에서 재확인하기 전에는 "운영에서도 정확히 50에서
> 같은 방식으로 무너진다"고까지 말하면 안 된다.

바꾸고 런 2에 되돌려 검산했다:

| 레벨 | 판정 | TTFB 배수 |
|---|---|---|
| VU45 | 통과 | 정상 |

**뭉뚱그린 평균은 신호를 1.80배로 희석하고 있었다.** 레벨별로 보니 3.17배로 선명해진다 —
"어느 구간이 무너졌는가"를 지우는 집계는 판정에 쓸 수 없다.

### 3.1 배경 조건 — 런 1과 20.3시간 차이, 그 사이 크롤링 창이 지나갔다

## 4. 조치 — `maxConcurrency`를 명시하고 재측정 (커밋 `262bfa3c`)

3.3의 천장이 **하드웨어가 아니라 설정한 적 없는 기본값**이었으므로, 그것을 걷어냈을 때
다음 병목이 무엇인지가 RAG의 진짜 용량이다.

```java
// 두 경로 모두에 건다 — 부하테스트만 올리면 운영에 없는 천장을 재게 된다.
var httpClient = NettyNioAsyncHttpClient.builder().maxConcurrency(asyncMaxConcurrency);
if (hasText(endpointOverride)) {
    builder.endpointOverride(URI.create(endpointOverride));
    httpClient.protocol(Protocol.HTTP1_1);   // mock(JDK HttpServer)만 h2 미지원
}
return builder.httpClientBuilder(httpClient).build();
```

### 4.1 값을 300으로 정한 근거

`server.tomcat.max-connections`와 맞췄다. 원칙은 **"LLM 클라이언트가 서버가 받아들이는 수보다
더 좁은 제약이 되어서는 안 된다"**이고, 뒤집으면 **동시성을 제한하고 싶다면 그건 SDK 기본값이 아니라
명시적인 유입 제어여야 한다** — 검색이 `SearchConcurrencyLimiter`(상한 초과 시 429)로 한 것처럼.
**RAG에는 아직 유입 제어가 없다(부채).** 이번 조치는 우연한 제약을 없앤 것이지 제약을 설계한 게 아니다.

`connectionAcquisitionTimeout`(기본 10초)은 일부러 그대로 뒀다. 풀이 다시 마르면 조용히 느려지는
것보다 3.3과 똑같은 명확한 에러로 드러나는 편이 낫다.

### 4.2 운영 경로를 깨지 않는다는 확인

운영은 h2, 부하테스트 mock은 h1.1이다. 커스텀 `httpClientBuilder`를 넘기면 프로토콜까지
바뀌는 것 아닌가 — SDK 소스로 확인했다(v2.33.5):

```java
// NettyNioAsyncHttpClient.Builder#buildWithDefaults
return new NettyNioAsyncHttpClient(this, standardOptions.build()
                                                .merge(serviceDefaults)
                                                .merge(NETTY_HTTP_DEFAULTS)
                                                .merge(SdkHttpConfigurationOption.GLOBAL_HTTP_DEFAULTS));
// DefaultBedrockRuntimeBaseClientBuilder#serviceHttpConfig
.put(SdkHttpConfigurationOption.PROTOCOL, Protocol.HTTP2)
.put(SdkHttpConfigurationOption.PROTOCOL_NEGOTIATION, ProtocolNegotiation.ALPN)
```

`merge`는 이미 있는 값을 유지하므로 **명시한 옵션이 이기고, 명시하지 않은 옵션은 서비스 기본값이
이긴다.** 따라서 `maxConcurrency`만 걸면 실 AWS 경로의 h2는 그대로다. mock 경로만 `protocol`을
명시해 h1.1로 내린다 — 종전과 동일.

0.444보다 훨씬 믿을 만한 기준), 이 값으로 다음 병목을 예측해 사다리를 잡는다.

| "그러니 올리면 용량이 는다" | ❌ **기각.** 올리자 VU90부터 백엔드가 OOM으로 죽었다 |
| RAG의 다음 한계는 DB CPU다 | ❌ **기각.** DB는 붕괴 시점에 오히려 한가했다(0.28/2.0). 한계는 **JVM 힙 512MB** |
| 50은 잘못된 값이다 | ❌ **기각.** 이 힙 예산에서는 **우연히 맞는 값**이었다 — 벌크헤드로 기능하고 있었다 |

**교훈: 병목을 없애기 전에 그 뒤에 무엇이 받아주는지를 먼저 확인해야 한다.**
50을 걷어낸 것은 "제약을 없앤" 게 아니라 **"보호 장치를 없앤"** 것이었다.
검색은 반대 순서로 갔다 — 무릎을 실측한 뒤 그 상단에 맞춰
`SearchConcurrencyLimiter`(상한 15, 초과 시 429)를 **넣었다.** RAG에는 그게 아직 없다.

### 5.5 올리려면 선행되어야 하는 것

1. **RAG 유입 제어** — 검색의 `SearchConcurrencyLimiter` 상당. 상한 초과를 429로 거절해야
   한다. 상한을 올린다는 건 그 뒤에 받아줄 장치가 있다는 뜻이어야 한다
   → ✅ **해소 (11장)**: `RagConcurrencyLimiter`, 상한 45 / 초과 시 429
2. **힙 예산 재산정** — 512는 검색 부하 기준 산정값이다(`2026-08-20-jvm-heap-sizing.md`).
   동시 스트림 N개가 힙을 얼마나 쓰는지 측정하지 않은 채 동시성만 올리면 같은 결과가 난다
3. **과부하 시 로깅 억제** — 초당 52줄의 스택트레이스는 그 자체가 부하다

## 6. 결론 — RAG의 현재 용량

| | 값 | 근거 |
|---|---|---|
| **SLA 충족 운용 용량** | **VU45 ≈ 2.05 RPS** | 런 2·런 3에서 각각 2.05 / 2.04로 재현. first_token p95가 같은 창 무부하 대비 1.07배 |
| 하드 천장 | 동시 스트림 **50** | Bedrock async 클라이언트 `maxConcurrency` (SDK 기본값) |
| 그 천장의 성격 | **우연한 벌크헤드** | 걷어내면 JVM 힙이 OOM으로 무너진다 (5장) |
| 병목 위치 | **DB 아님** | 포화 시점 DB CPU 23~31%, iowait 0.19, mock 청크 간격 설정값 그대로 |
| 힙이 버티는 동시성 | 동시 **90** → **약 180** | 10장에서 eventstream 버퍼 축소로 2배가 됐다 |

검색이 "병목을 커넥션 → I/O를 거쳐 순수 DB CPU(2 vCPU, 94%)라는 **하드웨어 한계**까지 이동시켰다"로
끝난 것과 대조적으로, **RAG는 하드웨어 한참 앞의 소프트웨어 상한에 막혀 있다.**
다음 작업은 처리량 튜닝이 아니라 **유입 제어**다. (→ 11장에서 했다)

> **갱신 (10장)**: "그 상한을 풀면 힙이 먼저 터진다"는 5장의 판정은 여전히 유효하지만
> **한계가 동시 90 → 약 180으로 밀려났다.** 스트림당 live 힙이 3.60 → 1.87 MB로 줄었고
> (AWS SDK eventstream 디코더 버퍼 2 MiB → 32 KiB), 커밋 힙도 VU45에서 498 → 310 MB다.
> 이제 `maxConcurrency` 상향의 전제로 남은 것은 **유입 제어 하나뿐이다.**

> **갱신 (11장)**: 그 하나도 채워졌다 — `RagConcurrencyLimiter`(상한 45, 초과 시 429).
> 45는 SLA를 지킨 최고 동시성이자 async 풀 50보다 낮은 값이라, permit이 스트림 전 구간을
> 덮는 성질과 합쳐져 **`llm_stream ≤ 45 < 50`이 구조적으로 보장된다** — 초과분이 풀 앞의
> 조용한 대기가 아니라 429로 나간다. `maxConcurrency` 상향 자체는 여전히 미실행이고,
> 올릴 때는 **리미터 상한을 함께 올려야 한다.**

> ⚠️ 이 수치는 mock 지연(전처리 2,075ms / TTFT 1,650ms / 청크 51ms / 답변 410청크)에 종속된다.
> 완료 RPS ≈ VU / 21.4는 mock의 토큰 페이싱이 정하는 값이고, `MOCK_EMBED_MEDIAN_MS=150`은
> 미보정 상수다. 절대 RPS를 인용할 때 반드시 붙일 것.
> 또한 BM25 팔은 질문 30개를 반복하므로 캐시 미스가 아니다(1.2).

## 7. 긴 요청의 성능 지표 — RPS는 왜 안 맞는가

이번 측정에서 가장 크게 배운 방법론이다.

### 7.1 Little's Law가 문제를 정확히 말해준다

`L = λ × W`에서 우리가 제약받는 것은 **L(동시 진행 수)**인데, RPS는 `λ = L / W`이고
**분모 W(스트림 길이)가 LLM 손에 있다.** 그래서 λ는 우리 시스템이 아니라 LLM 속도를 재게 된다.

실제로 이번 천장은 **동시 스트림 50개**로 나왔지 2.05 RPS로 나오지 않았다. 2.05는 거기에
mock의 21.4초를 나눈 파생값이고, LLM이 2배 빨라지면 우리 코드가 한 줄도 안 바뀌어도 2배가 된다.
**동시 50은 불변이고 RPS는 아니다.**

### 7.2 지표별 판정 — 무엇이 신호를 담고 있었나

| 지표 | 이번 실행에서의 거동 | 판정 |
|---|---|---|
| **동시 진행 수** | 천장이 정확히 50에서 갈림 (VU45 정상 / VU70 붕괴) | ✅ **용량의 기본 단위** |
| **`first_token` p95** | VU45→70에서 7,176 → 15,284 (**+113%**) | ✅ **지연 SLA 기준선** |
| `stream_duration` p95 | 같은 구간 25,035 → 32,871 (+31%) | ❌ 토큰 페이싱이 지배 — 무릎을 놓친다 |
| `ttfb` p95 (첫 SSE 이벤트) | 같은 구간 3,984 → 4,256 (**+7%**) | ✅ 단계 국소화 — 전처리는 멀쩡했음을 증명 |
| **청크 간격** | 51.1ms vs 설정 51.0ms | ✅ **상류 포화 탐지기** — "mock이 아니라 획득 단계"를 가름 |
| HTTP 상태코드 | VU70에서 **비-2xx 0건인데 84 스트림 실패** | ❌ 헤더는 이미 200으로 나간 뒤 죽는다 |
| SSE terminal 사유 분포 | done/error/http_5xx로 실패를 정확히 분류 | ✅ **스트리밍의 성공 판정은 이것으로** |
| `core-s/req`, `blks/req` | VU25~70에서 0.201~0.237로 안정 | ✅ **시간 불변** — A/B와 외삽의 기준 |

`stream_duration`을 판정에 썼다면 무릎을 놓쳤다. 붕괴 구간에서도 +31%밖에 안 움직인다.

### 7.3 처리량을 보고해야 한다면 삼중항으로

λ 단독은 의미가 미정이다. 조건이 바뀌어도 안 틀리게 쓰려면:

> **동시 45 스트림 / 스트림 길이 p50 22.0초 / 완료 2.05 RPS**

셋 중 무엇이 변해서 숫자가 움직였는지 읽힌다. 참고로 LLM **서빙** 쪽 표준 지표인 tokens/sec는
여기서 상류를 재는 값이다 — 우리는 모델을 서빙하는 게 아니라 오케스트레이션하는 쪽이고,
우리 몫은 전처리 호출 + retrieval + 릴레이 셋뿐이라 지표도 상류와 분리해야 한다.

### 7.4 조치 — `rag_answer_in_flight` 게이지 신설 (커밋 `bd3f606e`)

7.1의 결론이 "동시 진행 수가 용량 단위"인데 **그걸 볼 지표가 없었다.** 검색은
`search_concurrency_in_use`를 노출하는데(SearchConcurrencyLimiter) RAG는 유입 제어가 없어
그것도 없었고, 이번엔 k6의 VU로 유추했다 — 부하테스트에서만 되고 운영에서는 안 보이는 방법이다.

- `rag_answer_in_flight` — 진행 중인 RAG 요청 수(핸들러 전체)
- `rag_answer_llm_stream_in_flight` — 그중 답변 스트림 단계에 있는 수

둘로 나눈 이유: **천장 50은 async 클라이언트 풀이고 그걸 쓰는 건 `generateStream`뿐이다.**
전처리(`generateJson`)는 sync 클라이언트라 별도 풀이다. 천장 근접도는 후자로, "몇 명이 기다리는가"는
전자로 봐야 한다. 전처리·retrieval 약 3초 / 답변 스트림 약 17초라 두 값은 15% 안팎 벌어진다.

게이지의 가치는 **안 새는 데** 전적으로 달려 있어(한 번 놓치면 단조증가해 못 쓰게 되고 하필
과부하 때 알아챈다) 반납 경로를 테스트로 고정했다 — 정상 종료·LLM 예외·retrieval 조기 반환
3경로 모두 0 복귀, 입력 검증 탈락 요청은 애초에 미집계.

이걸로 가능해지는 것: (a) 운영에서 천장 근접도 관측, (b) 향후 유입 제어의 입력,
(c) **부하테스트가 h1.1 mock 경로에서만 확인한 천장 50을 운영 h2 경로에서 검증** — 3.3의
"h2에서 재확인 전에는 단정하지 말 것"이 그제야 풀린다.

5.5의 요구사항이 아니라 수치로 확인됐다.

### 8.5 게이지 해석 정정 — 대기 중인 요청도 포함된다

실행 전 예측: "VU70에서 `llm_stream_in_flight`가 **50에서 멈춘다**(풀 크기)".
**실측: 70까지 갔다.** 예측이 틀렸고, 이유가 지표 해석에 중요하다.

게이지는 `generateStream()` **호출 직전에** 증가하는데 커넥션 획득은 그 호출 **안에서** 일어난다.
따라서 **커넥션을 기다리며 큐에 있는 요청도 이 게이지에 포함된다.**
VU70이면 약 50개 스트리밍 + 약 20개 대기 = 70, 관측과 맞는다.

즉 이 게이지는 「풀 점유량」이 아니라 「LLM 단계에 있는 요청 수」다. 그래도 **50 임계선은 유효하다** —
넘었다는 것은 곧 대기가 시작됐다는 뜻이고, 오히려 알람으로 쓰기 좋은 신호다.
풀 정의상 다음이 성립하므로 대시보드에서 둘을 분리할 수 있다:

```
스트리밍 중 = min(llm_stream_in_flight, maxConcurrency)
대기 중     = max(0, llm_stream_in_flight - maxConcurrency)
```

## 9. 스트림당 메모리의 정체 — AWS SDK eventstream 디코더 버퍼 2 MB

8.4에서 동시 스트림 1개가 live 힙 2.6~3.6 MB를 잡는 것을 실측했지만 **무슨 객체인지 못 갈랐다.**
프롬프트+답변은 수십 KB라 설명이 안 됐다. JFR로 확인했다.

### 9.1 방법 — 왜 힙 덤프가 아니라 JFR인가

- 이미지가 `eclipse-temurin:26-jre-jammy`(**JRE**)라 `jcmd`/`jmap`이 없다.
  실제 보유 도구: `java jfr jwebserver keytool rmiregistry`
- 힙 덤프는 full GC + 힙 전체 순회라 모든 페이지를 건드린다. 이 호스트는 스왑 347 MB 사용 중이고
  유휴에도 초당 523페이지를 밀어내므로, **최악 정지 21.6초(STW 중 swap-in)를 의도적으로 재현**하는 꼴이 된다
- `-XX:StartFlightRecording=settings=default,jdk.OldObjectSample#stackTrace=true,duration=30m,...`
  (`default`는 stackTrace가 false라 출처를 모르고, `profile`은 할당 프로파일링까지 켜져 2 vCPU에서
  측정을 흔든다 — 필요한 것만 켰다)
- `jcmd`가 없어 on-demand 덤프가 불가하므로 `duration` 만료로 자동 기록시켰다.
  **`OldObjectSample`은 덤프 시점의 live 표본을 싣기 때문에 부하 중에 만료돼야 한다** —
  JVM 기동 후 30분에 만료되도록 부하 시작 시각을 맞췄다.
  만료 시점 실측: `rag_answer_in_flight` **45**, live **350 MB**, committed 502/512 MB

### 9.2 결과 — 41개 샘플이 한 곳을 가리킨다

`OldObjectSample` 164개 중 타입 상위:

| 8 | `java.util.HashMap$Node` |
| 3 | `HashMap$Node[131072]` |
| 3 | `java.lang.String` |
| … | 나머지는 개수 1~2의 잡다한 것 |

크기 분포도 같은 그림이다 — **41개가 `2.0 MB`**, 나머지는 대부분 수십~수백 바이트.

할당 스택이 한 줄도 안 흩어진다:

### 9.3 바이트코드로 확정

`eventstream-1.0.1.jar`의 `MessageDecoder` 무인자 생성자:

```
invokestatic  #9    // ByteBuffer.allocate:(I)

```

**`ConverseStream` 호출 하나당 2 MiB `ByteBuffer`를 무조건 잡는다.** 인자 없는 생성자라
크기 인자가 없고, SDK 내부라 우리 설정으로 못 건드린다.

**업그레이드로도 못 푼다** — Maven Central에 존재하는 버전은 `1.0.0`과 `1.0.1`뿐이고
우리가 이미 최신(1.0.1)이다.

> 우리가 잘못한 게 아니라 SDK 설계다.

### 9.5 판정 — 결론이 바뀐다

5.5는 상한을 올리기 전 선행조건으로 "힙 예산 재산정"을 요구했다. 그 답이 나왔고,
**"버퍼를 줄인다"는 선택지는 없다.**

| 선택지 | 판정 |
|---|---|
| eventstream 버퍼 축소 | ❌ **불가.** 무인자 생성자에 하드코딩, SDK 내부, 최신 버전 |
| SDK 업그레이드 | ❌ **불가.** 1.0.1이 최신 |
| **동시성 상한을 이 비용으로 산정** | ✅ **현실적인 답.** 동시 N개 = `2 MB × N` 확보 |
| Bedrock async 대신 다른 경로 | ⚠️ 검토 대상. `rag.openai.base-url`이 이미 Bedrock mantle을 가리키고 그쪽은 SSE라 이 디코더를 안 탄다. 다만 모델 라우팅·응답 형식이 달라 큰 변경 |

**따라서 RAG 동시성의 메모리 원가는 스트림당 최소 2 MB로 고정이다.**
현재 상한 50이면 스트리밍 중 **100 MB가 항상 잡혀 있다.** 동시 100을 원하면 그것만으로 +100 MB다.
이건 이제 추측이 아니라 확정된 제약이며, 유입 제어 상한을 정할 때의 기준선이다.

### 9.6 한계

- `OldObjectSample`은 **표본이지 전수가 아니다.** 41개가 45 스트림과 1:1로 맞는 것은
  강한 증거지만, "2.0/3.6 = 55%"라는 비율 자체는 8.4의 힙 측정에 기대고 있다
- JFR 녹화 자체가 유휴 live set을 약 50 MB 올린 것으로 보인다(180 → 229 MB, 부하 종료 후에도
  안 내려감). **플래그 제거 후 180으로 복귀하는지 확인해야 확정된다**

## 10. 조치 — eventstream 버퍼 2 MiB → 32 KiB (커밋 `aec44b4a`)

9장이 규명한 "스트림당 2 MB는 SDK 디코더 버퍼"를 걷어냈다.
9.5는 이걸 **"버퍼를 줄인다는 선택지는 없다"**고 판정했는데, **그 판정이 틀렸다.**

### 10.1 왜 판정이 뒤집혔나 — 소스를 끝까지 읽지 않았다

9장에서는 바이트코드(`ldc 2097152`)만 보고 "하드코딩이라 못 건드린다"고 결론냈다.
소스를 열어보니 **원본 주석 자체가 답을 갖고 있었다**:

```java
/** Initial buffer size is 2MB. Will grow as needed to accommodate larger messages. */
private static final int INITIAL_BUFFER_SIZE = 2048 * 1024;
```

그리고 `feed()`에 실제로 확장 분기가 있다:

```java
if (buf.capacity() < currentPrelude.getTotalLength()) {
    buf = ByteBuffer.allocate(currentPrelude.getTotalLength());   // 메시지 크기에 맞춰 재할당
```

**2 MiB는 상한이 아니라 그냥 "처음부터 크게 잡아둔 값"이다.** 줄여도 정확성에 영향이 없다.
크기 인자 생성자 `MessageDecoder(Consumer, int)`도 이미 존재한다(package-private, "tests only").

> **교훈**: 바이트코드는 "무엇을 하는가"는 보여주지만 "왜 그 값인가"는 안 보여준다.
> 9장에서 소스까지 갔으면 하루 빨리 알았다.

### 10.2 다른 길은 실제로 전부 막혀 있었다 (9.5는 여기까진 맞았다)

| 시도 | 결과 |
|---|---|
| SDK 설정 노브 | ❌ 없음 (aws-core·sdk-core 전수 검색) |
| 주입 지점 | ❌ `SynchronousMessageDecoder`는 `private static final` 내부 클래스, `new MessageDecoder()` 하드코딩 |
| 버전 업그레이드 | ❌ Maven Central에 1.0.0/1.0.1뿐, 이미 최신 |

### 10.3 조치 — 클래스패스 섀도잉

`src/main/java/software/amazon/eventstream/MessageDecoder.java`에 같은 FQCN을 둔다.
Spring Boot 실행 jar는 `BOOT-INF/classes/`를 `BOOT-INF/lib/*.jar`보다 먼저 탐색하므로 우리 것이 이긴다.
**추측하지 않고 실측했다** — 같은 jar에서 클래스패스 순서만 바꿔:

| 순서 | 결과 |
|---|---|
| `BOOT-INF/classes` 먼저 | 우리 클래스(class file v70)를 찾아 로드 시도 |
| 라이브러리 먼저 | `INITIAL_BUFFER_SIZE = 2097152` 로드 (대조군) |

변경은 상수 한 줄뿐이고 디코딩 로직은 원본과 동일하다.
`-Dsmalltown.eventstream.initial-buffer-bytes`로 재컴파일 없이 조정 가능(크기 스윕용).

**32 KiB를 고른 근거**: Bedrock 메시지는 프렐류드 12B + 헤더 약 100B + JSON 수십~수백 B로
보통 250B 남짓이다. 32 KiB면 100배 넘는 여유이고 원본의 1/64다.

### 10.4 검증 — 실 SDK 언마샬러가 통과했다

README가 *"eventstream 프레이밍(CRC/헤더)은 실 SDK 언마샬러로만 검증 가능하다"*고 지목한
`BedrockMockServerSdkIT`가 우리 32 KiB 디코더로 **CRC까지 끝까지 소진**한다.

추가로 `MessageDecoderShadowingTest` 5건. 이 포크의 가장 큰 위험은
**섀도잉이 풀려도 아무 에러 없이 조용히 2 MiB로 돌아가는 것**이라 그걸 잡는 테스트가 핵심이다:

| 테스트 | 막는 것 |
|---|---|
| 섀도잉 적용됨 | 빌드/패키징 변화로 라이브러리가 다시 이기는 조용한 회귀 |
| 작은 메시지 왕복 | 디코딩 정확성 |
| **큰 메시지 자동 확장** | 초기 버퍼 축소의 안전 근거(64B로 시작해 100KB 메시지 처리) |
| 다중 메시지 분리 | 한 청크에 여러 메시지 |
| 1바이트씩 쪼개진 청크 복원 | SSE 실제 도착 형태 |

전체 891건 통과. Spotless는 이 파일만 제외했다 — **원본과 diff가 가능해야 업그레이드 때
로직 변경분을 대조할 수 있는데 재포맷하면 그게 깨진다.**

### 10.5 실측 (`20260828-095056`, VU45 × 20분)

| VU45 | 이전(런5) | 이번 | 변화 |
|---|---|---|---|
| 유휴 live | 180 MB | 166 MB | −14 |
| **live set** | **342 MB** | **250 MB** | **−92 MB** |
| **committed** | **498 MB** | **310 MB** | **−188 MB** |
| **스트림당** | **3.60 MB** | **1.87 MB** | **−48%** |

**예측 대조**: 예상 절감 1.97 MB/스트림(2 MiB − 32 KiB), 실측 **1.73 MB = 예측의 88%**.
남은 12%는 32 KiB 버퍼 자체(45개 = 1.4 MB)와 live set 측정의 ±5% 편차로 설명된다.

**성능 회귀 없음** — RPS 2.04(이전 2.05/2.02/2.04), ft95 7,439(이전 7,176~8,816 범위 안),
에러 0, `blks/req` 22,240. 메모리만 줄었다.

### 10.6 예상 못 한 수확 — committed 188 MB 감소

이전에는 VU45에서 committed가 **498~512로 상한에 붙어** 있었는데 이제 **310**에서 안정된다.

`2026-08-20-jvm-heap-sizing.md`가 규명한 것이 **"used가 아니라 committed가 비용이다"**,
그리고 **"최악 정지 21.6초는 STW 중 swap-in"**이었다. 커밋 힙이 188 MB 줄었다는 것은
그만큼 차가운 페이지가 줄었다는 뜻이고, 실제로 스왑 아웃이 **523 → 0 pages/s**로 멎었다.

> ⚠️ 단 스왑 *사용량*은 347 → 552 MB로 늘었고 두 측정 모두 부하 직후라 **호스트 수준 개선은
> 단정하지 않는다.** 직접 귀속 가능한 것은 JVM 커밋 힙 감소까지다.

### 10.7 판정 — 힙이 버틸 수 있는 동시성이 2배가 됐다

```
live = 166 + N × 1.87 MB

  N= 90 → 334 MB (heap 512 대비 1.53배 여유)   ← 5장에서 OOM 3회 났던 지점
  N=140 → 427 MB (1.20배)
  N=180 → 502 MB (1.02배)                      ← 새 한계
```

**OOM 임계가 동시 90 → 약 180으로 이동했다.**

병목 순위는 이렇게 바뀐다:

| 순위 | 9장까지 | 지금 |
|---|---|---|
| 1 | `maxConcurrency` 50 | **`maxConcurrency` 50** (그대로) |
| 2 | JVM 힙 (동시 **90**) | JVM 힙 (동시 **180**) |
| 3 | DB CPU (9.2 RPS) | DB CPU (그대로) |

**1순위는 그대로지만 2순위가 멀어졌다.** 5장에서는 상한을 올리자마자 힙이 터졌는데,
이제 동시 90까지 여유가 1.53배다 — **`maxConcurrency`를 올려볼 여지가 처음으로 생겼다.**

다만 **순서는 여전히 유입 제어가 먼저다.** 5.4의 교훈("병목을 없애기 전에 그 뒤에 무엇이
받아주는지 확인해야 한다")은 힙이 두 배가 됐다고 사라지지 않는다.

## 11. 조치 — RAG 유입 제어 신설 (`RagConcurrencyLimiter`)

5.5의 1번이자 이 문서가 계속 가리켜 온 빈칸이다. 10장으로 힙 여유가 2배가 되면서
`maxConcurrency` 상향의 전제로 남은 것이 이것 하나였다.

### 11.1 상한을 45로 정한 근거

두 가지가 독립적으로 같은 값을 가리킨다.

**(1) 실측으로 SLA를 지킨 최고 동시성이 VU45다.**

| VU | RPS | 판정 | 출처 |
|---|---|---|---|
| 45 | 2.05 / 2.04 / 2.02 / 2.04 | ✅ SLA 통과, **4회 재현** | 런2 3.2 · 런3 5.1 · 런5 8장 · 10.5 |
| 70 | — | ❌ 붕괴 (first_token p95 7,176 → 15,284, **+113%**) | 런2 3.2 |

검색이 상한 15를 "실측 무릎(VU10 정점 14.3 RPS, VU15에서 꺾임)의 상단"으로 잡은 것과 같은 방식이다.
RAG의 무릎은 50(풀)이고, 그 아래에서 SLA 통과가 확인된 마지막 레벨이 45다.

**(2) 풀(50)보다 낮아야 리미터가 실제로 셰딩을 한다.**

permit을 컨트롤러 진입부터 스트림 종료까지 유지하므로 구조적으로 다음이 성립한다:

```
rag_concurrency_in_use  ≥  rag_answer_in_flight  ≥  rag_answer_llm_stream_in_flight
     (문을 통과한 수)         (서비스가 처리 중)         (async 풀을 쓰는 구간)
```

따라서 **상한 L을 걸면 `llm_stream ≤ L`이 항상 보장된다.** L=45 < 50이면 async 풀이 큐를 만들 일이
없다 — 초과분은 429로 즉시·관측 가능하게 거절되고, SDK 풀의 **조용한 큐잉**으로 새지 않는다.
이게 중요한 이유는 8.5가 이미 확인한 성질 때문이다: `rag_answer_llm_stream_in_flight`는 커넥션
획득 **전에** 증가하므로 풀 앞 대기가 게이지에는 잡히지만 **상태코드로는 안 잡힌다**.
7.2의 "VU70에서 비-2xx 0건인데 84 스트림 실패"가 바로 그 모양이다.

남는 5칸은 **리미터를 타지 않는 관리자 RAG 테스트 페이지**(`streamAnswer` 6-arg 오버로드)가
같은 async 풀을 쓰기 때문에 남긴 여유다. 수동 단발 경로라 상한을 걸지 않았다.

힙으로도 확인된다 — 10.7의 식에 대입하면 `166 + 45 × 1.87 = 250 MB`이고, 이건 10.5의 VU45 실측
live set **250 MB**와 정확히 같다. heap max 512 대비 2.05배 여유.

> ⚠️ **이 값이 mock에 종속되지 않는 이유.** 45는 mock 지연(스트림 21.4초)에서 측정됐지만,
> 7.1의 결론대로 **불변량은 동시성이고 RPS가 아니다.** LLM이 2배 빨라져도 동시 45가 점유하는
> 힙(84 MB)과 풀 슬롯(≤45)은 그대로다. 실 Bedrock 경로로 옮겨지지 않는 것은
> "45 ≈ 2.05 RPS"라는 **파생값** 쪽이고, 상한 자체가 아니다.

**acquire timeout = 300ms** (검색과 동일). 상한 45 / 스트림 약 21초면 이탈률이
`45 / 21 ≈ 2.1건/초`라 300ms 창에 약 0.6건이 빠져나간다 — 도착 지터를 흡수하되 큐를 만들지 않는
길이다. Tomcat이 virtual thread(`spring.threads.virtual.enabled=true`)라 대기 자체는 거의 공짜다.

### 11.2 검색의 모양이 그대로 안 옮겨진 것 둘

**(a) permit 반납 지점.** 검색은 `try/finally`로 핸들러 본문을 감싼다. RAG는 안 된다 —
컨트롤러가 `SseEmitter`를 반환한 뒤에도 실제 작업은 `searchExecutor`에서 계속 돌기 때문에,
같은 모양을 쓰면 **정작 힙과 async 풀을 물고 있는 구간에 상한이 없어진다.**
그래서 반납은 `CompletableFuture.runAsync(...).whenComplete(...)`에 붙이고,
handoff 이전 이탈(시간당 한도 거절 · 모델 미설정 · executor 거부)만 `finally`가 담당한다.
양쪽이 겹치면 permit이 늘어나므로 `handedOff` 플래그로 정확히 한 번만 반납되게 했다.

**(b) 거절에 예외를 안 쓴다.** 요구사항 두 개가 동시에 걸린다 — SSE라 `SseEmitter` 생성
**전에** 상태코드를 확정해야 하고, 과부하 시 거절은 로그를 남기면 안 된다(5.3).
`RagBusyResponse`가 응답에 직접 429를 쓰고 핸들러는 `null`을 반환한다
(`ResponseBodyEmitterReturnValueHandler`가 `null`을 `requestHandled=true`로 처리한다).

또 permit을 **시간당 한도 체크보다 먼저** 잡는다. 한도 체크는 `rag_query_log`에 COUNT를 날리는
DB 조회이고 HikariCP 풀은 5개다. 과부하분이 그 앞에 줄 서는 것이 정확히 5.3이 관측한 붕괴 모양이라,
문을 먼저 닫아야 의미가 있다.

### 11.3 곁가지로 발견한 것 — `/api/*`의 429는 지금까지 500이었다

`RestApiExceptionHandler`는 `@Order(HIGHEST_PRECEDENCE)`에 `@ExceptionHandler(Exception.class)`를
갖고 있고 `isApiRequest("/api/...")`가 참이다. Spring MVC는 `ExceptionHandlerExceptionResolver`를
`ResponseStatusExceptionResolver`보다 **먼저** 돌리므로, `/api/*`에서 던진
`ResponseStatusException`은 전부 이 핸들러에 잡혀 **500 + 스택트레이스 ERROR 로그**가 됐다.

해당하던 곳: `/api/rag/answer`의 시간당 한도 429, `/api/rag/answer/loadtest`의 404·503 게이트,
`/api/search/articles/loadtest`의 동시성 429. **셋 다 HTTP 레벨 테스트가 없어 안 드러나 있었다**
(기존 테스트는 "던져진 예외의 타입"만 봤다).

추측이 아니라 실측했다 — 수정을 잠시 되돌리고 새 HTTP 테스트를 돌리니 그대로 나왔다:

```
시간당 한도 초과   Status expected:<429> but was:<500>
부하테스트 비활성  Status expected:<404> but was:<500>
```

`@ExceptionHandler(ResponseStatusException.class)`를 추가해 선언된 상태코드를 그대로 내보내고,
**4xx는 로그를 남기지 않는다**(5xx만 메시지 한 줄, 스택 없음). 15개 throw 지점이 한 번에 정상화됐다.

새 유입 제어 경로는 이 수정과 **무관하게** 예외를 안 쓴다 — 고쳐도 예외는 스택트레이스 fill-in과
리졸버 체인 전체를 타므로 셰딩 경로에는 여전히 부적합하다.

### 11.4 관측

메트릭 4종을 검색과 1:1로 노출한다: `rag_concurrency_requests_total{result}` ·
`rag_concurrency_in_use` · `rag_concurrency_limit` · `rag_concurrency_acquire_wait`.
`small-town-rag-answer` 대시보드에 패널 17(통과/거절)을 추가했고, 패널 16에는
`rag_concurrency_limit`을 겹쳐 그려 **"왜 45에서 멈추는가"** 가 풀 상한(50)과 함께 읽히게 했다.
패널 3은 이제 429가 두 종류(시간당 한도 + 유입 제어)라 제목을 정정했다.

`rag_concurrency_in_use`와 기존 `rag_answer_in_flight`의 차이는 "문을 통과한 수" vs
"서비스가 실제로 처리 중인 수"다(컨트롤러 구간과 입력 검증 탈락분만큼 전자가 크다).
7.4가 게이지를 만들며 적어 둔 **"(b) 향후 유입 제어의 입력"** 이 이걸로 회수됐다.

### 11.5 아직 안 한 것

**`maxConcurrency`는 여전히 50이다.** 5.4의 교훈("병목을 없애기 전에 그 뒤에 무엇이 받아주는지를
먼저 확인해야 한다")은 이제 충족됐지만, 올리는 것 자체가 새 사다리를 요구한다.
그리고 올릴 때는 **리미터 상한을 함께 올려야 한다** — 45 < 50이 뒤집히면 11.1의 (2)번 보장이 깨져
초과분이 429가 아니라 조용한 대기로 돌아간다.

### 11.6 실측 (`20260829-015822`, VU 45/70/140 × 7분) — 무릎이 사라졌다

배포 후 첫 런. 기본 mock(페이싱 유지), 실경로와 같은 리미터를 타는 `/api/rag/answer/loadtest`.

| VU | done | RPS | bad | shed(429) | ft50 | ft95 | DB CPU | appCPU | **llm_stream max** | in_use max |
|---|---|---|---|---|---|---|---|---|---|---|
| 45 | 868 | **2.01** | 0 | 2 | 4,534 | 8,356 | 0.489 | 0.146 | **45** | 45 |
| 70 | 868 | **2.01** | 0 | 32,912 | 4,732 | 7,549 | 0.491 | 0.184 | **45** | 45 |
| 140 | 866 | **2.03** | 3 | 111,032 | 4,848 | 8,256 | 0.473 | 0.292 | **45** | 45 |

**판정 — 세 가지가 확인됐다.**

**(1) 처리량이 평평하다.** 제공 부하를 3배로 올렸는데 완료 RPS가 2.01 → 2.01 → 2.03이다.
유입 제어가 하는 일이 정확히 이것이다 — 초과분을 흘려보내고 처리량을 유지한다.
런 3의 같은 구간과 대조하면:

| | 런 3 (유입 제어 없음) | 이번 (상한 45) |
|---|---|---|
| VU140 done | **0** | **866** |
| VU140 RPS | — (측정 불가) | **2.03** |
| 비-2xx | http_502 **38,543** | http_429 111,032 (설계된 거절) |
| 백엔드 | **12분간 3회 OOM 재기동** | uptime 4,686초, **리셋 0회** |
| DB CPU | 0.275 (한가해짐 = collapse) | 0.473 (평평) |
| HikariCP acq / pend | 1.0442s / 86 | 0.0114s / 9 |

**(2) 보장이 실측으로 성립했다.** `llm_stream max`가 세 레벨 모두 **정확히 45**다. 46이 된 적이 없다.
11.1의 (2)번 — permit이 컨트롤러 진입~스트림 종료를 덮으므로 상한 L에서 `llm_stream ≤ L` —
이 구조적 주장이 맞았고, 따라서 **async 풀(50)에는 닿지 않는다.**

**(3) 지연 무릎이 없어졌다.** first_token p95가 8,356 / 7,549 / 8,256으로 전 레벨 평평하다.
런 2에서 VU45→70은 7,176 → 15,284(**+113%**)였다. 초과분이 큐에 서지 않고 즉시 거절되므로
**통과한 요청의 지연이 부하와 무관해졌다.**

시간 불변량도 안정적이다 — `core-s/req` 0.237/0.237/0.229, `blks/req` 21,383/21,254/21,297.
세 레벨이 같은 일을 했다는 확인이라(7.2) 비교가 유효하다.

### 11.7 이번 런의 한계 — `shed` 건수는 못 쓴다

**k6 이미지를 다시 굽지 않고 돌렸다.** `docker/Dockerfile`이 `scenarios/`를 이미지에 COPY하므로
로컬에서 넣은 429 백오프가 Fargate에 안 실렸다(README가 "2026-08-08에 이 함정에 걸려 한 번
헛돌렸다"고 적어 둔 바로 그 함정 — 두 번째다).

그래서 거절된 VU가 `Retry-After`를 안 지키고 즉시 재발사했다. 결과:

- **`shed` 건수(32,912 / 111,032)는 VU 회전 속도지 제공 부하가 아니다.** 초당 약 264건까지 갔는데,
  백오프가 걸렸으면 약 5건/초였을 값이다. 상한 위 레벨에서 **VU를 동시성으로 읽으면 안 된다.**
- 다만 판정 자체는 **더 가혹한 조건에서** 통과했다. 초당 264건이 두들기는 동안에도
  `llm_stream ≤ 45`·힙 평평·재기동 0이었다. 현실적인 부하보다 훨씬 센 시험이다.

**VU140의 `bad` 3건**(error 1 · http_503 2)은 약 11.2만 요청 중 0.003%다. 로그를 안 봐서
귀속은 못 했다 — nginx 순간 503인지 mock ECS 흔들림인지 구분이 안 된다. **셰딩이 실패를 0으로
만들지는 못했다**는 것까지가 이 런이 말할 수 있는 전부다.

또 `통과`(807)와 `done`(868)이 7% 어긋나는데, 전자는 `increase()` 윈도 추정이고 후자는 레벨
누적이라 생기는 경계 효과다. 실제 누락이 아니다.

## 12. 계측 유효성 — mock 재캘리브레이션은 순환이었다

11장 다음 순서로 "mock 재캘리브레이션 → 런 4"를 잡았는데, **그 순서가 틀렸다.** 재캘리브레이션을
시작하자마자 막혔고, 막힌 이유가 앞으로의 모든 측정에 영향을 준다.

### 12.1 표본의 99.5%가 mock이었다

README는 mock 지연 상수를 `rag_answer_llm_*` 지표로 보정하라고 적어 뒀다. 그런데 그 지표에는
**경로를 가르는 라벨이 없었다.** 30일 창 실측(2026-08-28):

| 경로 | 요청 수 (30일) |
|---|---|
| 실경로 `/api/rag/answer` | **54** |
| mock 경로 `/api/rag/answer/loadtest` | **11,024** |
| `rag_answer_llm_ttfb_seconds_count` 합계 | 11,035 |

즉 **LLM 타이머 표본의 99.5%가 mock이 만든 것**이다. 이 지표로 mock을 보정하면 mock이 자기가 넣은
지연 상수를 되읽는 셈이다. 8월 초 캘리브레이션(요청 12건)은 mock이 생기기 전이라 유효했지만,
8월 말 사다리 런들이 그 뒤로 우물을 오염시켰다.

**더 나쁜 건 이게 조용히 성공한다는 점이다.** 눈치채지 못하고 돌렸으면 "실측과 일치함"이라는
확인을 받고 넘어갔을 것이다.

### 12.2 조치 — `source` 라벨

`rag_answer_llm_ttfb_seconds` / `_duration_seconds` / `_chunk_gap_seconds` / `_chunk_size_bytes`와
전처리 Observation에 `source=real|loadtest|admin`을 붙였다. 경로별로 **미리 등록**해 두고 스트림
시작 때 한 번만 고른다 — chunk gap·size는 요청당 수백 번 기록되므로 매번 미터를 조회하면 안 된다.

기존 대시보드 쿼리는 `sum by (le)` 집계라 그대로 동작한다(라벨이 늘어도 합산 결과는 같다).
바뀐 건 **필터가 가능해졌다**는 것뿐이다. 라벨 도입 이전 구간은 분리 불가라 버린다.

### 12.3 그래도 지금 확인된 것 — mock은 실제보다 1.46배 느리다

`http_server_requests_seconds`는 `uri` 라벨로 두 경로가 이미 갈린다. 라벨 도입 전에도 **전체 스트림
길이**만은 비교가 된다 (30일 창, status=200):

| | 평균 | p50 | 표본 |
|---|---|---|---|
| 실경로 | **15.95s** | 11.93s | 54건 |
| mock 경로 | **23.27s** | — | 11,024건 |

**방향이 중요하다.** `λ = L/W`에서 mock은 W를 46% 과대평가하므로, mock 기반 용량 수치는
**보수적인 쪽으로 틀린다** — 실제로는 같은 상한에서 처리량이 더 나오고(L=45에서 2.05가 아니라
약 2.8 RPS), 같은 도착률에서 동시 스트림 수와 힙 점유가 더 적다.
**상한 45의 안전성을 흔들지 않는다.** 오히려 여유가 더 있다는 뜻이다.

단 46%가 어느 단계(전처리 / TTFT / 토큰 페이싱)에서 오는지는 `source` 표본이 쌓여야 갈리므로
**개별 상수는 바꾸지 않았다.** 총합만 알고 배분을 모르는 채 상수를 손대면 더 나빠진다.
(실경로 p95는 표본이 3건 수준이라 히스토그램 최상단 버킷에 걸린다 — 인용 금지.)

`MOCK_EMBED_MEDIAN_MS`(150)는 여전히 미보정이다. 유일한 후보 `search_query_embedding_seconds`의
30일 평균은 86.7ms인데, README가 이미 지적한 대로 **DB 캐시 히트가 섞여 있어** 실제 API 레이턴시가
아니다. 같은 자리에 머물러 있음을 확인한 것까지가 이번 소득이다.

### 12.4 순서 정정

실경로 트래픽이 **하루 약 1.8건**이다. 라벨을 붙였어도 의미 있는 표본이 쌓이는 데 몇 주가 걸린다.
**재캘리브레이션은 노력이 아니라 트래픽 축적에 막힌 항목**이고, 따라서 다른 작업의 선행조건으로
두면 안 된다.

그리고 런 4는 애초에 여기 의존하지 않는다 — 런 4는 토큰 페이싱을 **제거하고** 도는 실험이라
mock 지연 상수를 0 근처로 두고 서버 코어 비용만 잰다. 오염된 상수가 개입할 여지가 없다.

**정정된 순서: 11장 검증 → 런 4 → maxConcurrency 상향.** 재캘리브레이션은 그 옆에서
트래픽이 쌓이는 대로 따로 회수한다.
