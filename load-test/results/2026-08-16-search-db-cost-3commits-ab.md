### BM25 단계의 −185ms는 유의어 커밋이 아니다

처음엔 "유의어 확장이 BM25 타이머 안에 있었다"고 읽었는데 **코드로 확인하니 틀렸다.**
`ArticleSearchService`에서 `bm25StartTime`은 `buildBM25SearchQuery`(확장이 도는 곳)
**다음 줄**에서 찍히고(`:535`), 타이머가 감싸는 것은 `readOnlyTx` 트랜잭션뿐이다(`:535~555`).
즉 BM25 타이머 = **커넥션 획득 + BM25 쿼리 실행**이고, 확장은 양쪽 빌드 모두 그 바깥에 있다.

그러면 202 → 17ms는 **워밍 쿼리 제거(`b020104`)의 2차 효과**다. 같은 DB 2코어에서
요청마다 20만 블록을 훑던 스캔이 사라지자 BM25 쿼리와 커넥션 획득이 원래 속도를 되찾았다.
17ms는 `1012da0` 커밋 메시지가 인용한 Tempo 실측 "BM25 본검색 11~31ms"와 일치한다 —
**M의 202ms는 BM25가 느렸던 게 아니라 DB가 붐볐던 것이다.**

확장은 M/M'에서 **컨트롤러**가 서비스 호출 **전에** 돌렸으므로 서버측 `총:`에도 안 잡힌다.

### 4.1 VU2가 정점이고, 거기엔 풀 압력이 아예 없다

VU1→VU2는 두 실행 모두 **완전 선형**(2.70→5.52, 2.59→5.51)이고 획득대기가 **정확히 0**이다.
닫힌 루프라 처리량 = VU ÷ 지연이며(2 ÷ 0.345s = 5.8 ≈ 실측 5.7), **VU2는 포화가 아니라
지연 바운드**다. 즉 **현재 처리량은 풀에 막혀 있지 않다.**

풀은 그 위(VU5)에서 비로소 벽이 된다. 셋이 독립적으로 같은 말을 한다:

| 증거 | VU2 | VU5 |
|---|---|---|
| Hikari 활성 커넥션 평균 (`avg_over_time`) | 2.25 / 5 (45%) | **4.58 / 5 (92%)** |
| 획득대기 평균 | 0.000s | **0.189~0.233s** |
| `search_query_embedding` 단일행 SELECT 중앙값 | **2ms** | **120ms** |

마지막 줄이 가장 선명하다 — 인덱스로 한 행 집는 쿼리가 60배 느려졌는데 **DB CPU는 49%**다.
DB가 느린 게 아니라 커넥션을 못 잡는 것이다. 그 사이 DB 코어(49%)·디스크(nvme 49% busy)·
앱 호스트(0.42코어, 21%)는 전부 절반이 논다.

### 4.2 그런데 풀을 채우고 있는 건 DB 일이 아니다

커넥션 점유 시간(`usage`) 중 **실제로 쿼리가 도는 비율**을 계산하면:

| 구성 | VU1 | VU2 | VU5 |
|---|---|---|---|
| M' (before) | 73% | **84%** | 53% |
| **N (after)** | 38% | **40%** | 22% |
| **N' (after)** | 34% | **39%** | 18% |

<sub>점유 = `rate(usage_sum)` (= 체크아웃/s × 평균 점유), 실행 = `rate(pg_stat_database_active_time)`.</sub>

**이전에는 커넥션 시간의 73~84%가 실제 쿼리였다 — 그때는 DB가 진짜 병목이 맞았다.**
지금은 요청당 DB 일이 10배 줄었는데 **유휴 점유는 그대로 남아** 비율이 40%로 떨어졌다.
경합이 없는 VU1에서도 34~38%이므로 이건 혼잡의 결과가 아니라 **구조적 상수**다.

요청당으로 보면 VU2에서 커넥션을 **430ms** 잡는데 그중 쿼리는 **193ms**뿐이다(아래 트레이스).

### 4.3 유휴 점유의 정체 — OSIV가 유력하다 (가설, 미검증)

Tempo 트레이스 1건(VU2, 총 391ms, `14ac0c27e132db80`)의 스팬 타임라인:

| 스팬 | 시작 | 길이 |
|---|---|---|
| SELECT (유의어 확장, 요청 스레드·**비트랜잭션**) | 1.4ms | 1.6ms |
| SELECT `search_query_embedding` (벡터 브랜치) | 2.0ms | 1.1ms |
| http post — Clova mock | 3.3ms | 197ms |
| SELECT `article_analyzed_content` (BM25) | 4.3ms | 9.2ms |
| SELECT (벡터 2단계) | 201ms | 104ms |
| SELECT (cross-scoring 퍼널) | 306ms | 47ms |
| SELECT `article_analyzed_content` (보충) | 353ms | 14ms |
| SELECT `article` / `small_town` / `like_log` (페이지 조립) | 367~389ms | 17ms |
| **SQL 합계** | | **193ms** |

측정된 **요청당 체크아웃 2.93회**가 가설을 가른다:

| 가설 | 예측 체크아웃 | 예측 점유/req | 실측(2.93회 / 430ms) |
|---|---|---|---|
| **(a) OSIV가 요청 스레드 커넥션을 요청 끝까지 고정** | **3회** (요청스레드 1 + 벡터브랜치 2) | 요청길이 319 + 벡터쿼리 104 + 조회 1 ≈ **424ms** | ✅ 일치 |
| (b) 벡터 브랜치가 Clova 197ms 내내 점유 | 4~5회 | 193 + 197 = 390ms | ❌ 체크아웃 수 불일치 |

(a)를 뒷받침하는 정황:

- `spring.jpa.open-in-view`가 **어디에도 설정돼 있지 않다**(기본 true). 기동 로그에 Spring의
  OSIV 경고가 그대로 찍힌다.
- 요청 스레드의 **첫 쿼리가 비트랜잭션**(유의어 확장, t=1.4ms)이고 **마지막 쿼리가 t=389ms**
  (페이지 조립)다. OSIV라면 그 사이 내내 커넥션 1개가 물려 있다.
- 벡터 브랜치는 별도 가상 스레드라 OSIV 바인딩을 물려받지 않아 체크아웃이 따로 잡힌다 —
  관측된 "3회"의 구성과 맞는다.

> ⚠️ **이건 아직 가설이다.** 산술이 맞아떨어지지만 커넥션 체크아웃 자체를 계측한 건 아니다.
> 확정하려면 `spring.jpa.open-in-view=false`로 배포해 요청당 점유(`usage_sum/count × 체크아웃`)가
> 430 → 200ms대로 떨어지는지 보면 된다. 리스크는 직렬화 중 지연로딩(`LazyInitializationException`)인데,
> 이 프로젝트는 규약상 응답에 엔티티를 직접 노출하지 않고 DTO를 쓰므로 노출면이 좁다.

### 4.4 그래서 "풀 크기를 올리자"는 절반만 맞다

| 레버 | 평가 |
|---|---|
| **1. 유휴 점유 제거 (OSIV / 트랜잭션 경계)** | **최우선.** DB에 부하를 1도 더 주지 않고 풀 실효 용량을 **2배 이상** 늘린다. 요청당 430 → 200ms면 같은 풀 5로 지금의 2배 동시성을 받는다 |
| 2. `DB_POOL_SIZE` 상향 | **테스트는 값싸니 병행.** 다만 이건 유휴 점유를 그대로 둔 채 포화 DB가 아닌 **절반 노는 DB에 동시성을 더 밀어넣는** 방식이다. DB CPU·디스크에 여유가 있으니 이득은 나겠지만, 1번을 먼저 하면 필요 없을 수도 있다 |
| 3. DB 코어 증설 | **보류.** 정점에서 코어 절반, 디스크 절반이 논다. 지금 늘려도 풀이 먼저 막는다 |
| 4. 동시성 제한(admission control) | 천장은 못 올리지만 VU5 이상에서 degraded(4.8~5.2%)와 커넥션 타임아웃 5xx를 없앤다 |

### 선행 문서의 두 결론을 뒤집는다

| 선행 결론 | 지금 |
|---|---|
| 하드 천장 = 2코어 × 1.34 = **2.7 RPS** | **폐기.** 요청당 비용이 상수가 아니었다. 현재 정점 5.5~5.6 RPS, 정상상태 5.3~6.6 RPS |
| `DB_POOL_SIZE` 상향 **철회** (근거: 정점에서 CPU 93%) | **그 근거는 사라졌다**(정점 CPU 48~50%). 다만 풀 상향이 정답이라는 뜻은 아니다 — 4.4 참고 |
| DB 코어 증설 2순위 | **하향.** 코어·디스크 모두 절반이 논다 |

| 주장 | 판정 |
|---|---|
| 요청당 DB 비용 감소 | ✅ **확인(2회).** blks/req −92%, core-s/req −76%, dbact/req −84%. after 2회가 소수점까지 일치 |
| 지연 감소 | ✅ **확인(2회).** 클라이언트 p50 전 레벨 −47~67%, 서버 `총:` −33~43% |
| 처리량 개선 | ✅ **확인(2회).** level_5 정상상태 2.29 → 5.93 (**+159%**), 전 레벨 +57~162% |
| 워밍 쿼리가 DB 블록의 지배 항목이었나 (A) | ✅ **확인.** blks/req 22만 → 1.7~1.8만 |
| 유의어 확장이 요청 앞단 ~190ms였나 (B·C) | ✅ **확인.** 클라이언트−서버 격차 188~231 → 23~34ms |
| 커밋별 분리 귀속 | ⚠️ **부분만 가능.** A(블록·DB CPU 축)와 B·C(요청 앞단 지연 축)는 갈렸다. **B와 C 사이는 분리 불가** |
| 랭킹 정확도 | — 범위 밖 (mock 벡터, 기존 부채) |

**결론: 3개 커밋은 의도대로 작동했고, 이 시스템의 병목을 "DB가 일하느라 커넥션이 없다"에서
"일도 안 하면서 커넥션을 잡고 있다"로 옮겼다.**

정점(VU2)에는 아직 풀 압력이 전혀 없고, 그 위(VU5)에서 풀이 벽이 된다. 다만 풀을 채우는 것의
60~80%가 쿼리가 돌지 않는 시간이므로 **다음 레버는 풀 크기가 아니라 점유 시간**이다 (4장).

### 한계

- after 2회의 level_5 처리량 편차가 ±11%(5.26 / 6.59)로 before(±6%)보다 크다.
  요청당 비용 지표는 반대로 거의 완전히 일치하므로, 이 편차는 **커밋의 효과가 아니라
  포화 구간의 스케줄링 편차**로 본다(선행 문서 3장의 과도구간 현상과 같은 계열).
- before가 3일 전 실행이라 시간대·배경 조건이 완전히 같지는 않다(N은 21:14 KST,
  M'는 10:07 KST). 시작 전 DB는 양쪽 다 무부하였다.
- M/M' 스크립트 재수집값은 발행 수치와 레벨 RPS는 일치하나 정상상태 RPS가
  2.15/2.42(발행) vs 2.20/2.30(재수집)으로 ±3% 다르다. 오래된 샘플의 압축 영향으로 보이며,
  N과의 격차(3배)에 비하면 무시 가능하다.
