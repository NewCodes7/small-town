## 3.3 관련 질문 및 답변

### Q1. TOAST를 무엇의 범인으로 지목한 거지?

**답변 요약:** 
문서 작성자는 TOAST를 **"쿼리 성능 저하(처리 지연)를 유발하는 I/O 병목의 주원인"**으로 잘못 지목했었습니다.

**상세 설명:**
1. **TOAST란?** 
   PostgreSQL의 TOAST(The Oversized-Attribute Storage Technique)는 단일 데이터베이스 페이지(기본 8KB)의 크기를 초과하는 큰 데이터를 저장하기 위한 메커니즘입니다. 데이터를 압축하거나 별도의 백그라운드 테이블(TOAST 테이블)로 빼내어 저장합니다. ([PostgreSQL 공식문서: TOAST](https://www.postgresql.org/docs/current/storage-toast.html))
2. **범인으로 지목한 이유:**
   데이터베이스 통계(예: `pg_stat_statements`)의 블록 I/O 카운터를 확인했을 때, **"블록 접근의 64%가 TOAST 인덱스 조회"**에 집중되어 있다는 수치가 도출되었습니다. 측정 가능한 지표에서 압도적인 비중을 차지하고 있었기 때문에, TOAST 테이블에서 무거운 데이터를 읽어오는 I/O 비용이 쿼리를 느리게 만든다고 착각(오진)한 것입니다.
3. **오진이었던 이유:**
   해당 TOAST 블록들은 디스크에서 읽어온 것이 아니라 이미 메모리에 올라와 있는 상태(Cache Hit)였습니다. 메모리 읽기 비용은 마이크로초(µs) 수준이므로 전체 지연 시간의 진짜 원인이 될 수 없었습니다. 진짜 원인은 **블록 카운터라는 '계기판'에는 아예 기록되지 않는 순수 CPU 연산 시간(파라미터 텍스트 재파싱)**이었습니다.

### Q2. 파라미터 텍스트 재파싱이 아무 데도 안 찍히는데 알게 된 계기가 뭐지?

**답변 요약:**
`pg_stat_statements`와 같은 일반적인 I/O 지표에는 순수 CPU 파싱 비용이 남지 않지만, **`EXPLAIN (ANALYZE, BUFFERS, VERBOSE)` 명령어를 통한 노드별 소요 시간 분해와 표현식 확인**을 통해 진범을 잡아냈습니다.

**상세 발견 과정 (문서 2장 참고):**
1. **시간의 공백 발견 (`actual time` 분석):**
   `EXPLAIN ANALYZE` 실행 계획을 보면 부모 노드와 자식 노드의 소요 시간이 나옵니다. 자식 노드(실제 데이터 조인 및 인덱스 스캔)들이 소모한 시간의 합은 1.2ms에 불과한데, 이들을 감싸고 있는 부모 노드(Nested Loop)의 누적 시간은 86.5ms로 나타났습니다. 이는 **부모 노드 자체가 스스로 소모한 시간이 무려 85.3ms**나 된다는 것을 의미합니다.
2. **병목의 정체 확인 (`VERBOSE` 출력 분석):**
   그렇다면 부모 노드에서 무엇을 했길래 85ms나 걸렸는지 확인해야 합니다. `VERBOSE` 옵션을 주면 각 노드가 반환하는 출력 표현식(`Output`)을 보여줍니다. 부모 노드의 Output에 `l2_normalize(($1)::halfvec)`라는 표현식이 그대로 남아있는 것이 발견되었습니다.
3. **결론 도출:**
   `$1`로 표시된 11.8KB 크기의 파라미터 문자열이 실행 전 상수로 치환되지 못하고(`generic plan` 고착), **조건에 맞는 매 행(row)을 스캔할 때마다 무거운 파싱(텍스트 -> 벡터) 연산을 반복 수행**하고 있었다는 사실을 밝혀낸 것입니다. 이는 계기판의 총합에는 숨어있었지만, 실행 계획의 노드 간 시간 격차를 통해 역추적할 수 있었습니다.

## 3.4 관련 질문 및 답변

### Q3. 해당 첫 번째 SELECT 쿼리는 무슨 원리로 뭘 측정하는 거지?

**해당 쿼리:**
```sql
SELECT state, wait_event_type, wait_event, count(*)
FROM pg_stat_activity WHERE datname = current_database()
GROUP BY 1,2,3 ORDER BY 4 DESC;
```

**답변 요약:**
이 쿼리는 PostgreSQL의 시스템 뷰인 `pg_stat_activity`를 활용하여, **현재 활성화된 데이터베이스 커넥션들이 구체적으로 '어떤 대기 상태(Wait Event)'에 머물러 있는지 실시간으로 그룹화하여 측정(샘플링)하는 쿼리**입니다.

**작동 원리 및 측정 대상:**
*   **`pg_stat_activity` 뷰:** PostgreSQL 서버에 연결된 각 백엔드 프로세스(세션)의 현재 상태와 실행 중인 쿼리 등의 스냅샷 정보를 제공합니다. ([PostgreSQL 공식문서: pg_stat_activity](https://www.postgresql.org/docs/current/monitoring-stats.html#MONITORING-PG-STAT-ACTIVITY-VIEW))
*   **`wait_event_type` & `wait_event`:** 
    프로세스가 무언가를 기다리고 있을 때, 무엇을 왜 기다리는지 알려주는 강력한 지표입니다.
    *   `Lock`: 다른 트랜잭션이 테이블이나 행에 건 무거운 락(Heavyweight Lock)이 풀리기를 대기.
    *   `LWLock` (Lightweight Lock): 공유 메모리 버퍼 접근 등 내부 엔진의 가벼운 동기화 락 대기.
    *   `IO`: 디스크에서 데이터를 읽거나 쓰는 물리적 파일 I/O 대기.
*   **`state = 'active'` 이면서 `wait_event_type IS NULL`인 상태의 의미:**
    이 조합이 문서에서 가장 핵심적인 부분입니다. 커넥션이 쿼리를 실행 중(`active`)인데 대기 이벤트가 없다(`NULL`)는 것은, 디스크를 기다리거나 락 경합 중인 상태가 아니라 **"프로세스가 온전히 CPU를 100% 점유하며 연산을 수행 중"**이라는 뜻입니다.

**문서에서의 시사점:**
문서 작성자는 성능이 오르지 않는 상황에서 이 쿼리를 실행해 보았습니다. 만약 I/O가 병목이었다면 `wait_event_type`에 `IO`가 다수 집계되었을 것이고, 락 경합이 문제였다면 `Lock`이 많이 보였을 것입니다. 
하지만 결과는 계속해서 `NULL`과 `active` 상태가 압도적이었습니다. 이를 통해 현재 시스템의 처리량(Throughput)이 오르지 않는 진짜 한계점이 **'DB 서버의 CPU 자원 포화'**임을 정확히 확정(측정)할 수 있었습니다.
