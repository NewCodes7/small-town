## 1.1 세 가지 지표

### Q1. 세 가지 지표 뿐만 아니라 시스템 측정 지표도 있어야 하지 않나? CPU, memory, network 등

**맞다. 그리고 이미 체계화되어 있다.**

원문이 다루는 지연(latency)·처리량(throughput)·포화도(saturation)는 **서비스 관점의 지표**다. CPU·메모리·네트워크·디스크 같은 **시스템 자원 관점의 지표**는 별도의 방법론으로 분류된다. 실무에서는 이 두 관점을 **동시에** 봐야 한다. 이를 체계화한 유명한 프레임워크가 두 개 있다:

#### (1) USE Method — 자원(인프라) 관점

Brendan Gregg가 만든 방법론으로, **모든 물리·논리 자원**에 대해 세 가지를 점검한다:

| 약어 | 뜻 | 예시 |
|---|---|---|
| **U**tilization (사용률) | 자원이 일을 하고 있는 비율 | CPU 사용률 70%, 디스크 busy 49% |
| **S**aturation (포화도) | 자원 앞에 쌓인 대기열 | CPU run queue 길이, 커넥션 풀 대기 시간 |
| **E**rrors (에러) | 자원에서 발생한 오류 수 | 네트워크 dropped packets, ECC 메모리 에러 |

이 방법론을 적용하면, 자원별로 이렇게 정리할 수 있다:

| 자원 | Utilization 지표 | Saturation 지표 | Error 지표 |
|---|---|---|---|
| **CPU** | `%user + %system` (또는 `1 - %idle`) | run queue 길이 (`vmstat`의 `r`), load average | machine check exceptions |
| **메모리** | 사용 중 RAM / 전체 RAM | swap in/out (paging), OOM kill 횟수 | ECC 에러 |
| **네트워크** | 대역폭 사용률 (현재 throughput / 최대 대역폭) | TCP retransmit, dropped packets | interface errors (`ifconfig`의 errors) |
| **디스크** | `%util` (`iostat`) | I/O queue depth (`avgqu-sz`) | 디바이스 에러 |
| **커넥션 풀** | 활성 커넥션 / 최대 풀 크기 | 획득 대기 시간, 대기 큐 길이 | 타임아웃 에러 |

> 출처: Brendan Gregg, *The USE Method*, https://www.brendangregg.com/usemethod.html

#### (2) RED Method — 서비스(요청) 관점

Tom Wilkie가 마이크로서비스 모니터링을 위해 만든 방법론으로, 원문의 세 지표와 거의 일치한다:

| 약어 | 뜻 | 원문의 대응 지표 |
|---|---|---|
| **R**ate | 초당 요청 수 | 처리량 (throughput, RPS) |
| **E**rrors | 초당 실패한 요청 수 | (원문에서는 직접 다루지 않음) |
| **D**uration | 요청 처리 시간의 분포 | 지연 (latency) |

#### 왜 원문에서 CPU·메모리·네트워크를 먼저 안 꺼냈나

원문이 의도적으로 서비스 관점(RED 계열)부터 시작한 이유가 있다. **"CPU가 70%니까 CPU가 병목이다"라는 추론은 위험하다.** 원문 1.4절의 USE 방법론 테이블을 보면, OSIV 해제 전에 **DB CPU 70%, 앱 CPU 21%, 디스크 49%로 모든 자원이 절반씩 놀고 있는데 처리량이 안 올랐다.** 이럴 때 자원 지표만 보면 "어디도 병목이 아니다"로 판단하게 된다.

실제 원인은 **커넥션을 유휴 상태로 오래 잡고 있는 구조적 직렬화**였다. 이건 **서비스 관점 지표(커넥션 점유 시간 중 쿼리 비율 40%)로 먼저 잡히고**, 그 뒤에 자원 지표로 확인하는 순서가 맞다.

**결론: 두 관점을 동시에 써야 한다.** 실무에서의 진단 순서는 보통 이렇다:

```
1. RED로 서비스 이상을 감지 → "응답 느려짐, 에러율 상승"
2. USE로 어떤 자원이 포화인지 확인 → "CPU? 메모리? 네트워크? 커넥션 풀?"
3. 특정된 자원을 깊이 파고들기 → EXPLAIN, pg_stat_statements 등
```

> 참고: Tom Wilkie, *The RED Method: key metrics for microservices architecture*  
> https://grafana.com/blog/2018/08/02/the-red-method-how-to-instrument-your-services/

### Q2. 평균 동시 처리 건수는 커넥션 풀과 같은 자원을 의미하는 건가?

**비슷하지만 정확히 같지는 않다.** Little's Law에서 L(평균 동시 처리 건수)은 **시스템 안에 머물고 있는 요청의 평균 개수**다. 커넥션 풀은 그 L에 **상한(ceiling)을 거는 자원** 중 하나다.

| 개념 | 설명 | 원문의 예 |
|---|---|---|
| **L** (동시 처리 건수) | 시스템 안에 "머물고 있는" 요청의 평균 수. 처리 중이든 대기 중이든 상관없다. | 커넥션 5개를 잡고 있는 상태라면 L ≤ 5 |
| **커넥션 풀 크기** | L의 상한을 정하는 **물리적 제약** 중 하나 | `maximumPoolSize=5`이면 동시에 DB를 쓸 수 있는 건 최대 5 |
| **다른 자원들** | CPU 코어 수, 워커 스레드 수, 디스크 I/O 채널 수 등도 각각 동시성의 상한이 된다 | DB CPU 2코어 → 동시에 순수 CPU 작업을 할 수 있는 건 최대 2 |

**L을 커넥션 풀 크기로 놓은 것은** 그 시점에서 **커넥션 풀이 가장 먼저 포화되는 자원(가장 타이트한 병목)이었기 때문**이다. **병목인 자원**을 L의 상한으로 놓고 계산하면 시스템의 이론적 최대 처리량이 나온다.

### Q3. Little's Law에 대해서 자세히 알려줘

#### 공식

```
L = λ × W
```

| 기호 | 뜻 | 단위 |
|---|---|---|
| **L** | 시스템 안에 머물고 있는 항목의 **평균 개수** (average number in system) | 개 |
| **λ** (lambda) | 항목이 시스템에 **도착하는 평균 속도** (average arrival rate) | 개/초 |
| **W** | 항목이 시스템에 **머무는 평균 시간** (average time in system) | 초 |

아무 두 개를 알면 나머지 하나를 구할 수 있다: `λ = L / W`, `W = L / λ`

#### 누가 만들었나

**John D.C. Little** (1928~2024), MIT Sloan 경영대학원 교수.

- **1958년**: Philip M. Morse가 교과서에서 여러 모델에서 이 관계가 성립함을 보여주며, **"성립하지 않는 경우를 찾아보라"** 고 도전.
- **1960년경**: Case Institute of Technology 학생 Sid Hess가 **"이걸 일반적으로 증명하는 건 얼마나 어렵나요?"** 라고 질문.
- **1961년**: Little이 증명을 완성. *Operations Research* 학술지에 **"A Proof for the Queuing Formula: L = λW"** 발표.

#### 왜 대단한가

**아무런 가정이 필요 없다**: 도착 분포, 서비스 시간 분포, 서비스 순서(FIFO/LIFO/랜덤), 서버 수 모두 상관없다. **유일한 전제: 시스템이 정상 상태(steady state)**에 있어야 한다.

#### 성능 작업에서의 시사점

원문이 Little's Law를 쓰는 방식: `λ = L / W`

**(1) 처리량을 높이는 방법은 두 가지뿐이다** — L을 키우거나(자원 추가), W를 줄이거나(점유 시간 단축). 원문의 핵심 교훈은 **W를 줄이는 것이 훨씬 효과적**이라는 것이다.

**(2) "쿼리를 하나도 안 고쳐도 처리량이 2배"의 원리** — OSIV를 끈 것은 W(커넥션 점유 시간)를 430ms → 195ms로 줄인 것. L은 그대로인데 λ가 2배.

**(3) 일상 비유** — 식당 좌석 20석(L), 식사 시간 1시간(W) → 시간당 20팀. 식사 시간을 30분으로 줄이면 → 시간당 40팀. 좌석을 안 늘렸는데 2배. **이게 OSIV 해제와 정확히 같다.**

> 출처: Little, J.D.C. (1961). "A Proof for the Queuing Formula: L = λW". *Operations Research*, 9(3), 383-387.  
> Wikipedia, https://en.wikipedia.org/wiki/Little%27s_law

## 1.3 core-s/req와 blks/req

### Q4. core-s/req는 실제로 많이 쓰는 용어인가?

**"CPU seconds per request"** 라는 개념 자체는 널리 쓰인다. 약어의 표기가 조직마다 다를 뿐이다.

| 맥락 | 표기 / 용어 | 설명 |
|---|---|---|
| **서버리스 (AWS Lambda, GCP Cloud Functions)** | "GB-seconds", "vCPU-seconds" | 과금 단위 자체가 이 지표 |
| **Kubernetes / Prometheus** | `container_cpu_usage_seconds_total / http_requests_total` | PromQL로 정확히 이 값을 계산 |
| **클라우드 비용 최적화** | "cost per request" | FinOps에서 비용 귀속의 핵심 |
| **성능 엔지니어링** | "CPU time per transaction" | Oracle DB, SQL Server 튜닝에서도 같은 개념 |

**네트워크를 빼서 좋은 이유**: RPS는 ±11% 흔들리지만, `core-s/req`는 DB 호스트 CPU 시간만 보므로 노이즈가 작다. `workers=0` vs `workers=2`를 RPS로는 못 갈랐는데, `core-s/req`로는 2.1배 차이가 또렷이 나왔다.

> 출처: last9.io, "Understanding Core-Seconds Per Request", https://last9.io/blog/understanding-core-seconds-per-request/

### Q5. blks/req도 마찬가지?

**그렇다.** `blks/req = (만진 8KB 블록 수) ÷ (요청 수)`. 캐시 상태에 덜 흔들리는 "I/O 일의 양" 지표다.

| | core-s/req | blks/req |
|---|---|---|
| 측정 대상 | CPU 연산 비용 | 데이터 접근 비용 |
| 잘 잡는 것 | 파싱, 정렬, 해싱, 함수 계산 | 테이블/인덱스 스캔 범위, TOAST 접근 |
| 못 잡는 것 | I/O 대기 | 순수 CPU 작업 (블록을 안 건드리는 계산) |

**둘을 같이 보는 것이 핵심이다.** OSIV 해제 전후 `blks/req`가 17,621 → 16,903으로 거의 같았던 것이 "DB에 시킨 일은 그대로인데 처리량이 2배"의 결정적 증거였다.

# 2장. EXPLAIN (ANALYZE, BUFFERS) 읽는 법

### Q7. 부모와 자식의 시간 차이는 뭘 말하는 거지?

EXPLAIN ANALYZE 출력은 **트리(나무) 구조**다. **부모의 시간에는 자식들의 시간이 전부 포함**(inclusive time)되어 있으므로:

```
부모 시간 − 자식들 시간의 합 = 그 노드 자체가 소비한 시간 (exclusive time)
```

원문의 사례: 부모 86.5ms − 자식 1.2ms = **차액 85.3ms**. 조인은 1.2ms에 끝났는데 부모가 **행마다 표현식을 계산**하느라 85ms를 더 썼다.

> 비유: 팀장(부모)의 보고서 총 86분. 팀원들(자식) 작업 1분. 팀장 자신의 작업에 85분. 팀원을 최적화해도 1분만 줄지만, 팀장의 85분을 줄이면 극적 개선.

> 출처: PostgreSQL, *Using EXPLAIN* — https://www.postgresql.org/docs/current/using-explain.html

---

### Q8. 출력 표현식이 뭐야?

`EXPLAIN (VERBOSE)`를 붙이면 나타나는 **`Output:` 줄**. 각 노드가 **윗단에 넘겨주는 열과 계산식의 목록**이다.

```
Index Scan using article_pkey on public.article a
   Output: a.id, a.title, upper(a.title)    ← 출력 표현식
```

원문에서 `Output:`에 `l2_normalize(($1)::halfvec)`가 박혀 있는 것을 보고 "행마다 파싱"을 특정했다. `VERBOSE` 없이는 이 정보가 보이지 않는다.

> 출처: PostgreSQL, *EXPLAIN — VERBOSE* — https://www.postgresql.org/docs/current/sql-explain.html

### Q9. 노드가 뭐야?

**실행계획 트리를 구성하는 하나의 작업 단위.**

| 계층 | 대표 노드 | 하는 일 |
|---|---|---|
| **스캔 노드 (Leaf)** | `Seq Scan`, `Index Scan`, `Bitmap Heap Scan` | 테이블에서 행을 가져옴 |
| **조인 노드** | `Nested Loop`, `Hash Join`, `Merge Join` | 두 입력의 행을 결합 |
| **상위 노드** | `Sort`, `Aggregate`, `Limit`, `Hash`, `Materialize`, `Gather` | 가져온 행을 가공 |

데이터는 잎(leaf)에서 위로 올라간다. 각 부모 노드는 자식에게 "다음 행 줘"라고 요청하는 방식(Volcano/Iterator 모델).

---

### Q10. loops가 뭐야?

**해당 노드가 몇 번 반복 실행되었는지.** Nested Loop 조인의 안쪽(inner) 노드가 대표적 — outer에서 850행이 나오면 inner는 `loops=850`.

**핵심: `loops > 1`이면 표시된 시간은 1회 평균. 총비용 = actual time × loops.**

---

### Q11. rows 용도가 뭐야? 10배 이상?

`rows`는 **두 곳**에 나온다: (1) 플래너의 예측값 `cost=... rows=500`, (2) 실측값 `actual... rows=18585`.

**플래너는 예측 rows로 전략을 선택**하므로, 예측과 실제가 10배 이상 벌어지면 전략 자체가 잘못되었을 가능성이 높다. → `ANALYZE` 실행으로 통계 갱신.

---

### Q12. Nested Loop는 뭘 loop 돈다는 거야? OR절 같은 거?

**OR절과 관계없다.** 두 테이블을 **이중 for문**으로 조인하는 방식이다:

```java
for (Row outer : outerTable) {        // 바깥 루프
    for (Row inner : innerTable) {    // 안쪽 루프 (= loops 횟수)
        if (match) emit(outer, inner);
    }
}
```

실행계획에서 **위쪽 자식 = outer(구동 쪽)**, **아래쪽 자식 = inner(반복 탐색 쪽)**. OR절은 단일 테이블의 `BitmapOr`로 처리됨.

PostgreSQL 3가지 조인: **Nested Loop**(이중 for문), **Hash Join**(HashMap), **Merge Join**(정렬 후 대조).

> 출처: *The Internals of PostgreSQL*, Ch.3 — https://www.interdb.jp/pg/pgsql03/04.html

---

### Q13. Output의 역할이 뭐지?

Q8과 같다. `Output:` = **그 노드가 윗단으로 전달하는 데이터 목록**. 각 노드는 하나의 "미니 SELECT"이고, `Output:`은 그 SELECT 절에 해당. 여기에 복잡한 계산식이 있으면 **행마다 그 계산이 실행**된다.

---

### Q14. 노드 시간이 뭐야?

= Q7의 **배타 시간(exclusive time)**. `해당 노드 actual time − 자식들 actual time 합`. 이것이 크면 그 노드 자체가 비싼 작업(표현식 계산 등)을 하고 있다.

---

### Q15. target list나 필터의 표현식은 주로 WHERE 조건인가?

**WHERE만이 아니다.** 행마다 계산되는 모든 표현식이 해당:

| 종류 | EXPLAIN 위치 | SQL 출처 |
|---|---|---|
| **Output (target list)** | `Output:` | `SELECT` 절 |
| **Filter** | `Filter:` | `WHERE` 중 인덱스 못 타는 것 |
| **Index Cond** | `Index Cond:` | `WHERE` 중 인덱스 타는 것 |
| **Join Filter** | `Join Filter:` | `JOIN ON` 중 인덱스 못 타는 것 |

원문에서 범인은 `WHERE`가 아니라 **`Output:`(target list)**에 있었다 — 벡터 유사도 계산식.

---

### Q16. Bitmap Index Scan / Bitmap Heap Scan?

**2단계 구조**:

1. **Bitmap Index Scan**: 인덱스를 뒤져서 "어떤 페이지에 매칭 행이 있는지" **비트맵**을 만듦 (테이블 데이터 안 읽음)
2. **Bitmap Heap Scan**: 비트맵을 받아 **페이지 순서대로** 테이블을 읽음

Index Scan과의 차이: Index Scan은 행마다 즉시 테이블로 가서 **랜덤 I/O**. Bitmap은 모아서 **순차 I/O**. 중간 크기 결과에 좋음. **BitmapAnd/BitmapOr로 여러 인덱스 결합 가능.**

Recheck Condition: 비트맵이 `work_mem`을 넘으면 lossy 모드(페이지 단위로만 기록) → 페이지 읽은 뒤 행마다 조건 재검사.

> 출처: pganalyze, *Bitmap Heap Scan* — https://pganalyze.com/docs/explain/scan-nodes/bitmap-heap-scan

---

### Q17. Gather / Gather Merge?

**병렬 쿼리에서 여러 워커의 결과를 모으는 노드.** `Gather`는 순서 무관, `Gather Merge`는 정렬 유지(병합 정렬).

`Workers Planned: 2` = 계획, `Workers Launched: 2` = 실제 시작됨 (자원 부족 시 0 가능). 원문 15장에서 `max_parallel_workers_per_gather=0`으로 설정한 것이 이 기능을 끈 것.

---

### Q18. Materialize / Sort / Hash?

모두 **블로킹 노드** — 자식 결과를 전부 모은 뒤 처리:

| 노드 | 하는 일 | 위험 신호 |
|---|---|---|
| **Materialize** | 결과를 메모리/디스크에 캐싱 (반복 접근용) | 행 수 과다 |
| **Sort** | 전체 행 정렬 | `external merge Disk:` (work_mem 부족) |
| **Hash** | Hash Join용 해시 테이블 생성 | `Batches > 1` (work_mem 부족) |

---

### Q19. 실무 체크리스트 상세 설명

**① `Rows Removed by Filter` 크면**: 10만 행 읽고 10개만 남김 = 99.99% 헛읽음. → 인덱스 추가.

**② `Heap Fetches` 크면**: Index Only Scan이 무늬만. visibility map이 낡아서 힙에 가서 확인. → `VACUUM` 실행.

**③ `shared read` 크면**: 캐시 미스. 워킹셋이 `shared_buffers`에 안 들어감. → shared_buffers 늘리거나 접근 범위 줄이기.

**④ `external merge Disk:` 보이면**: 정렬 데이터가 `work_mem`(기본 4MB)을 초과해 디스크 정렬. → `work_mem` 늘리기 (⚠️ 노드마다 적용되므로 전역은 주의).

**⑤ `loops` 큰 노드**: actual time × loops = 총비용. `0.005ms × 50,000 = 250ms`.

**⑥ 예측 rows vs 실측 rows 10배 이상 차이**: 통계 낡음 → `ANALYZE` 먼저.

### Q20. TOAST를 무엇의 범인으로 지목한 거지?

**"벡터 검색 쿼리가 느린 원인"의 범인으로 지목.** 블록 카운터에서 "블록 접근의 64%가 TOAST"가 눈에 확 들어왔기 때문이다.

TOAST = PostgreSQL이 큰 데이터(TEXT, 벡터 배열 등)를 별도 테이블에 ~2KB씩 쪼개 저장하는 방식. 쿼리 시 투명하게 청크를 읽어 복원하며, 이 과정이 블록 카운터에 잡힌다.

**하지만 진범은 TOAST가 아니었다.** TOAST 블록 접근의 대부분이 캐시 히트(µs)였고, 시간은 **블록을 안 건드리는 파라미터 재파싱(순수 CPU)**에서 샜다. "관측 가능한 지표만 보면 관측 가능한 원인만 찾게 된다."

> 출처: PostgreSQL, *TOAST* — https://www.postgresql.org/docs/current/storage-toast.html

---

### Q21. 파라미터 텍스트 재파싱이 아무 데도 안 찍히는데 알게 된 계기가 뭐지?

**EXPLAIN ANALYZE의 "부모-자식 시간 차이"와 VERBOSE의 Output 줄이 결정적 단서.**

```
1단계: 블록 카운터 → "TOAST 64%" → 가설: TOAST가 범인
2단계: 가설 검증 → shared read가 커야 하는데 실제는 대부분 hit → ❌ 기각
3단계: EXPLAIN (ANALYZE, VERBOSE) → 부모 86.5ms − 자식 1.2ms = 차액 85ms
4단계: Output 줄에 $1 잔존 확인 → generic plan → 행마다 11.8KB 파싱
5단계: 850행 × 97µs = 82.5ms 예측 vs 86ms 실측 → 4% 이내 일치 → ✅ 확정
```

**핵심 방법론**: 범인을 지목한 뒤, 그 가설이 참이면 반드시 관측되어야 할 **"다른 것"을 하나 더 확인**. 이것이 오진을 막는다.

**도구별 역할**: pgss = "어떤 쿼리가 느린가", EXPLAIN ANALYZE = "어떤 노드가 느린가", VERBOSE = "무엇을 계산하는가".

### Q22. 3.4절 첫 번째 SELECT 쿼리는 무슨 원리로 뭘 측정하는 거지?

```sql
SELECT state, wait_event_type, wait_event, count(*)
FROM pg_stat_activity WHERE datname = current_database()
GROUP BY 1,2,3 ORDER BY 4 DESC;
```

**"지금 DB의 모든 프로세스가 무슨 상태인지" 스냅샷.**

| 상태 조합 | 해석 |
|---|---|
| `active` + `wait_event_type=NULL` | **순수 CPU 작업 중** (아무것도 안 기다림) |
| `active` + `IO` | 디스크 읽기 대기 |
| `active` + `Lock` | 락 대기 |
| `active` + `LWLock` | 내부 경합 |
| `idle` + `Client` | 클라이언트 명령 대기 (정상) |
| `idle in transaction` | ⚠️ 트랜잭션 열어놓고 놀고 있음 |

원문에서 `active + NULL`이 계속 지배적 = **병목이 CPU 연산**. TOAST(I/O)가 진범이면 `IO`가 많아야 하는데 실제로는 `NULL`.

# 5장. 통계와 autovacuum

---

### Q23. 그래서 내 경우에는 autovacuum이 이 테이블에 도달하지 못한 건가?

**가장 유력한 원인은 (b) 대량 쓰기(rebuild) 직후 통계 갱신 전**이다. 하지만 원문에서 확정 진단은 하지 않았고, 여러 후보를 열거했다. 자세히 살펴보자.

#### 원문의 상황

```
article_analyzed_content : n_live_tup = 204     (실제 18,585)
clova_chunk_vectors      : n_live_tup = 1,573   (실제 154,698)
```

100배 차이. 이 테이블들은 **임베딩 빌드 파이프라인**에서 대량으로 데이터를 넣는 테이블이다.

#### 후보별 분석

**(a) autovacuum이 이 테이블에 도달하지 못함**

autovacuum 데몬은 기본 `autovacuum_max_workers=3`개의 워커로, 모든 테이블을 순회한다. 테이블이 많으면 특정 테이블에 도달하기까지 시간이 오래 걸릴 수 있다. 하지만 이것은 보통 "약간 늦는" 수준이지, 100배 차이를 만들지는 않는다.

**(b) 대량 쓰기 직후 통계 갱신 전** ← 가장 유력

임베딩 빌드 파이프라인은 다음 과정을 거친다:
1. 기존 데이터를 `DELETE` 또는 `TRUNCATE`
2. 새 데이터를 대량 `INSERT`

autoanalyze의 트리거 조건: `변경된 행 > autovacuum_analyze_threshold(50) + 0.1 × n_live_tup`

문제는 **`n_live_tup` 자체가 낡은 값**이라는 것이다:
- `n_live_tup = 204`인 상태에서 트리거 조건 = `50 + 0.1 × 204 = 70.4`
- 18,585행을 넣었으면 70행 기준은 진작 넘었는데, **autoanalyze가 미처 돌기 전에 쿼리가 시작**되었을 수 있다
- 또는 `TRUNCATE` → 대량 INSERT 패턴에서, PostgreSQL 13 이전에는 INSERT만으로는 autovacuum이 안 돌았다 (dead tuple이 안 생기므로). PostgreSQL 13+에서 `autovacuum_vacuum_insert_threshold`가 추가되어 개선됨

**(c) pg_stat_* 카운터 리셋**

`pg_stat_reset()` 호출이나 서버 재시작 시 카운터가 리셋된다. 이 경우 `n_live_tup`이 0부터 다시 세기 시작하므로 실제와 크게 다를 수 있다.

#### 확인하는 방법

```sql
SELECT relname, n_live_tup, n_dead_tup,
       last_analyze, last_autoanalyze, last_autovacuum,
       n_ins_since_vacuum   -- PG 13+
FROM pg_stat_user_tables
WHERE relname IN ('article_analyzed_content', 'clova_chunk_vectors');
```

- `last_autoanalyze`가 `NULL`이거나 매우 오래됐으면 → autoanalyze가 한 번도 안 돌았거나 오래 전에 돌았음
- `n_ins_since_vacuum`이 매우 크면 → INSERT 후 vacuum이 안 돌았음

#### 원문이 적용한 해결책

테이블별 오버라이드로 임계값을 낮춤:

```sql
ALTER TABLE article_analyzed_content
  SET (autovacuum_analyze_scale_factor = 0.02,    -- 기본 0.1 → 0.02 (5배 민감)
       autovacuum_vacuum_scale_factor = 0.05);     -- 기본 0.2 → 0.05 (4배 민감)
```

이것은 "대량 rebuild가 있는 테이블은 기본 설정으로는 부족하다"는 판단이다. 추가로, 대량 빌드 직후 수동 `ANALYZE`를 실행하는 것이 가장 확실한 방법이다:

```sql
-- 대량 빌드 파이프라인 끝에 추가
ANALYZE article_analyzed_content;
ANALYZE clova_chunk_vectors;
```

> 출처: PostgreSQL, *Routine Vacuuming* — https://www.postgresql.org/docs/current/routine-vacuuming.html  
> PostgreSQL 13 Release Notes, *autovacuum_vacuum_insert_threshold* — https://www.postgresql.org/docs/13/release-13.html

# 6장. 프리페어드 스테이트먼트와 플랜 캐시 (6.3절)

---

### Q24. JDBC에도 이런 게(prepareThreshold) 있다고 하는데, 왜 있는 거임? DB에만 있어도 되는 거 아닌가?

**DB에만 있어도 "기능적으로는" 된다. 하지만 성능상의 이유로 JDBC 드라이버에도 별도 임계값이 있다.** 핵심은 **서버 측 프리페어드 스테이트먼트를 만드는 것 자체가 공짜가 아니기 때문**이다.

#### 서버 측 프리페어드 스테이트먼트를 만들면 뭐가 달라지나?

| 단계 | 서버 측 PS **없이** (기본 상태) | 서버 측 PS **있을 때** |
|---|---|---|
| 클라이언트 → 서버 | SQL 텍스트 + 파라미터 값을 **합쳐서** 한 번에 전송 | (1) `PREPARE`: 템플릿 전송, (2) `BIND`: 값 전송, (3) `EXECUTE` |
| 서버 처리 | 매번 파싱 → 계획 → 실행 | 최초 1회 파싱, 이후 값만 바꿔 실행 |
| 네트워크 왕복 | 1회 | 최초 생성 시 추가 왕복 필요 |
| 서버 메모리 | 없음 | 실행계획을 세션 메모리에 보관 |

#### 왜 JDBC 드라이버에 임계값이 필요한가

**(1) 서버 측 PS 생성에는 추가 네트워크 왕복이 필요하다**

서버 측 PS를 처음 만들 때, 드라이버는 PostgreSQL의 확장 쿼리 프로토콜(Extended Query Protocol)을 사용해서 `Parse → Bind → Describe → Execute` 메시지를 보낸다. 이것은 단순 쿼리(Simple Query Protocol)보다 **메시지가 더 많고**, 최초 실행 시 추가 왕복이 발생한다.

**한두 번만 실행할 쿼리**에 이 비용을 들이면, 절약하는 파싱 시간보다 **추가 왕복 비용이 더 크다.**

**(2) 서버 메모리를 소모한다**

서버 측 PS는 **세션(커넥션) 메모리에 실행계획을 보관**한다. 쿼리 종류가 수백 개이고 커넥션 풀이 20개이면, 수천 개의 실행계획이 메모리에 상주한다. 자주 안 쓰는 쿼리까지 전부 PS로 만들면 메모리 낭비다.

**(3) 커넥션 풀 환경에서의 생애주기 문제**

서버 측 PS는 **특정 커넥션에 종속**된다. 커넥션이 풀에서 반환되고 다른 요청에 재사용될 때, 이전에 그 커넥션에서 만든 PS가 그대로 남아 있다. 쿼리를 1-2번만 쓰는 경우에도 PS를 만들면, 커넥션이 재사용될 때마다 쓸모없는 PS가 쌓인다.

**(4) pgbouncer 같은 커넥션 프록시와의 호환성**

pgbouncer를 transaction pooling 모드로 쓰면, 서버 측 PS가 **작동하지 않는다**. 트랜잭션이 끝나면 실제 서버 커넥션이 바뀔 수 있어서 이전에 만든 PS가 사라지기 때문이다. 이 경우 `prepareThreshold=0`으로 설정해야 한다.

#### prepareThreshold의 역할 — "성능 안전 밸브"

`prepareThreshold`는 **"이 쿼리가 정말 반복되는 쿼리인가?"를 자동으로 판단하는 휴리스틱**이다:

```
실행 1~4회: "아직 모르겠다. 그냥 값과 함께 전체 SQL을 보내자."
           → Simple Query Protocol → 서버는 매번 실제 값으로 계획 (custom plan 효과)

실행 5회:   "이건 반복되는 쿼리다. 서버 측 PS로 승격하자."
           → Extended Query Protocol → 이후 파싱 비용 절약
```

이것이 없으면, 개발자가 모든 쿼리에 대해 **"이건 PS로 만들고 저건 안 만들고"를 수동으로 결정**해야 한다. `prepareThreshold`가 이것을 **사용 패턴에 따라 자동으로** 관리해준다.

#### 원문과의 연결 — 왜 이것이 중요했나

원문 6.3절에서 이 두 임계값(JDBC 5회 + PG 5회)이 겹치면서 **"운영 트래픽이 조금만 쌓이면 모든 커넥션이 generic plan"**이 된다고 했다:

```
JDBC 측 실행 1~4회: 클라이언트 측 (매번 값과 함께 전송) → 서버는 값을 보고 계획
JDBC 측 실행 5회:   서버 측 statement 생성 (PREPARE)
PG 측 실행 1~5회:   custom plan (값으로 최적화)
PG 측 실행 6회~:    generic plan 고착 ← ⚠️ 여기서 4.6배 느려짐
```

로컬에서 한두 번 실행하면 JDBC 임계값(5)에도 안 도달하니까 항상 custom plan이고 빠르다. **운영에서만 느려지는 이유가 이 2단계 임계값에 있었다.**

#### 설정 가이드

| 상황 | 설정 | 이유 |
|---|---|---|
| 일반적인 운영 | `prepareThreshold=5` (기본값) | 자동 관리에 맡김 |
| pgbouncer transaction pooling | `prepareThreshold=0` | 서버 측 PS 호환 불가 |
| 배치 작업 (같은 쿼리 수만 회) | `prepareThreshold=1` | 즉시 PS로 승격해 파싱 절약 |
| generic plan 문제 진단 | `prepareThreshold=0` | 모든 쿼리를 custom plan으로 돌려보고 차이 확인 |
