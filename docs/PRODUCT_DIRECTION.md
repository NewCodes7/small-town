# 제품 방향성 & 다음 단계 (PM 관점)

> 작성일: 2026-06-08 (v2 — 코드 대조 후 정정)
> 대상: small-town (기업 기술 블로그 큐레이션·검색 서비스)
> 목적: "한 단계 더 나아가기" 위한 방향 정리 + 개발자로서의 성장 관점
>
> **v2 변경 요약**: ① 분배(커뮤니티 시딩) 전략 추가 — 빠져 있던 가장 큰 구멍, ② Phase 1을 "재방문 해결책"이 아니라 "획득+활성화 플레이"로 정직하게 재라벨, ③ 측정·요약 자산이 코드상 "절반만 준비됨"을 반영(2개 이벤트 신규 계측 필요), ④ SEO 타임라인·프로그래매틱 페널티 리스크 명시, ⑤ 경쟁자(GeekNews 등) 포지셔닝 추가, ⑥ HN 모듈 "삭제 기한" 명시, ⑦ Phase 1 분량을 솔로 개발자 현실에 맞게 축소.

## 0. 솔직한 한 줄 진단

당신은 **기술적으로는 이미 충분히 잘 만들었다.** 하이브리드 검색(BM25+Vector NSF 리랭킹), 임베딩 파이프라인, SSE AI 요약, AI 셀렉터 자동 분석까지 — 이건 주니어가 만드는 사이드 프로젝트의 수준이 아니다.

**문제는 기술이 아니라 "왜 다시 방문해야 하는가"에 대한 답이 약하다는 것.**
지금 구조는 **검색 엔진**(찾으러 온 사람을 잘 응대)에 최적화돼 있는데, 재방문을 만드는 건 **피드/발견 경험**(굳이 찾을 게 없어도 들르는 곳)이다. 이 간극이 핵심이다.

그리고 당신이 나열한 아이디어 리스트(앱, 알림톡, 댓글, 뉴스레터, 테크뉴스, 카테고리 필터…)는 전부 "맞는 말"이지만, **전부 다 하면 전부 다 어중간해진다.** PM의 일은 아이디어를 더하는 게 아니라 **순서를 정하고 쳐내는 것**이다.

### 0-1. 경쟁자를 진공 상태에서 보지 마라

가치 제안은 경쟁자 대비로만 의미가 있다. 이 영역엔 이미:

- **GeekNews(news.hada.io)** — 한국 개발 "뉴스" 큐레이션+요약의 사실상 표준. "원문보다 빠르게 흐름 파악"은 *뉴스 영역에선 이미 GeekNews가 점유*하고 있다.
- **커리어리 / 디스콰이엇** — 개발자 콘텐츠·인사이트 피드.

→ 그러므로 small-town의 차별화는 "기술 뉴스를 빠르게"가 **아니다**(그건 진 싸움). 차별화는 **"국내외 top 기업의 *기술 블로그 그 자체*를, 회사·주제 단위로 깊이 있게 모으고 검색·요약하는 곳"**이다. 즉 *뉴스 속보*가 아니라 *기업 엔지니어링 아카이브*. 모든 카피·기능은 이 포지션으로 수렴해야 한다.

### 0-2. 정직하게: "요약"은 재방문을 *줄일* 수도 있다

뒤에서 핵심 베팅이 되는 "글 페이지 고유가치화(요약·목차)"는 **이탈을 쉽게 만드는 양날의 검**이다. 핵심만 얻고 떠나는 사람은 재방문 이유가 줄어든다. 그래서 이 투자는 **재방문이 아니라 획득(SEO)·활성화의 무기**로 봐야 정직하다. 재방문 엔진은 따로 있다(피드/팔로우/뉴스레터 — Phase 2~3).

## 1. 핵심 질문 재정의

> "어떻게 자주 방문하게 할까?" 는 너무 이른 질문이다.

먼저 답해야 할 질문 순서:

1. **(가치)** 이 서비스가 없으면 사용자가 아쉬운 게 정확히 뭔가?
2. **(활성화)** 처음 온 사람이 그 가치를 첫 방문에 경험하는가?
3. **(재방문)** 그 가치가 일주일 뒤에도 다시 필요한 이유가 있는가?

지금은 1번 답이 흐릿하다. 내가 보기에 가장 정직한 가치 제안은 이거다:

> **"기술 블로그를 다 읽을 시간은 없지만 흐름은 놓치고 싶지 않은 개발자"가, 국내외 top 기업들이 지금 뭘 쓰고 있는지 원문을 읽는 것보다 빠르게 파악하는 곳.**

핵심 동사는 **읽기**가 아니라 **추리기(digest) + 발견(discover)**. 원문 블로그와 경쟁하면 안 된다 — 원문으로 가는 **가장 좋은 관문**이 되어야 한다.

## 2. 전략: 한 곳에 집중 — "발견 + 소화의 깊이"

당신의 아이디어들을 두 축으로 분류하면:

| | 획득(Acquisition) | 재방문(Retention) |
|---|---|---|
| **넓히기(Breadth)** | 기업 추가 AI, 테크뉴스, SEO | 뉴스레터, 알림 |
| **깊게(Depth)** | 3줄요약·목차·AI댓글로 페이지 가치↑ | 추천탭, 카테고리 필터, 팔로우 피드 |

여기서 가장 레버리지가 큰 사분면은 **"깊게"** 다. 이유:

- **3줄요약 / 목차 / AI 반응**을 모든 글에 붙이면 → 각 글 페이지가 **원본을 그대로 베끼지 않은 고유 가치 페이지**가 된다 → **그게 곧 SEO 자산**이 된다(아래 6장). 즉 "깊게"가 "획득"까지 끌고 온다.
- 동시에 그게 **재방문의 이유**(여기 오면 글을 안 읽어도 핵심을 안다)도 만든다.

→ **하나의 투자(글 페이지 가치 향상)가 SEO·활성화·재방문을 동시에 친다.** 이게 지금 당신이 칠 단 하나의 핀이다.

## 3. 단계별 로드맵

### Phase 1 (지금 ~ 6주) — "글 하나하나를 무기로" + 측정 깔기 + 분배 시작

**이 단계의 정체: 재방문이 아니라 *획득(SEO) + 활성화* 플레이다.** (0-2 참고) 재방문은 Phase 2~3가 푼다. Phase 1을 "재방문 해결책"으로 기대하지 마라 — 그건 과대 포장이고 나중에 지표가 배신한다.

**목표: 모든 글 페이지를 "원문보다 먼저 보는 소화 페이지"로 만들고, 그 가치를 *측정할 수 있게* 만든다.**

> ⚠️ **솔로 개발자 현실 점검**: 아래를 4주에 다 하는 건 불가능하다("전부 다 하면 어중간"이 Phase 1 자신에게도 적용된다). **반드시 자를 것** → 대시보드를 만들지 말고 raw SQL로 본다. "모바일 다듬기"는 모달이 안 깨지는 수준까지만. 핵심은 **digest 모달 + 2개 이벤트 계측** 단 하나다.

- [ ] **목차(TOC)부터** — 코드 확인 결과 `ArticleSummary`는 `content_type = "h3, li"` 구조라 **이미 목차/개요에 가깝다.** 이걸 글 상세/모달에 노출하는 게 가장 빠른 승리. (생각보다 준비돼 있음)
- [ ] **3줄 요약은 *신규 생성* 필요** — `ArticleSummary`는 3문장 초록이 아니다(h3/li 구조). 진짜 3줄 요약은 별도 LLM 호출로 새로 만들어야 한다. "재활용"이 아님에 주의.
- [ ] **글 클릭 → 모달**로 요약/목차 먼저, "원문 읽기"는 명확한 CTA로 (관문 패턴)
- [ ] **측정 — "이미 있다"는 절반만 사실(코드 확인)**: `ArticleClickLog`는 *글로 들어오는 유입(source)*만 기록한다. 문서가 원하는 두 전환 지표는 **계측 자체가 없다** →
  - [ ] **요약/목차 펼침 이벤트** 신규 추가
  - [ ] **원문 이동(아웃바운드 클릭) 이벤트** 신규 추가
  - → 이 2개를 **먼저 심고 → 데이터가 쌓일 시간을 준 뒤** baseline을 기록한다. "기존 데이터로 즉시 baseline"은 불가능하다.
- [ ] **분배 시작(병행)**: Search Console 등록 + sitemap(아래 6장)은 5분짜리니 끼워넣되, **진짜 초기 트래픽은 커뮤니티 시딩에서 온다 → 6-1장 참고.** SEO만 기다리지 마라.
- [ ] **모바일은 "안 깨지게"까지만** (앱 X — 5장). 풀 리디자인은 데이터 본 뒤.

> AI 댓글(여러 AI 반응 제시)은 **재미있지만 Phase 1엔 넣지 마라.** 차별화 포인트가 될 수 있으나 검증 안 된 기믹이다. Phase 2에서 작은 실험으로.

### Phase 2 (4~10주) — "발견 경험" 구축 + 공급 확장

**목표: 검색 안 해도 둘러볼 가치가 있는 홈을 만든다.**

- [ ] **new-home 재설계**: 당신 직감이 맞다 — **HN/유튜브는 홈에서 걷어내라.** 블로그 콘텐츠로 정체성을 명확히. (코드는 삭제 말고 별도 탭/페이지로 격리)
  - ⚠️ **단, "격리"에 기한을 박아라.** HN 모듈은 매시 스케줄러 + DeepL 번역 비용을 계속 먹는다. 7장이 설교하는 "기능 죽이기"를 여기서 실천하라 → **격리 후 8주 내 HN 탭 트래픽이 전체의 (예) 5%를 못 넘으면 스케줄러·번역 종료하고 모듈 제거.** 좀비 모듈을 안고 가는 건 이 문서가 비판한 바로 그 "도구만 늘어남"이다.
- [ ] **카테고리·태그 필터링** (이미 `Category`/`Tag` 엔티티 있음)
- [ ] **추천/큐레이션 탭**: `RelatedArticleService` 임베딩 활용 + "이번 주 많이 본 글", "주제별 모음"
- [ ] **기업 대량 추가**: `AI 블로그 등록 큐`(V1_18) 활용해 공격적으로 30~50개 기업 온보딩. 공급이 곧 검색·SEO 표면적이다.
- [ ] **AI 댓글 실험** (선택): "이 글에 대한 AI 패널 반응" — A/B로 체류시간 보고 판단.

### Phase 3 (10주~) — "잊지 않게" 재방문 루프

**목표: Phase 1·2로 콘텐츠가 충분히 쌓이고 활성화 지표가 검증된 뒤에만 착수.**

- [ ] **이메일 뉴스레터** (알림톡보다 먼저 — 비용·승인 장벽 낮음). "이번 주 top 기업 블로그 요약 5개" 큐레이션 발송.
- [ ] **팔로우 → 새 글 알림** (웹푸시/이메일). 이게 진짜 재방문 엔진. 단, **콘텐츠 다양성(Phase 2)이 먼저 있어야** 팔로우할 맛이 난다.
- [ ] 카카오 알림톡, 앱은 그 다음. (6장)

## 4. 우선순위 한눈에 (지금 당장 vs. 나중)

| 아이디어 | 판단 | 이유 |
|---|---|---|
| **커뮤니티 시딩(직접 글 공유)** | **🟢 지금(최우선 분배)** | 초기 트래픽의 진짜 출처. 즉각 피드백 + 백링크 → SEO 연료. 비용 0 |
| 목차(TOC) 노출 | **🟢 지금** | `ArticleSummary`(h3/li)가 이미 거의 준비됨 — 가장 빠른 승리 |
| 3줄요약 + 글 모달 | **🟢 지금** | 획득(SEO)+활성화 무기. 단 요약은 *신규 생성* 필요(재활용 아님) |
| 측정 2개 이벤트 신규 계측 | **🟢 지금** | 요약 펼침·원문 이동은 *계측 자체가 없음*. 이거 먼저 |
| HN/유튜브 홈에서 제거 | **🟢 지금** | 정체성 선명화. + 8주 내 트래픽 미달 시 **제거 기한 설정** |
| 기업 대량 추가(AI큐) | **🟡 곧** | 공급=SEO표면적, 이미 도구 있음 |
| 카테고리 필터·추천탭 | **🟡 곧** | 발견 경험, 엔티티 이미 존재 |
| 테크뉴스 종합 정보 | **🟡 곧(좁게)** | "큐레이션"으로만. 원문 호스팅 금지(5장) |
| 프로그래매틱 SEO 모음페이지 | **🟡 곧(주의)** | 롱테일에 강함 *but* 각 페이지에 고유 텍스트 없으면 페널티(6장) |
| AI 댓글 | **🟠 실험** | 차별화 가능성 but 미검증 기믹 |
| 이메일 뉴스레터 | **🔵 Phase 3** | 콘텐츠 쌓인 뒤 |
| 팔로우 알림 | **🔵 Phase 3** | 다양성 확보 후 |
| 카카오 알림톡 | **🔴 보류** | 비용·승인 장벽, 이메일로 먼저 검증 |
| 모바일 앱 출시 | **🔴 보류** | 과도한 투자, PWA로 충분 |

> ⚠️ **SEO를 "지금 레버"에서 뺀 이유**: 신규 도메인 SEO는 4주가 아니라 **6~12개월 복리 게임**이다. 동기부여가 필요한 솔로 개발자가 핵심 전략을 가장 느린 피드백 채널에 걸면 안 된다. SEO는 *커뮤니티 시딩(즉각 피드백 + 백링크)*이 먼저 깔아준 위에서 복리로 따라온다. 순서: **분배(빠름) → SEO(느림)**.

## 5. 명확하게 "하지 마라"고 말하는 것들

PM으로서 가장 가치 있는 조언은 **막는 것**이다.

- **앱 출시 — 지금은 절대 아니다.** 앱은 유지보수·배포·스토어 심사·푸시 인프라 비용이 막대하다. 당신이 풀려는 문제(팔로우 글 알림)는 **웹푸시 + PWA**로 90% 해결된다. 앱은 "웹에서 재방문이 이미 증명된 뒤" 채널 확장으로만 정당화된다. 지금 만들면 아무도 안 깐 앱을 유지보수하느라 본질을 못 건드린다.
- **카카오 알림톡 — 이메일 검증 후.** 알림톡은 비용·템플릿 승인·발송 사유 제약이 있다. 재방문 메시지가 통하는지부터 이메일(무료에 가깝게)로 검증하라.
- **원문 전문(full text) 호스팅 — 금지.** 저작권 + 구글의 중복 콘텐츠 페널티 둘 다 맞는다. **요약·목차·AI 반응 같은 "고유 가치"만** 호스팅하고 본문은 원문으로 보낸다. 이건 법적/SEO 양쪽에서 중요한 선이다.
- **새 기능을 측정 없이 추가 — 금지.** 지금 `ArticleClickLog`까지 만들어 놓고 그걸 안 보고 다음 기능 만들면 도구만 늘어난다.

## 6. SEO 구체 전술 (당신이 명시적으로 원한 것)

SEO는 "마법"이 아니라 **고유한 가치 페이지를 많이, 잘 구조화해서 쌓는 것**의 결과다.

1. **고유 가치 페이지화**: 3줄요약·목차·AI코멘트가 above-the-fold에 오면 구글이 "원본 복붙이 아닌 가치 있는 페이지"로 인식한다. (Phase 1이 곧 SEO다)
2. **프로그래매틱 SEO (단, 페널티 주의)**: `/corporation/{회사}` 페이지를 "OO 기업 기술 블로그 모음 + 요약"으로, `/tag/{주제}`, `/theme/{테마}` 페이지를 자동 생성. 이런 모음 페이지가 롱테일 검색에 강하다.
   - ⚠️ **그러나 자동 생성 자체가 좋은 게 아니다.** 구글의 최근 *"site reputation abuse / unhelpful content / doorway page"* 업데이트가 정확히 때리는 패턴이 "고유 텍스트 없는 대량 자동 생성 모음 페이지"다. **각 모음 페이지에 사람이 쓴(또는 LLM이 그 회사/주제 맥락으로 생성한) 고유 한 문단 + 큐레이션 의도**가 반드시 있어야 한다. 빈 껍데기 리스트 페이지를 수백 개 찍으면 도메인 전체가 평가절하된다.
3. **구조화 데이터**: `schema.org/Article`, `BreadcrumbList` JSON-LD 삽입. 요약을 `meta description`으로.
4. **sitemap.xml 자동 갱신** + Search Console 등록 → **노출/클릭 지표를 실제 KPI로** 본다.
5. **Core Web Vitals / 모바일**: 구글 랭킹 직접 요소. Phase 1 모바일 다듬기와 직결.
6. **내부 링크**: `RelatedArticleService`로 글↔글 연결 강화 (크롤 효율 + 체류).

> 한 줄 요약: **"콘텐츠 늘리기 = 기업 추가(공급) + 글마다 고유 가치 붙이기(Phase1)" 이 두 개가 SEO의 90%다.** 테크뉴스를 무작정 늘리는 것보다 이게 먼저다.

### 6-1. 분배(Distribution) — 이 문서 v1에서 통째로 빠졌던, 가장 큰 구멍

SEO는 가장 *느린* 채널이다. 그 위에서 복리가 돌려면, **먼저 사람이 직접 끌어오는 빠른 루프**가 필요하다. 한국 개발자 대상 기술 큐레이션 제품의 초기 트래픽은 거의 항상 **커뮤니티 시딩**에서 나온다. (GeekNews 자체가 그 증거다.)

왜 SEO보다 *먼저*인가:

- **피드백이 즉각적이다.** SEO는 6개월 뒤에야 맞았는지 알지만, 커뮤니티 글은 그날 반응으로 안다. 솔로 개발자에게 이 빠른 피드백 = 지속 동력.
- **백링크를 만든다 → 그게 다시 SEO 도메인 어소리티를 올린다.** 즉 분배가 SEO의 *연료*다. 순서가 거꾸로면 둘 다 안 된다.
- 7장이 말한 "분배를 한 번은 직접 경험하라"의 **가장 좋은 첫 연습**이 바로 이 수동 시딩이다(SEO 세팅보다 낫다).

**구체 액션 (Phase 1과 *병행*):**

1. **매주 1~2회**, small-town에서 *진짜 좋은* 기업 블로그 글/모음을 골라 **GeekNews, 커리어리, 디스콰이엇, 관련 페북·디스코드·슬랙 개발자 그룹, (영문이면) r/programming**에 직접 공유. 스팸이 아니라 "큐레이터의 추천"으로.
2. 공유할 때 **small-town의 고유 가치 페이지(요약·목차 모달)로 링크** — 원문 직링크가 아니라. 그래야 유입이 제품을 경험한다.
3. 어느 커뮤니티가 클릭/체류로 이어지는지 `ReferralSource`/UTM으로 측정 → **잘 되는 한두 채널에 집중.**
4. 이 루프를 **최소 8주는 사람이 직접 돌린다.** 자동화·뉴스레터는 그다음.

> 한 줄: **SEO(느림) 이전에 커뮤니티 시딩(빠름)이 있어야 한다. 분배는 SEO의 연료이고, 솔로 개발자가 가장 안 해본 근육이다.**

## 7. 개발자로서의 성장 관점 (당신이 물어본 것)

솔직히 말한다. 당신의 **백엔드/검색/AI 인프라 역량은 이미 시장 평균을 한참 넘었다.** 여기서 인프라를 더 화려하게 만드는 건 **성장 곡선이 완만**하다. 다음 레벨의 성장은 다른 근육에서 나온다:

1. **"만드는 사람"에서 "선택하는 사람"으로.**
   강한 엔지니어의 함정은 *아무도 안 쓰는 멋진 걸 계속 만드는 것*. `ArticleClickLog`를 이미 만든 건 신호가 좋다 — 이제 **그 데이터를 보고 기능을 죽이는 경험**을 해라. "측정 → 가설 → 실험 → 폐기/확장" 루프를 한 바퀴 도는 게 새 모듈 5개보다 커리어에 값지다.

2. **AI-네이티브 제품 엔지니어링에 베팅하라.**
   이미 Clova 임베딩, Gemini SSE, AI 셀렉터 분석을 한다. 이건 지금 시장에서 가장 비싼 스킬셋이다. "AI를 붙인 검색"을 넘어서 **"AI가 콘텐츠를 소화·재구성하는 제품"**(요약·목차·AI 패널 반응·자동 큐레이션)으로 깊게 들어가면, 제품 차별화 + 커리어 포지셔닝이 동시에 강해진다.

3. **분배(distribution)를 한 번은 직접 경험하라 — 이게 진짜 성장 모서리.**
   엔지니어가 보통 약한 부분이 SEO/그로스/리텐션이다. 그런데 그중에서도 **가장 안 해본 근육은 SEO 세팅이 아니라 "사람이 직접 끌어오는 분배"**다. 이번에 GeekNews·커리어리 같은 데 *직접 글을 올리고 반응을 보는 루프*(6-1장)를 한 바퀴 돌려봐라. 자동화·뉴스레터·SEO보다 이게 먼저고, 더 값지다 — "기술을 사용자에게 닿게 하는" 전 과정을 몸으로 아는 드문 엔지니어가 된다. 이게 시니어/창업/PM-엔지니어 어느 방향으로 가든 복리로 작동한다.

> 성장 관점 결론: **"더 어려운 걸 만든다"가 아니라 "만든 게 실제로 쓰이게 만든다"가 지금 당신의 성장 모서리다. 그 첫 연습은 코드가 아니라, 좋은 글 하나를 골라 직접 커뮤니티에 공유하고 반응을 보는 것이다.**

## 8. 다음 2주 액션 (구체적으로)

1. **계측 먼저(2개 신규 이벤트)**: ① 요약/목차 펼침, ② 원문 이동(아웃바운드 클릭). `ArticleClickLog`엔 이 둘이 *없다* — 새로 심어야 데이터가 생긴다. raw SQL로 본다(대시보드 X).
2. **목차(TOC) 노출**: `ArticleSummary`(h3/li)가 이미 거의 준비됨 — 가장 빠른 승리부터.
3. **3줄 요약 신규 생성 + 글 모달**(요약·목차 먼저) 프로토타입, 모바일 우선. (요약은 재활용 아님 — 별도 LLM 호출)
4. **HN/유튜브를 new-home에서 분리**(별도 탭 격리) + **제거 기한 캘린더에 박기**(8주 뒤 트래픽 확인).
5. **분배 루프 시작**: 이번 주부터 GeekNews/커리어리 등에 *직접* 1~2건 공유(6-1장). + Search Console 등록 + sitemap(5분).

그 다음, **1번에서 데이터가 쌓이기를 기다린 뒤(즉시 baseline 불가)** 그 숫자와 5번 분배 반응을 보고 Phase 2 우선순위를 다시 정한다.
